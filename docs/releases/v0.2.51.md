# v0.2.51 — 시작도 못 한 실행을 시작한 것처럼 말하지 않고, 샌드박스 거부는 원인과 출처를 짚는다 (A53·A54·A55)

2026-11-03. grok이 **시작하기도 전에** 끝난 위임에서 래퍼가 세 가지를 틀리게 말했다. 미리 정한 세션 id를 이어갈 세션처럼 돌려줬고
(A53), 다른 폴더의 세션을 이어가다 거부된 실행에 "그 폴더에서 작업했다"고 했으며(A55), 샌드박스 때문에 거부된 실행의 원인과 출처를
짚지 못하고 통하지 않는 해결책까지 권했다(A54). 세 항목은 2026-09-30에 grok 1.0.44로 찾았고, 이번에 1.0.70으로 다시 잰 뒤
고쳤다 — 모두 1.0.70에서도 재현됐다.

## 재현 (쿼터 0 — grok 1.0.70, win32와 Linux 컨테이너, 실제 `~/.grok` 미접촉)

모든 측정은 버릴 홈(`GROK_HOME`·`HOME`·`USERPROFILE`·`APPDATA`·`LOCALAPPDATA`)과 합성 세션(`scripts/synthetic-auth.mjs`)으로 했고,
grok의 API 주소 둘을 **모든 요청에 404로 답하는 루프백**으로 돌렸다 — 서버가 합성 세션을 거절하면 grok이 브라우저 로그인을 열기
때문이다(A68, 계약 §7 E). 로그인은 한 번도 시작되지 않았다. Linux는 Docker(`node:22-bookworm`에 설치 스크립트로 넣은 1.0.70,
bubblewrap 유무·root와 uid 1000·`--privileged` 유무)다. 같은 페이로드를 v0.2.50 번들과 이 릴리스의 번들로 쳤다.

**A53 — 미리 정한 세션 id.** 래퍼는 새 실행마다 `--session-id`를 정해 넘기고(B1), 결과 봉투가 id를 적지 않으면 그 id를 돌려준다.

| 결말 | 세션 폴더 | v0.2.50: 응답·이력·`lastSession` | v0.2.51 |
|---|---|---|---|
| 깨진 `config.toml` (delegate·plan) | 없음 | 그 id | 없음 |
| 갱신이 실패한 만료 세션 ("Not signed in") | 없음 | 그 id | 없음 |
| 시작 전 캡 (`timeout_ms: 1`) | 없음 | 그 id + "`/grok:resume`으로 이어갈 수 있습니다" | 없음, 약속도 없음 |
| Linux 샌드박스 거부 | 없음 | 그 id | 없음 |
| 대조 — 모델 요청까지 간 실행, 실행 도중 캡, 모르는 `--model` | 있음 | 그 id | 그 id (캡은 약속도) |

세션 폴더가 없는 id를 이어가면 grok은 원격 복원을 시도하다 실패한다(계약 §12). 모르는 `--model`("Couldn't set model")은
1.0.70에서 세션 폴더를 남겼고 그 세션은 이어졌다 — 2026-09-30 계획이 다섯 번째 모양으로 적은 "세션 없음"은 1.0.70에서 맞지 않는다.

**A55 — "그 폴더에서 작업했다".** 세션이 속한 폴더와 다른 폴더에서 resume하면 래퍼는 `resumedCwd`와 "resume한 세션은 …에
속해 있어 … 그 디렉터리에서 작업했습니다"를 붙인다(A3). v0.2.50은 grok이 **시작 전에 거부한** resume에도 그것을 붙였다 —
프로필 변경 거부(delegate·plan·verify), 깨진 `config.toml`, "Not signed in", 환경변수가 준 프로필. 이력 행에도 `resumedCwd`가
남았다. Linux에서도 같았다 — 다른 폴더에서 이어간 `workspace` 세션이 샌드박스에 거부되거나(namespace·bubblewrap 없음) `off`로의 변경으로
거부된 네 경우 모두 v0.2.50은 `resumedCwd`를 붙였다. v0.2.51은 이들에 붙이지 않는다. 두 번째 방법: 거부된 실행 동안 세션 폴더의
파일은 바이트까지 그대로였고, 시작한 resume은 `chat_history.jsonl`을 늘렸다. 시작한 resume에는 그대로 붙고, timeout에는 "그 디렉터리에서
작업했을 수 있습니다 — 시간 초과로 멈춰, 시작했는지는 알 수 없습니다"로 붙는다(1 ms 캡은 세션 파일을 건드리기 전이었다).

**A54 — 샌드박스 거부의 원인과 출처.** ① `read-only` 세션을 서버의 `GROK_SANDBOX=workspace`로 이어가면 grok은 거부하는데, v0.2.50의
응답은 일반 메시지와 grok의 "Omit --sandbox"뿐이었다 — 요청은 이미 `sandbox`를 생략했다. ② Linux에서 `$GROK_HOME/config.toml`의
`[sandbox] profile`이 거부를 낳아도 메시지는 원인으로 `GROK_SANDBOX`만 댔다. ③ bubblewrap은 있는데 namespace를 못 만드는 거부(root와
uid 1000이 다르게 말한다)도 원인을 말하지 않았다. 그리고 **resume에서는 메시지의 첫 해결책 `sandbox: "off"`가 통하지 않았다** —
bubblewrap이 도는 곳에서 만든 `workspace` 세션을 못 도는 곳에서 이어가면 저장된 프로필이 적용돼 거부되고, `sandbox: "off"`나
`GROK_SANDBOX=off`는 프로필 변경으로 또 거부됐다(1.0.70 Linux에서 새로 잰 것).

## 고친 것 (`mcp-server/src/delegate.ts` — argv·env는 그대로, 응답 필드는 더하지 않았다)

- **A53:** 미리 정한 id는 grok이 그 세션 폴더(`<GROK_HOME>/sessions/*/<id>`)를 만들었을 때만 돌려준다 — 모든 인코딩 폴더에서
  찾고(긴 이름의 A69 폴더 포함, 디코딩하지 않는다), 실행 **뒤에** 한 번만 본다(grok이 실행 중에 만든다). 결과 봉투가 id를 적었으면
  찾지 않는다. timeout의 resume 약속도 같은 답을 따른다. 브라우저 로그인으로 멈춘 실행(A68)의 같은 확인도 이것으로 합쳤다.
- **A55:** stderr가 시작 전 거부로 **시작하면**(프로필 변경 거부, `Error: Failed to load config`, `Error: Not signed in`, 샌드박스
  거부 문장, 머리의 `bwrap:`) 그 resume에는 `resumedCwd`와 안내를 싣지 않는다. 캡으로 끝난 실행은 해당하지 않는다 — grok이 시작해
  부분 편집을 남겼을 수 있어, 안내를 "작업했을 수 있습니다"로 말한다(로그인으로 멈춘 실행은 A68대로 안내가 없다). 머리에 앵커하는 이유: grok이 세션을
  불러온 resume은 `Session … found locally (originally in …)`를 먼저 찍는다(측정). A33의 넷째 거부 문구(`sandbox initialization failed`,
  1.0.70에서는 보지 못했다)도 같은 목록에 있다. "빈 stdout"은 조건이 아니다 — "Not signed in"은 stdout에도 오류 봉투를 찍는다.
- **A54 ①:** resume·continue의 stderr가 프로필 변경 거부로 시작하면 전용 메시지를 낸다 — 세션의 프로필, 받은 프로필, 그 출처(요청의
  `sandbox`, 없으면 `GROK_SANDBOX`)와 이어가는 플래그 `sandbox: "<세션 프로필>"`(요청의 `sandbox`가 env를 이긴다 — 측정). 그 플래그는
  **이 환경이 그 프로필을 적용할 수 있을 때만** 이어진다고 따로 한 문장으로 말한다(세션 이름을 읽지 못했을 때도 — `off` 세션으로 알려진
  때만 빼고) — Linux에서 bubblewrap을 못 쓰는 곳의 `workspace` 세션은 그 프로필로도 `off`로도 이어지지 않았다(측정). 받은 프로필이
  `off`면 새 세션(그곳에서 통한 유일한 길)을 먼저 말한다. `off`는 세션이 `off`로 만들어졌을 때만 권하고, 변수를 지우라고 할 때는 이 MCP
  서버를 다시 띄우라고(Claude Code라면 재시작) 함께 말한다 — 서버의 env는 그 호스트가 띄울 때 정해진다. grok의 두 문구(1.0.44의 `—`,
  1.0.70의 `:`)를 다 읽는다.
- **A54 ②③:** A33 메시지가 사유(찾지 못한 프로필 이름·bubblewrap 없음·namespace 거부 — grok의 말이 정확히 한 사유를 가리킬 때만:
  "설치돼 있지 않다"는 `bwrap exec failed: No such file or directory`일 때만, namespace는 머리의 `bwrap:` 줄이 namespace를 말할 때만;
  그 밖에는 rawStderrTail)와 출처(요청의 `sandbox` → `GROK_SANDBOX` → resume·continue면 이어간 세션의 저장된 프로필, 아니면 그 홈의
  `config.toml`의 `[sandbox] profile` — 경로만 대고 값은 읽지 않는다)를 댄다. 새 실행에는 `sandbox: "off"`(요청·env·config를 다
  이긴다 — 측정)와 출처별 해결책을, resume에는 `off`가 아니라 그 프로필을 적용할 수 있는 환경이나 새 세션을 권한다(모르는 이름이면
  다시 정의하라고만 한다 — 내장 프로필은 resume에서 변경이다). 메시지에 싣는 프로필 이름은 안전한 토큰일 때만이다(env 값은 무엇이든
  될 수 있다).

## 1.0.70에서 새로 잰 것 (계약 §11–§13에 옮겼다)

- 프로필 변경 거부 문장의 구두점이 바뀌었다(`… profile 'X': it was created with 'Y'`). 모델 요청 전, exit 1, stdout 0바이트.
- 플래그가 `GROK_SANDBOX`를 이기고, resume은 `off`로 바꾸는 것도 거부한다. `config.toml`의 `[sandbox] profile`은 resume에 적용되지
  않는다(win32·Linux) — 새 실행에만 적용된다. Linux에서 `<cwd>/.grok/config.toml`은 적용되지 않았다.
- win32는 모르는 프로필 이름을 거부하지 않았다 — 그 실행은 모델 요청까지 갔다(Linux는 해석 오류로 죽는다).
- 세션 폴더는 grok이 시작해야 생긴다(위 A53 표). 세션의 프로필은 `summary.json`의 `sandbox_profile`에 있다.
- Claude Code 플러그인이 설치된 홈(grok은 그 MCP 서버를 띄운다 — 계약 §14)에서도 거부의 stderr는 거부 문장 한 줄이었다 — 앵커한
  신호가 실제 사용자 환경에서도 맞는다(win32·Linux). `--continue`도 `config.toml`이 아니라 세션의 프로필로 시작했다. Linux에서 resume에
  다른 프로필을 주면 샌드박스 적용보다, 모르는 이름을 주면 이름 해석보다 프로필 변경 거부가 먼저다 — resume에서 "찾지 못한 프로필"은 세션
  자신의 프로필 이름이 풀리지 않을 때만 나온다(그래서 "다시 정의하세요"가 맞다).

## 하지 않는 것 · 남는 것

- **이미 기록된 이력 행의 id는 그대로다.** v0.2.50까지 시작도 못 한 실행이 남긴 id는 `~/.grok-build/history.jsonl`에 남고,
  `/grok:status`·`/grok:usage`의 `lastSession`은 가장 최근에 id가 있는 행을 고르므로 그 행이 가장 최근이면 여전히 그 id를 권한다.
  새 실행이 쌓이면 밀려난다.
- timeout에는 resume 안내를 계속 붙인다(그 세션 폴더가 있으면 이어가기 약속도) — 래퍼는 grok이 시작했는지 모르므로 "작업했을 수
  있습니다"로 말한다(1 ms 캡은 시작 전이었지만 실제 캡은 대개 시작 뒤다).
- 거부 문장은 grok의 출력이지 계약이 아니다 — 문구가 바뀌면 신호가 맞지 않아 예전의 일반 메시지와 안내로 돌아간다(새 주장을
  만들지 않는 쪽).
- 더 넓은 변경은 하지 않았다 — 세션 프로필 자동 주입, grok에 넘기는 env에서 `GROK_SANDBOX` 지우기, 응답의 출처 필드, `config.toml` 값
  읽기. 하려면 오너 목표가 먼저다(계획 `docs/plans/2026-09-30-handoff-plan.md`의 A54 절). 응답에 "샌드박스가 작동했다"를 싣지 않는 것은
  그대로다(`docs/10` B4).
- win32의 샌드박스가 무엇을 막는지는 재지 않았다 — 메시지는 그것을 주장하지 않는다.

## 검증

- `delegate.test.ts`의 A53·A54·A55 묶음에서 결함을 재는 테스트는 고치기 전 소스에서 빨강이고 고친 뒤 통과한다. 대조군(세션이 있는
  B1 핸들, 시작한 resume의 안내)과, 옛 메시지도 지키던 것을 새 메시지가 지키는지 보는 가드(원인을 단정하지 않는 칸들, "설치돼 있지 않다"를
  ENOENT에만 쓰는 칸)는 그때도 녹색이었고, `usage.test.ts`의 새 칸은 그 결과(id 없는 행을 건너뛰어 앞선 세션을 고른다)를 적어 둘 뿐이라
  고치기 전에도 녹색이다. 수치는 `npm test`가 원천이다. 테스트가 정말 지키는지 변이로 쟀다 — 미리 정한 id를
  늘 돌려주기, timeout 약속만 남기기, spawn 전에 찾기, 상태만·빈 stdout만으로 안내 끄기, 앵커 없음·`m` 플래그, resume 분기 삭제, 새
  실행에도 프로필 변경 분기, 해결책을 늘 `off`로, env가 요청을 이기기(두 메시지), resume에 `off` 권하기, 사유를 코드 순서로 고르기,
  아무 `bwrap:` 줄이나 namespace로 읽기, 요청 값을 거르지 않기 등 — 모두 테스트 실패로 잡혔다(머지 전 검토 뒤의 것은 아래).
- 같은 페이로드를 새 번들로 다시 쳤다(win32·Linux 컨테이너). A53은 위 표의 v0.2.51 열, A55는 위 문단이 그 결과다(Linux의 네 경우
  포함). A54는 거부마다 새 메시지가 사유·출처를 위 "고친 것"대로 댔다 — 예: bubblewrap 없는 곳의 `GROK_SANDBOX=workspace` 새 실행은
  "bubblewrap(bwrap)을 실행하지 못했습니다(설치돼 있지 않습니다). 요청은 `sandbox`를 넘기지 않았고, 프로필은 서버 환경변수
  `GROK_SANDBOX`(값 "workspace")에서 왔습니다", `config.toml`이 준 프로필은 그 파일의 경로와 `[sandbox] profile`을, 이어간 세션의 저장된
  프로필은 "이어간 세션에 저장된 프로필입니다"와 새 세션을 말했다. 대조군(모델 요청까지 간 실행)은 그대로다.
- Grok 반증(정적, effort low, 주장 하나에 경로마다 분류) 두 묶음 — A53+A55(13경로)와 A54(25경로). 첫 판정이 코드에서 짚은 것:
  머리의 `bwrap:` 줄이면 무엇이든 namespace 거부라 했고, 두 사유의 말이 함께 있으면 코드 순서가 하나를 골랐으며, 두 메시지 함수가
  스스로는 이름을 거르지 않았다(실제 경로에서는 stderr 파싱과 요청 검증이 걸렀다) — 셋 다 고쳤다(위 A54 ②③). 나머지 지적 둘은 주장
  문구의 잘못이었다(로그인으로 멈춘 resume은 A68대로 안내가 없는 쪽이고, 프로필 변경 거부에서 받은 프로필의 출처는 저장된 프로필일 수
  없다). 고친 코드와 바로잡은 주장으로 둘 다 **CLAIM_HOLDS**, 반례 없음. 그 판정이 짚은 순서(재배치 줄 뒤의 샌드박스 거부)는 Linux에서
  다시 재 보니 나오지 않았다 — 거부 문장이 먼저였다(위 A55).
- 머지 전 검토(리뷰어 1명, diff만): BLOCKER 0, MAJOR 2 — ① 메시지의 해결책이 Linux에서 잰 경우(bubblewrap을 못 쓰는 곳의 `workspace`
  세션)에 통하지 않았고, 이 노트의 검증 문장 두 개가 사실보다 넓었다. 둘 다 고쳤다(위 A54 ①, 이 절). MINOR·NIT도 모두 반영했다 — resume의
  모르는 프로필에 내장 프로필을 권하지 않기, "설치돼 있지 않다"는 ENOENT일 때만, 변수를 지울 때는 Claude Code 재시작, A33의 넷째 거부
