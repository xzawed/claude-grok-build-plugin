# v0.2.56 — MCP 2.0(SDK v2): stdio 하나가 2025 계열과 2026-07-28 계열을 둘 다 받고, Node.js 20 하한을 밝힌다

> ⚠️ **Node.js 20 이상이 필요하다.** 플러그인의 MCP 서버는 PATH에서 찾히는 `node`로 돈다. Node 18이면 서버는 찾은 버전을
> 밝히는 한 줄(`grok-build MCP server did not start: Node.js 20 or newer is required (this is Node.js 18.20.8). Update
> Node.js, then restart Claude Code.`)을 남기고 exit 1로 끝나고, 그보다 오래된 Node는 그 전에 문법 오류로 멈출 수 있다(Node 16.0이
> 그렇다). 어느 쪽이든 grok 도구가 보이지 않는다 — 그러면 `node --version`부터 본다(`/grok:setup`도 그렇게 안내한다). 인증 hook은
> Node 18에서도 돈다(실측).

MCP 서버를 `@modelcontextprotocol/sdk` 1.x에서 MCP SDK v2(`@modelcontextprotocol/server` 2.4.0)로 옮겼다. 진입점 `serveStdio`가
연결마다 계열을 골라, 같은 stdio가 2025 계열(`initialize`)과 2026-07-28 계열(`server/discover`, 요청마다 `params._meta`)을 둘 다 받는다
— 도구 아홉 개의 등록과 핸들러는 그대로다. Claude Code 2.1.332는 이 번들에 2026-07-28 계열로 붙는다(아래 #8). 실제 동작을 처음부터
다시 쟀다(아래 매트릭스 13행 — 설계 §6.7). MCP 2.0 계획(`docs/plans/2026-11-28-mcp-v2-dual-protocol-plan.md`)의 2번 PR이다.

## 사용자에게 바뀌는 것

- **Node.js 20 하한**(위 경고). README·README.ko·`docs/08`에 처음으로 적었고, `/grok:setup`·`/grok:status`·`/grok:tour`와 첫 사용
  스킬은 grok 도구가 없을 때 Node 버전부터 보게 한다.
- **두 프로토콜 계열.** 어느 계열로 붙어도 도구 9개와 입력 스키마, 결과 모양(`isError`·`mode`·`billing`), 광고하는 capabilities,
  워커 안의 거절, 요청 한 줄의 10 MiB 한도가 같다(`docs/04` "두 프로토콜 계열").
- **SDK v1 번들과 달라진 것** — 두 계열 공통, 2026-11-28 v0.2.55 번들과 대조해 실측(`docs/04`가 원천, 테스트가 v2 쪽을 지킨다):
  - 없는 도구 이름은 JSON-RPC 오류 −32602(`Tool <이름> not found`)로 답한다. v1은 같은 문구를 `isError` 결과로 돌려줬다.
  - 입력 검증 실패는 지금처럼 `isError` 결과다. 문구는 앞의 `MCP error -32602: `가 빠지고, 경로가 있는 오류는 `<경로>: <메시지>`로
    (v1은 `<메시지> at <경로>`), 여럿이면 쉼표로(v1은 줄바꿈) 잇는다.
  - 입력 스키마의 `$schema`가 draft-07에서 2020-12로 바뀌었고, 도구마다 붙던 `execution: {"taskSupport": "forbidden"}`이 없다. 그
    밖의 필드는 같다.
  - `params` 없는 `tools/call`은 −32602다(v1은 −32603). 그 밖의 모양이 틀린 프레임은 v1과 같이 답 없이 버린다.
  - 클라이언트가 stdin을 닫으면 그때 아직 끝나지 않은 호출은 — 위임만이 아니라 `worktree`처럼 비동기로 답하는 호출 모두 — 답을 받지
    못한다(전송이 이미 닫혔다; v1은 답을 썼다). 서버는 하던 일을 마치고 끝난다 — 위임이면 grok이 끝날 때까지 살고, grok을 남기지 않으며,
    이력도 쓴다(v1과 같다). 요청을 한꺼번에 쓰는 클라이언트도 답을 다 읽을 때까지 stdin을 열어 둔다.
- **제3자 라이선스 고지.** 번들 옆에 `mcp-server/dist/THIRD_PARTY_NOTICES.md`가 있다 — SDK v2(Apache-2.0), zod, 그리고 SDK 배포 파일
  안에 묶여 온 ajv·ajv-formats·fast-uri·json-schema-traverse·fast-deep-equal·content-type. 묶여 온 패키지의 라이선스 전문은 원래 npm
  tarball에서 받아 레포에 두었다(`mcp-server/third-party/`).

## 바꾼 것

- 의존성: 실행 `@modelcontextprotocol/server` ^2.4.0·`zod` ^4.6.7, 개발 `@modelcontextprotocol/client` ^2.4.0; v1 SDK와 그것이 끌어온 hono
  등은 빠졌다(`npm ci` 63개 패키지, 취약점 0). `engines` `>=20.0.0`, `build.mjs`의 `target: 'node20'`.
- `src/index.ts` — `serveStdio(() => buildServer(…))`(`legacy: 'reject'` 없음). `src/node-guard.ts`는 첫 import라 SDK 코드보다 먼저 돈다.
- `build.mjs` — esbuild 메타파일과 `third-party/vendored.json`으로 고지 파일을 만든다(결정적; 다른 패키지 밑에 중첩된 패키지도 제
  이름으로 싣는다; 묶인 패키지가 매니페스트에 없거나, node_modules에서 온 코드가 읽을 수 없는 배치로 묶여 있으면 빌드가 그것을 대며
  멈춘다). CI의 dist 검사가 그 파일도 본다.
- `.claude/tools/rpc-era.mjs`(새로) — SDK 없이 원시 JSON-RPC 줄로 두 계열을 연다. 2026 계열을 받지 않는 번들(`server/discover`에 오류,
  2026-07-28이 없는 답, 또는 시간 안에 답 없음 — 명세의 stdio 탐침 규칙)은 "받지 않음"이다. `.claude/tools/accept-checks.mjs`(새로) —
  채점기의 격리와 검사를 옮겨 세션 여는 법을 바꿔 끼울 수 있게 했다; 칸마다 연 세션이 열리다 실패해도 연 것을 닫고 임시 폴더를 지운다.
  `accept-release.mjs`는 검사를 계열마다 돌린다(2025 16행 + 2026-07-28 13행): `--repo`와 이 레포가 선언한 버전의 설치본에서는 2026 계열이
  필수이고, `--version`이 다른 판을 가리키면 "받지 않음"을 알리기만 한다. `mcpcall.mjs`는 `--era legacy|modern`을 받는다.
- CI — 필수 체크 둘(Node 22)은 그대로 두고 Node 20 잡을 따로 더했다(`mcp-server (ubuntu-latest, node 20)`, 필수 아님).
- 문서 — `docs/04`(두 계열·달라진 것·한도의 근거), `docs/01`·`docs/03`·`docs/08`·`docs/11`·README 둘·`CLAUDE.md`·`CONTRIBUTING`·preflight
  스킬(번들에 드는 패키지가 v2에서 무엇인지, 개발 도구가 Node 20.19+를 원하는 것), 설계 §6.4·§6.7(예측과 다른 행을 실측으로).

## 하지 않은 것 · 한계

- Node 16.11–17은 재지 않았다(파싱은 되는 판이라 한 줄 안내가 나올 수 있다).
- Claude Code가 보낸 `subscriptions/listen`의 인자와 서버의 답은 기록하지 않았다 — 빈 인자로 보내면 v2는 −32602로 답한다; Claude Code의
  세션은 끝까지 정상이었다.
- 위임 중 stdin EOF 테스트의 가짜 grok은 win32에서 .NET Framework의 `csc`가 있어야 만든다(없으면 그 테스트를 건너뛴다) — Windows의
  spawn은 `grok.exe`만 찾는다.

## 검증

- **게이트** — `npm ci`(취약점 0) · `npm test` 52 파일 2734 통과·37 건너뜀 · `npm run typecheck` · `npm run build`(두 번들의 폴백 리터럴이
  0.2.56) · `node .claude/tools/accept-release.mjs --repo` 29/29(두 계열). 새 테스트는 고치기 전 코드에서 먼저 실패하는 것을 봤다.
- **리뷰와 반증**
  - 리뷰어 1명: BLOCKER·MAJOR 0, MINOR 6·NIT 10 — 모두 처리했다. 위 "달라진 것"의 검증 문구·스키마·`params` 없는 호출·stdin을 실측으로
    바로잡고 테스트로 고정했다; Node 16의 문법 오류를 밝혔다; 고지 생성기가 중첩 패키지와 읽을 수 없는 배치를 다루게 했다; 채점기가
    열리다 실패한 칸의 세션과 임시 폴더를 정리하고, discover에 답하지 않는 서버를 "받지 않음"으로 보고, 시간 초과에 도구 이름을 밝힌다.
  - 그 수정을 다시 본 확인: BLOCKER·MAJOR 0, NIT 8·메모 1 — 모두 처리했다. 여는 교환에 답하지 않거나 바로 끝나는 번들에서 `stdio-limit`의
    모든 칸이 실패하고, discover 도중 끝난 서버가 "받지 않음"이 아닌 실패로 남는 것을 테스트가 지키고, 스키마·모양이 틀린 프레임 검사가 2026
    계열에서도 돌고, `mcpcall`의 시간 초과 문구는 `tools/call`에서만 `timeout_ms`를 권한다.
  - 두 번째 재확인: BLOCKER·MAJOR 0, NIT 4 — 모두 처리했다. 원시 두 계열 테스트는 제 시간 안에 포기해 답하지 않는 번들에서도 임시 홈을
    남기지 않고(이 실행만의 TEMP로 잼: 고치기 전 4개, 뒤 0개), `/grok:setup`은 인증 모드 규칙을 정확히 말하고, `timeout_ms` 조언은 그것을
    받는 도구에만 맞게 쓴다.
  - 세 번째 재확인(그 diff만): 다섯 항목 모두 처리, NIT 1 — 같은 누수가 `rawLegacySession`을 쓰는 두 테스트에도 있었다(따로도 찾았다).
    고쳤다: 세션을 `try` 안에서 열고, 도우미가 답하지 않는 서버를 끄고, 그 테스트들은 도우미의 15 s보다 오래 기다린다(고치기 전 3개, 뒤 0개).
    SDK 클라이언트로 붙는 테스트는 실패 경로에서도 서버를 닫고 홈을 지운다 — SDK의 요청 제한(60 s)이 테스트 제한보다 긴 매달림만은 남는다.
  - 새 검사는 먼저 실패하는 것을 봤다 — 시작마다 한 줄 쓰는 변이 번들, v0.2.55 번들, 모든 프레임에 답하는 가짜 서버, 답하지 않거나 바로
    끝나는 가짜 서버, discover의 모든 실패를 "받지 않음"으로 바꾼 변이로. 고친 채점기로도 v0.2.55 캐시의 16행은 그대로다.
  - Grok 반증(검사 도구의 주장 — 2026 세션의 판정과 모든 요청의 결말, 두 계열의 격리와 `best_of_n`, 건너뛰거나 실패한 검사가 있으면 exit 0이
    아님): 14/14 HOLDS; 첫 수정 뒤의 도구로 다시 — discover 침묵, 시간 초과의 도구 이름, 열리다 실패한 칸의 정리를 더해 — 17/17 HOLDS. 두

- **변이 바닥** — Task 2.4의 변이 11개 모두 잡혔다(2026 요청의 봉투, −32601과 수정판 없는 discover, 끝난 서버, 계열의 오프닝, 채점기의
