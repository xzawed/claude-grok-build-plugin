# v0.2.47 — zod 4.6.7과 `grok_cli` 인자 상한: 호출 하나로 서버를 멈추던 검증 경로, 그리고 의존성 경보 9건

2026-10-26. Dependabot 경보 9건(38–46번)과 `npm audit`의 같은 권고를 처리했다. 그중 zod 권고는 배포 번들에 실제로 걸려 있었다 —
`grok_cli`의 `args`에 길이 상한이 없어서, 문자열이 아닌 원소를 많이 담은 호출 하나가 서버 메모리를 1GB 가까이 올리거나(원소 100만 개,
약 2MB) 응답을 수 분간 막았다(500만 개, 약 10MB — 아래 "재현"). **zod를 올리는 것만으로는 고쳐지지 않는다** — 고친 zod는 길이 상한이
있는 배열만 원소를 보기 전에 거절하므로, 상한을 함께 넣었다.

## 재현 (배포 번들, 쿼터 0 — 검증에서 거절돼 grok은 뜨지 않는다)

번들을 `.mcp.json`처럼 stdio로 띄우고, `args`에 숫자 n개를 담은 `tools/call grok_cli` 하나를 보냈다(서버의 최대 RSS는 프로세스
안에서 25ms마다 잰 값 — 동기 검증이 이벤트 루프를 붙잡는 동안은 재지 못한다). 시간과 RSS는 실행마다 조금 다르다.

| n (보낸 크기) | v0.2.46 | v0.2.47 |
|---|---|---|
| 1 | 6ms · 오류 응답 210B · 63MB | 4ms · 225B · 59MB |
| 100,000 (약 200KB) | 230ms · **4.9MB** · 158MB | 5ms · 218B · 59MB |
| 1,000,000 (약 2MB) | 6.0초 · **49.9MB** · **923MB** | 32ms · 218B · 73MB(RSS는 다시 잰 값) |
| 5,000,000 (약 10MB) | **300초 안에 응답 없음** | 231ms · 218B · 122MB |

SDK가 이슈를 하나도 빼지 않고 오류 문장에 쓰므로 응답도 함께 커졌다. 라이브러리 수준에서도 쟀다(실패만 하는 원소 100만 개):
3.25.76의 v3 API는 길이 상한이 있어도 이슈 1,000,001개(상한 이슈 포함)·힙 +276MB, 4.6.5는 +301MB, **4.6.7은 상한이 있을 때만
이슈 1개·2ms**이고 상한이 없으면 4.6.7도 1,000,000개다. 번들 수준에서도 같다 — zod 4.6.7에 상한만 뺀 번들은 원소 10만 개에
6,389,055바이트의 오류로 답했다. 그래서 업그레이드와 상한이 둘 다 필요하다.

## 고친 방법

- `zod` `^3.25.0` → `^4.6.7`. MCP SDK 1.32.1의 zod 범위가 `^3.25 || ^4.0`이라 SDK도 같은 4.6.7을 쓴다.
- `server.ts`: `import * as z from 'zod'` — v4 API다. `import { z } from 'zod'`로 두면 로캘 64개가 번들에 들어가 1,555,400바이트였다.
  이름공간 import는 쓰는 것만 남긴다 — 1,004,899바이트(v0.2.46은 938,563, 모두 LF 기준).
- `grok_cli`의 `args`: `.min(1)` → `.min(1).max(256)`(`GROK_CLI_MAX_ARGS`). grok 호출은 서브커맨드와 플래그 몇 개다.
- 테스트(`server-tools.test.ts`): 257개 거절(grok 미실행) · 256개 허용 · 문자열이 아닌 원소 10만 개가 오류 하나로 끝난다(문구 1,000자 미만).
- 락파일: 이 저장소의 npm 10.9.3에는 함정이 있어(`CLAUDE.md`) `npx npm@11`(11.19.1)로 `install --package-lock-only`와
  `update fast-uri body-parser ip-address --package-lock-only`를 돌렸다 — 커밋한 락파일에 같은 명령을 다시 돌려도 바뀌지 않는다.
  바뀐 패키지 항목 35개 중 하나는 이 패키지 자신의 버전(0.2.46 → 0.2.47)이고, 의존성 34개 중 런타임은 위 넷과 그것을 따라온
  `content-type`·`qs`이며 나머지는 vitest 묶음(개발용)이다. `libc` 블록 10개는 그대로다.

## 동작 변화

1. **잘못된 도구 인자의 오류 문구**가 zod v4의 것이 된다 — 예: `Expected string, received number at args[0]` →
   `Invalid input: expected string, received number at args[0]`.
2. **정수 칸 다섯**(`max_turns` 셋·`grok_build_usage`의 `limit`·`grok_cli`의 `max_chars`)이 `maximum: 9007199254740991`을 광고하고
   그보다 큰 수를 거절한다(v4의 `.int()`는 안전 정수다). `limit: 1e16`을 v0.2.46은 받았고 v0.2.47은 거절했다.
3. **정수가 아닌 숫자 칸 둘**(`grok_build_worktree`의 `max_age_days`, `best_of_n`)은 JSON의 `1e309`(파싱하면 무한대)를 거절한다.
   `max_age_days: 1e309`를 v0.2.46은 받았고(드라이런 prune이 `ok: true`) v0.2.47은 거절했다. `best_of_n`은 v0.2.46에서도 spawn 전에
   거절됐다(다른 층에서).
4. `grok_cli`의 `args`는 256개까지다.

`tools/list` 응답을 키 정렬한 JSON으로 전후 비교한 diff는 16줄이고, 2의 `maximum` 다섯과 4의 설명·`maxItems`뿐이다(1과 3은
스키마에 드러나지 않는다). 이 밖에 결과가 바뀐 입력은 찾지 못했다 — 테스트 2311개 통과, `accept-release` 16/16(Node 18.20.8로도).

## 남은 것

- MCP SDK가 들어오는 JSON-RPC 메시지를 검증하는 스키마에도 상한 없는 배열이 있을 수 있다 — 이 서버의 클라이언트는 로컬 Claude Code라
  재지 않았다. 고친 zod는 상한 없는 배열에는 효과가 없다(위 측정). SDK 1.32.1의 `maxToolInputElements` 옵션(도구 인자의 원소 수를
  검증 전에 센다)은 이 서버가 쓰지 않는다 — 더 넓은 방어로 켤지는 오너 판단이다.
- 번들에는 `zod/v3` 코드도 남는다 — SDK가 v3 스키마를 받기 위해 import한다. 이 서버의 스키마는 더 이상 v3를 쓰지 않는다.
