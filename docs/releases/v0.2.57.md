# v0.2.57 — 모델 API가 결제·사용량으로 거절한 턴(HTTP 402)을 알아보고 무엇인지 말한다 (`docs/09` §4 J, 2차 순서 3번)

2026-11-29.

구독의 Grok Build 사용량이 소진되면 xAI는 그 턴을 HTTP 402로 거절한다. 2026-11-04에 위임 넷이 그렇게 끝났다(grok 1.0.70, v0.2.51
번들). 그때 래퍼는 grok의 원문 "Internal error: { … API error (status 402 Payment Required): Grok Build usage balance exhausted … }"를
`grok_error`로 그대로 넘겼다. 다시 해도 같다는 말도, 종량제로 넘어가지 않았다는 말도 없었다(`docs/09` §4 J).

2026-11-05 오너가 "알아보고 안내"를 골랐다. 2026-11-29 남은 작업의 2차 순서에서 이 릴리스가 3번이 됐고, routing 스킬 한 줄이 함께 간다.

## 재현 (쿼터 0 — grok 1.0.92, win32, 실제 `~/.grok` 미접촉)

**조건.** 버릴 홈의 합성 세션을 썼고, grok의 API 주소 둘을 루프백으로 돌렸다(계약 §17).
- 루프백은 주 턴(`POST /v1/responses`)만 402로 답하고 나머지는 404로 답했다.
- 402 본문은 네 가지다:
  - `{"error":"Grok Build usage balance exhausted"}` — 2026-11-04에 xAI가 보낸 줄을 글자까지 재현한다;
  - 곁에 `code`를 둔 것;
  - `error`를 객체로 두고 그 안에 `type`을 둔 것;
  - JSON이 아닌 것.
- 대조는 모두 404로 답한 경우다.
- 다섯째 경우: 버릴 홈의 `config.toml`이 한 모델에 자체 키(가짜)를 준다. 그 설정에는 `billingCaveat`가 붙는다.

**번들 구동.** `.claude/tools/mcpcall.mjs`로 띄우되 env를 격리했다.
- 이 셸의 GROK_*·XAI_* 변수를 모두 뺐다.
- 홈 넷과 `CLAUDE_CONFIG_DIR`을 버릴 폴더로 돌렸다.
- api 모드의 키와 설정의 키는 가짜이고 루프백으로만 갔다.

v0.2.56 열은 그날 `main`의 번들, v0.2.57 열은 이 릴리스의 번들이다.

| 경우 | v0.2.56 | v0.2.57 |
|---|---|---|
| 위임·plan·verify, 구독, xAI의 말 | `grok_error`, `message`는 grok 원문 "Internal error: {…}" | `grok_error`, `paymentRequired: true`, "구독의 Grok Build 사용량이 소진됐습니다(HTTP 402 — "Grok Build usage balance exhausted"). 사용량이 돌아올 때까지 다시 시도해도 같습니다. env의 종량제 키(XAI_API_KEY·GROK_CODE_XAI_API_KEY)로 넘어가지 않았습니다 — 구독 모드는 그 둘을 grok에 넘기지 않습니다." |
| 위임, 구독, `code`나 중첩 `type`을 곁들인 본문 | 원문 | 같은 안내(따옴표 안은 `Payment Required: …`·`insufficient_quota: …`) |
| 위임, 구독, JSON이 아닌 본문 | 원문(grok의 말 "Request failed (HTTP 402).") | `paymentRequired: true`, "요청을 받은 모델 API가 HTTP 402(Payment Required)로 거절했습니다 — …" — 사용량 소진이라고 하지 않는다 |
| `grok_cli ["-p","Say ok."]`, 구독 | `error`, exit 1, `message` 없음 | `error`, exit 1, `paymentRequired: true`, 위와 같은 안내 |
| 위임·`grok_cli`, api 모드(가짜 키) | 원문 / `message` 없음 | `paymentRequired: true`, 구독 사용량 소진도 "종량제가 아니다"도 말하지 않는 안내 |
| 위임, 구독, 모델 자체 키를 둔 설정 | 원문과 `billingCaveat` | 첫 행의 안내 뒤에 "다만 이 응답의 billingCaveat대로 … 이 실행이 그 모델로 돌았을 때는 위의 "구독" 판단이 맞지 않을 수 있습니다 — 이 402는 그 키의 계정에서 왔을 수 있습니다."가 붙고, `billingCaveat`는 그대로 |
| 404 대조(위임·`grok_cli`) | 원문 / `message` 없음 | 같다 |

경우마다 모델 요청 셋이 402를 받았다(모두 `POST /v1/responses`). 위임 쪽의 `rawStderrTail`·`sessionId`와 `grok_cli`의 출력은 두
판이 같다. 하네스가 남긴 프로세스는 0이다.

## 고친 것

- **`delegate.ts`의 `paymentRequiredReason`.** grok 자신의 줄 `API error (status 402 …): <말>`이나 `"http_status": 402`를 찾아,
  그 줄이 실은 말을 돌려준다. 읽는 곳은 실패한 실행의 오류 봉투 문장과 stderr뿐이고, 성공한 실행의 요약은 읽지 않는다.
  - 정규식의 각 부분에 길이 상한을 둔다. 첫 판의 `[^)]*`는 ")"가 따라오지 않는 줄머리마다 입력 끝까지 다시 훑었다. 그래서
    제곱 시간이었다(머지 전 검토가 쟀다 — 44만 자에 4초, 크기가 두 배면 시간이 네 배).
  - 말은 이스케이프된 따옴표(`\"`)를 넘어 읽고, 각 이스케이프의 백슬래시를 뗀다(`\"`는 `"`, `\n`은 `n` — JSON 해독은 아니고, 영향은
    인용한 말에만 있다). 길이는 2000단위(글자 하나나 이스케이프 한 쌍)까지이고, 그보다 긴 말은 단위 경계에서 자른다.
  - 끝의 점·공백 다듬기는 루프로 한다. 끝에 고정한 정규식은 같은 이유로 제곱 시간이다.
- **`paymentRequiredMessage(mode, 말)`.**
  - 구독 모드: 그 말이 사용량 소진("usage balance exhausted")이면 "구독의 Grok Build 사용량이 소진됐습니다…"이다. 아니면 "요청을
    받은 모델 API가 HTTP 402로 거절했습니다…"이다.
  - 구독 모드의 끝 문장은 "env의 종량제 키(XAI_API_KEY·GROK_CODE_XAI_API_KEY)로 넘어가지 않았습니다 — 구독 모드는 그 둘을 grok에
    넘기지 않습니다."이다. 오너가 정한 "종량제로 넘어가지 않았다"를 `buildGrokEnv`가 보장하는 범위로 좁혔다. `config.toml`의 모델
    키는 grok이 구독 세션보다 먼저 쓰므로(계약 §10), 그 경우에는 넓은 문장이 참이 아니었다(머지 전 검토의 MAJOR).
  - api 모드: 거절 문장과, 그 요청이 쓴 자격증명(구독 세션이나 API 키)을 확인하라는 말만 한다. 어느 쪽을 썼는지 래퍼는 모르므로,
    구독 사용량이 소진됐다고도 종량제가 아니라고도 말하지 않는다.
- **서버(`runAndRecord`).** 같은 응답에 `billingCaveat`가 있으면 안내 끝에 `PAYMENT_CAVEAT_NOTE`를 붙인다. 설정의 모델 자체 키가
  쓰였다면 앞 문장의 "구독" 판단이 맞지 않을 수 있고, 그 402는 그 키의 계정에서 왔을 수 있다는 말이다. 원래 메시지는 손대지 않고
  그 뒤에 붙인다.
- **위임·plan·verify(`classifySpawnResult`).** 실패한 갈래 넷에서 402를 묻는다.
  - 오류 봉투 갈래: 봉투 문장과 stderr를 본다.
  - 봉투 없는 갈래: stderr를 본다.
  - 계획 텍스트가 빈 plan: stderr를 본다. Grok 반증이 찾은 빈틈이다.
  - 봉투는 읽혔지만 `stopReason`이 성공이 아닌 위임·verify: stderr만 본다.
  - 앞의 둘과 마지막 갈래에서는 인증 판단 바로 뒤에 묻는다. 빈 plan 갈래에는 원래 인증 판단이 없고, 그대로 두었다.
  - 뒤의 두 모양은 재지 않았다. 잰 402는 오류 봉투였고, 거기서는 grok 자신의 줄이 증거다.
  - 텍스트를 돌려준 plan은 설계대로 완료이니 그대로다.
  - `status`는 `grok_error` 그대로 두고, `paymentRequired: true`를 더하며, `message`를 안내로 바꾼다. `rawStderrTail`·`sessionId`는
    그대로다.
- **`grok_cli`.** 실패한 실행(상태 `error` — 0이 아닌 종료나 종료 코드 없음)의 stderr에서 같은 것을 찾으면 `paymentRequired`와 같은
  `message`를 싣는다. `grok_cli`의 응답에는 `billingCaveat`가 없으니 덧붙임도 없다.
- **배포 프롬프트.**
  - routing 스킬 "매 실행 뒤": `paymentRequired`면 `message`가 어느 쪽인지 말한다. 사용량·결제 문제가 풀렸다고 사용자가 말할 때까지
    다시 시도·resume·새 위임을 하지 않는다.
  - routing 스킬, 2차 순서 3번의 한 줄: 긴 기계적 작업은 `grok-worker`를 백그라운드로 돌릴 수 있다. 그 실행도 실제 위임이니
    돌아오면 diff를 검토한다. 도는 동안 같은 폴더에 두 번째 위임을 시작하지 않고, 이 세션에서도 그 폴더를 편집·커밋하지 않는다.
    `filesChanged`·`committed`가 실행 전후의 그 폴더를 비교하니 이 세션의 변경이 grok의 것으로 읽히기 때문이다. 아니면 `worktree: true`로
    돌린다.
  - `agents/grok-worker.md` 규칙 10과 `/grok:cli` 명령(`message`와 `paymentRequired`).
- **문서.**
  - `docs/04`(실패 결과, `grok_cli` 결과, 오류 문구), `docs/07` 8번, `examples/orchestrator-consumer.md`;
  - README 두 판의 문제 해결;
  - 계약 §17과 머리 표, `docs/09` §4 J, 계획;
  - `CLAUDE.md`의 Windows 줄에 셸 파이프 함정(아래 검증).

## 하지 않는 것

- **새 `status` 값을 만들지 않았다.** 소비자가 `status`로 갈라 둔 흐름이 그대로 돌도록 `grok_error`를 두고 `paymentRequired`를 더했다.
- **다시 보내지 않는다.** 래퍼는 402 뒤에 아무것도 다시 보내지 않고, API 키로 바꿔 보내지도 않는다.
- **사용량이 돌아왔는지 알리지 않는다.** 그 상태를 읽을 길이 없다(`grok_build_status`에는 넣지 않았다).
- **실세션의 다른 402 문구는 재지 않았다.** xAI가 다른 말을 보내면 안내는 "사용량 소진"이 아니라 "402로 거절"로 물러난다.
- **훅은 그대로다.** 402는 실행이 모델에 닿은 뒤에야 알 수 있다.
- **`grok_cli`에는 `billingCaveat`를 붙이지 않는다.** v0.2.33의 오너 범위가 status와 위임 응답이다
  (`docs/specs/2026-09-24-config-model-keys-billing-caveat.md`). 그래서 `grok_cli`의 402 안내에는 덧붙임이 없다.
  - 설정이 그 모델에 자체 키를 주었다면, 그 402는 그 키의 계정에서 왔을 수 있다. `grok_build_status`의 `billingCaveat`가 그 설정을
    알린다.
  - 끝 문장은 env의 두 키만 말하니 그 경우에도 참이다.

## 검증

- **새 테스트 37개.** 실측 원문은 `test/payment-402-fixtures.ts` 한 곳에 둔다. 이 테스트들을 `main`의 소스 넷에 돌려 재 보니
  31개가 실패했다. 바꾸지 않을 동작을 지키는 대조 6개는 그때도 통과한다: 404 둘, 성공한 요약, 인증 먼저, exit 0, caveat가 없거나
  402가 아닌 실패.
- **변이 35개, 모두 잡힌다.** 변이마다 실패한 테스트 수가 다르다.
  - 하네스는 셸 없이 vitest를 띄운다. 변이를 넣기 전에 변이 없는 기준선이 통과하는지(37)와, "못 찾는" 양성 대조가 실패하는지(21)를
    먼저 본다.
  - 첫 하네스는 이 확인이 없어 무효였다. win32의 `shell: true`가 인자 `-t 402|paymentRequiredReason`의 `|`를 cmd.exe 파이프로 읽어,
    변이 없이도 실패했다. 머지 전 검토가 찾았고, 그 검토가 셸 없이 다시 잰 첫 12개는 실제로 잡혔다.
  - 그 검토가 찾은 생존자 열도 테스트로 고정했다: 봉투만·stderr만 읽기, 경계 둘, 이스케이프, 종료 코드 없음, api 문장, 세션 핸들,
    유보 문장, 샌드박스보다 먼저.
  - 수정분 재확인이 찾은 생존자 일곱도 고정했다: 덧붙임 문구 둘(비우기, "왔습니다"로 단정), 대소문자 무관 비교, 2000단위 상한, 끝
    다듬기 둘(한 글자만, 점만), 이스케이프된 `n`.
  - 수치는 `npm test`가 원천이다.
- **다시 잰 것.** 위 표의 v0.2.57 열 — 같은 하네스, 본문 넷과 설정 키 경우, 이 릴리스의 최종 번들. 덧붙임 문구를 고친 뒤 열다섯
  경우를 모두 다시 쟀다.
  - 402 경우 열둘은 새 답을 내고, 404 대조 둘은 같은 답을 낸다.
  - 키 없는 api 위임 하나는 전처럼 서버의 키 확인에서 멈춘다. grok에 닿지 않는다.
  - 앞 측정에도 있던 열두 경우 가운데 달라진 것은 설정 키 경우의 문구뿐이다.
  - 남은 프로세스는 0이다.
