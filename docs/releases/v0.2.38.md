# v0.2.38 — fast-uri 3.1.8: 번들 안에 있던 권고 하나

2026-10-04. Dependabot 경보 하나(GHSA-hrr3-gc8f-f4qj, moderate)를 처리했다. 코드 변경은 없고 락파일·번들·버전이 바뀐다. 절차
문서도 함께 고쳤다(아래 "절차 문서"). 사용자에게 보이는 동작 변화는 없다.

## 무엇이 사용자에게 도달했는가

```
grep -c "node_modules/fast-uri" dist/index.js   →  6   ← 인라인됨
grep -c "node_modules/fast-uri" dist/hook.js    →  0
```

`fast-uri`는 MCP SDK(1.29.0)가 쓰는 `ajv`(8.20.0)를 거쳐 들어오고, esbuild는 런타임 의존성을 번들에 인라인한다. 그래서
설치한 사용자가 실행하는 `dist/index.js`에 3.1.7이 들어 있었다.

권고의 결함은 이렇다. scheme-relative 참조(`//host`)에서 퍼센트 인코딩된 대문자 옥텟(`%41`)이 호스트의 대소문자 정규화를
비켜 간다. 그러면 대소문자를 가리는 호스트 허용·거부 판단을 우회할 수 있다(CWE-178). 3.1.8에서 고쳐졌다.

## 이 서버에서 fast-uri가 하는 일

fast-uri의 공개 함수에 계수기를 감싸고 SDK의 `Server`를 만들어 쟀다.

- 서버가 시작할 때 SDK가 Ajv를 만들고, Ajv는 내장 메타스키마 id `http://json-schema.org/draft-07/schema` 하나에 `parse`와
  `serialize`를 한 번씩 부른다.
- 내장 메타스키마가 아닌 스키마가 fast-uri에 닿는 길은 SDK의 `getValidator`뿐이다. 그것을 부르는 곳은 폼
  elicitation(`elicitInput`) 하나인데, 컴파일되는 스키마는 서버 코드가 넘긴 `requestedSchema`이고 클라이언트 응답은 검증에만
  쓰인다(번들의 ajv-formats `uri` 형식은 정규식이라 fast-uri를 부르지 않는다). 이 서버의 `src/`는 `elicitInput`을 쓰지 않는다.

그래서 이 서버에는 바깥에서 준 URI로 호스트를 판단하는 경로가 없다. 다만 "fast-uri에 닿지 않는다"는 틀린 말이다 — 시작 때
돈다. 취약한 코드가 배포물에 있으니 고친다. 같은 주장을 Grok에게 코드 발췌째 주고 반증하게 했고, 판정은 `CLAIM_HOLDS`였다.
Grok이 판단을 유보한 것은 하나다: `getValidator`가 돌려준 검증기가 클라이언트 값을 검사할 때(검증 시점의 `format: "uri"`·
`$ref`). 이것도 이 서버가 부르지 않는 elicitation 경로 안에 있다.

## 번들 변경이 벤더 영역에 한정되는지

`npm ci` 뒤 fast-uri는 3.1.8이고, SDK 1.29.0과 ajv 8.20.0은 그대로다. 다시 빌드한 번들의 diff는 hunk 셋이다.

| 파일 | 위치 | 내용 |
|---|---|---|
| `dist/index.js` | `require_fast_uri` 안 | 3.1.8의 변경 — 호스트를 퍼센트 디코딩한 뒤 소문자로 접는다 |
| `dist/index.js` | `getServerVersion` | `"0.2.37"` → `"0.2.38"` |
| `dist/hook.js` | `getServerVersion` | 같음(이 번들은 fast-uri를 포함하지 않는다) |

패치가 들어갔는지는 락파일이 아니라 산출물로 확인했다. 3.1.8에만 있는 `normalizePercentEncoding(host.toLowerCase())`가 새
`dist/index.js`에 한 번 있고, 이전 번들에는 없다(고정 문자열로 셌다).

npm에서 받은 3.1.7과 3.1.8의 `index.js` diff(`lib/`는 같다)와 번들 diff를 Grok에게 그대로 주고 hunk마다 분류하게 했다. 판정은
`VENDOR_AND_VERSION_ONLY`였다 — vendor hunk의 모든 줄은 upstream 변경과 esbuild의 변환(주석 제거, `undefined` → `void 0`,
따옴표·세미콜론, 불필요한 괄호 제거)으로, 나머지 두 hunk는 버전 문자열로 설명된다.

## 버전

`v0.2.37`은 태그와 릴리스가 이미 나갔고 이번에 번들이 바뀌므로 0.2.38로 범프했다. 캐시는 버전 키다 — 같은 번호로 다른 번들을
내보내지 않는다.

## 절차 문서

`CONTRIBUTING.md` "Dependabot"은 Dependabot 브랜치에서 재빌드만 하라고 적고 있었다. 그대로 따르면 바뀐 번들이 옛 버전 번호로
`main`에 올라간다(PR #49 뒤 #51이 v0.2.6으로 낸 선례). `.claude/skills/maintainer-preflight`의 "Dependency PRs"도 범프 없이 PR
브랜치에서 재빌드해 push하는 절차만 적었는데, 바로 아래 절("If the rebuild changed `dist/` for end users", #51이 더했다)은
범프·릴리스 노트를 요구해 둘이 어긋나 있었다. 이제 dist를 바꾸는
재빌드는 릴리스로 다룬다 — 자기 브랜치에서 범프와 함께 한다. 이 릴리스가 그 절차로 나갔다: Dependabot의 락파일 변경(#157)을
가져와 범프했다. 같은 번호로 다른 번들이 나가는 것은 자동 감시가 잡지 못한다는 것도 `CLAUDE.md`·`CONTRIBUTING.md`에 적었다.
