# v0.2.26 — Grok 4.7이 도착했고, 우리는 17개 릴리스 동안 보지 못하고 있었다

2026-09-22. **오너 목표: Grok 4.7 출시를 근거 기반으로 받아, 전체 코드·전체 문서에서 무엇이
깨졌고 무엇이 가능해졌는지 Grok과 함께 확인한다.**

가장 먼저 나온 사실이 방향을 정했다. xAI는 2026-09-21에 Grok 4.7을 냈지만(2.1T 파라미터,
Terminal-Bench 4.0 20.3 → 38.0), **이 레포에 실제로 작용한 변화는 CLI가 `1.0.13` → `1.0.30`으로
간 것**이다. 계약 SSOT는 17개 패치 전에 멈춰 있었고, 그 사이 grok은 서브커맨드를 둘 더 달았고
plan 모드의 동작을 뒤집었다. **아무도 몰랐다.**

방법: 실측 프로브 9회 + 배포 번들 호출 8회, 코드·문서·테스트 11축 병렬 감사(에이전트 124개,
실패 0), 후보 112건 중 **101건이 적대적 검증을 통과**(9건 기각, 2건 판단 보류),
Grok 교차검증 4회. 유닛 수치는 `npm test`로 직접 낼 것.

## 1. 닫은 결함 5건 (A28~A32) — 전부 배포 번들에서 재현 후 재측정

| | before (실측) | after (같은 페이로드) |
|---|---|---|
| **A32** 자동 커밋 | grok이 커밋함, HEAD `4f91a63`→`7b862d3`, `filesChanged: []` | 커밋 없음, `committed: false`, `filesChanged: ["f.txt"]` |
| **A29** `cursor-worker` | `["--minimal","cursor-worker","--help"]` **spawn**, exit 0 | **blocked** (정확한 사유) |
| **A28** `-cp` 이력 누락 | history 851 → 851 (delta **0**) | delta **1**, `promptPreview` 기록 |
| **A30** `grok usage` | blocked ("모르는 서브커맨드") | ok — 실토큰·비용·`grok-4.7-build` 반환 |
| **A31** `shell:true` 금지 | 일반 서식을 **못 잡는 죽은 정규식** | 잡음 + **양성 대조**로 재발 시 실패 |

### A32가 가장 나빴던 이유 — 막지도, 보이지도 않았다

`--always-approve`는 붙는데 커밋을 막는 문장은 `VERIFY_PROMPT_SUFFIX` 안에만 있었고, 그것을
켜는 `check`는 `grok_build_delegate`의 `.strict()` 스키마에 **필드조차 없어** 어떤 호출자도
도달할 수 없었다. 그리고 커밋이 일어나는 순간 편집이 porcelain에서 사라지므로 `filesChanged`가
**빈 배열**이 된다 — 라우팅 정책 전체가 기대는 diff 검토 게이트가 조용히 우회된다.

막는 쪽은 프롬프트 접미사를 택했다. 1.0.30의 `--rules`도 실측으로 동작했지만(같은 프롬프트에서
grok이 편집만 하고 커밋을 거부), **1.0.13 스냅샷에 없는 플래그를 무조건 붙이면 구버전 사용자의
모든 위임이 exit 2**가 된다. 접미사는 버전을 깨뜨릴 수 없다.

지시는 설득이므로 **탐지**를 같이 넣었다 — `planWroteFiles`와 같은 패턴으로, git HEAD를 실행
전후로 읽어 `committed`로 보고한다.

### A29 — 두 집합은 반대 방향으로 실패한다

`cursor-worker`는 allowlist로만 막히고 있었는데, 그 규칙은 낯선 플래그로 파스가 불확실해지면
**설계상 물러난다**(스냅샷이 낡았을 때 정상 커맨드를 오차단하지 않기 위해). denylist는 모든 위치
인자를 훑어 같은 조건에서도 막는다 — 실측으로 `["--minimal","leader","list"]`는 차단됐다.

그런데 소스 주석은 유지보수자를 **틀린 집합**으로 안내하고 있었다("When grok adds a subcommand,
add it here"). 그 문장을 고쳤고, 드리프트 감지기의 실패 메시지에도 같은 규칙을 실었다.

## 2. Grok 4.7이 실제로 요구한 것 (B1~B3) — 긴 실행을 견디기

4.7의 판매 포인트는 **오래 도는 것**인데, 이 래퍼의 유일한 한계는 180초 벽시계 + SIGKILL이었다.
감사 11축 중 **8축이 독립적으로** 같은 곳을 가리켰다.

- **B1 — 세션 id를 실행 *전에* 발급한다.** 전에는 파싱에 성공해야 id가 생겼으므로 **가장 비싼
  런이 유일하게 재개 불가**였다. 오너 실제 이력 845행 재집계: **timeout 82행, sessionId 보유 0건.**
  실측으로 안전을 먼저 확인했다 — 1.0.30은 호출자가 만든 v4 UUID를 수용하고(grok 자신의 id는 v7
  모양이다), 25초에 SIGKILL된 런도 그 id로 **온전한 세션을 남긴다**.
  **끝까지 닫았다:** 20초 타임아웃 → `sessionId` 반환 → 같은 id로 **재개 성공**, grok이 맥락을
  기억했다("A detailed design document on distributed consensus").
- **B2 — `--max-turns`.** 시간이 아니라 **작업량** 상한. 실측: `--max-turns 1`이 3파일 과제를
  첫 파일에서 끊고 exit 1 + `cancelled` + stderr `max turns reached`, 부분 편집 보존.
- **B3 — 봉투가 이미 주던 것을 버리지 않는다.** `parseGrokResult`는 43줄이었고 `text`/`stopReason`/
  `sessionId`만 읽었다. 이제 `tokens`·`turns`·`model`을 싣고 이력에 `model`·`totalTokens`를 남긴다.
  핵심은 **위임이 모델 익명이었다**는 것이다 — 2026-09-21에 기본 모델이 4.6→4.7로 조용히 바뀌었는데
  기존 어떤 행도 어느 모델로 돌았는지 말하지 못한다.

### USD는 싣지 않는다

Grok에게 **실제 봉투를 주고** 판정시킨 결과가 근거다: 구독 로그인에서 `total_cost_usd`는 청구된
돈이 아니고, 봉투에는 어느 과금인지 말하는 필드가 없다. 숫자가 필요하면 `grok usage <SESSION_ID>`가
준다(A30이 열었다). 같은 판정이 합산 함정 셋을 짚었고 전부 직접 재검증했다:
`input`과 `cacheRead`는 **분리된 값**(합이 `grok usage`의 `inputTokens`), `total`은 grok의 것,
`reasoning`은 `output`의 **부분집합**이라 더하면 안 된다.

## 3. 이번 작업의 진짜 산출물 — `npm run probe:contract`

결함 목록보다 중요한 것은 **왜 손으로 찾아야 했는가**다. CI에 실제 grok을 건드리는 잡이 하나도
없고, 유닛 테스트는 전부 DI 목이라 **어떤 grok에서도 녹색**이다.

`scripts/probe-contract-drift.mjs`가 `--version`·`--help`·`models`를 커밋된 스냅샷과 대조한다.
**모델 호출이 없어 쿼터를 쓰지 않는다.** `--strict`면 드리프트에 exit 1.

**이 장치가 오늘의 드리프트를 잡았을지 시험했다.** 스냅샷을 1.0.13 시점으로 되돌리자 정확히
이것들이 떴다 — 서브커맨드 `cursor-worker`·`usage`, 모델 `grok-4.7`·`grok-4.7-build-fast`,
플래그 `--max-turns`·`--prompt-file`·`--rules`, 버전 이동.

## 4. 계약 변경: plan 모드가 **세 번째로** 뒤집혔다

1.0.3 막음 → 1.0.13 **안 막음** → 1.0.30 막음. 전부 실측이다. 1.0.30에서는 파일이 생기지 않고
`stopReason: cancelled`로 끝난다.

**`planWroteFiles`는 그대로 둔다.** 이 역사가 말하는 것은 "plan이 안전해졌다"가 아니라 **이 동작이
릴리스마다 뒤집힌다**는 것이다. 탐지는 이번 실행의 사실이라 버전과 무관하게 유효하다.

같은 이유로 사용자 대상 텍스트에서 **버전 단정을 걷어냈다** — `commands/plan.md`,
`grok_build_plan` 툴 설명, 코드 안의 경고 문구가 전부 "grok 1.0.13은 …한다"고 말하고 있었고
1.0.30에서 거짓이 됐다. 그런 문장은 **자기가 낡는 것을 스스로 알리지 못한다.**

## 5. 하지 않은 것 — 기각된 제안들

- **모델 목록에 4.7 추가 → 불필요.** `delegate.ts`는 allowlist가 아니라 은퇴 별칭 denylist다.
  배포 번들에 `model: "grok-4.7-build-fast"`를 넣어 **이미 completed** 확인했다.
- **라우팅 재튜닝 → 기각.** Grok에게 반증시켰다: `routeTask`는 모델 id·버전·점수를 하나도 읽지
  않고 결과의 심각도만 잰다. Grok의 지적이 정확했다 — *"4.7이 스스로 검토한다는 것은
  `finalReview`를 Claude에 두는 근거를 약화시키는 게 아니라 강화한다."*
- **`--json-schema` 채택 → 기각**(독립 근거 2개). 레포가 이미 문서로 기각했고
  (`docs/specs/2026-08-14-grok-1.0-compat-design.md` — 편집 품질을 해칠 수 있음), 그 플래그는
  1.0.30 신규도 아니다(이미 1.0.5/1.0.13에 있었다).
- **`disable_api_key_auth`를 2차 방어선으로 → 기각.** `grok setup` 확인 결과 **팀 배포키 전용**이라
  이 플러그인의 대상인 개인 구독자는 쓸 수 없다.
- **`--prompt-file` 전환 → `ADOPT_WITH_CARE`, 이번엔 미채택.** Windows 32767자 명령줄 한계 해소는
  실재하지만, Grok이 셋을 짚었다: 임시 파일이 `--sandbox` 프로필 밖이면 읽히지 않을 수 있고,
  쓰기 실패가 `spawnError` 구조화 분기 **밖**에서 나며, **프롬프트 전문이 담긴 잔존 파일이
  시크릿 노출면**이다(절대 원칙 #4).

## 6. Grok이 내 주장을 죽인 곳 — 그리고 하네스가 틀린 곳

**Grok이 옳았다.** `-cp`를 "인증 게이트도 통과한다"고 보고했는데, Grok이 `mayRunTurn`의 **두 번째
경로**가 `BOOLEAN_SHORTS`를 아예 보지 않는다고 반증했다. 배포된 `dist/hook.js`에 빈 `GROK_HOME`으로
확인: `-cp x` → **deny**, `-p x`와 동일. 내 근거는 "인증된 상태에서 실행이 성공했다"였는데 그건
게이트 미작동의 증거가 아니다. **A28은 보안 결함이 아니라 이력 누락이다.**

Grok은 커밋 탐지기의 한계도 짚었다 — 다른 ref로의 커밋, 커밋 후 reset 복귀, 중첩 저장소,
`git stash`. 넓히지 않고 **코드에 명시**했다. 위협 모델은 회피가 아니라 과욕이다.

**하네스가 틀린 횟수: 2.** ① 동시 실행 중인 감사 에이전트들이 공용 스크래치패드에 쓴 `build.mjs`가
`filesChanged`에 섞인 것을 결함으로 의심했다 — 래퍼는 정확했다. ② `--always-approve` 필요성
재측정은 사용자 `~/.grok/config.toml`의 `permission_mode = "always-approve"`가 오염시켜
**이 머신에서는 측정 불가**다. 계약 §6에 그 함정을 적어뒀다.

그리고 **heredoc 역슬래시 함정을 이 세션에서 두 번 더 밟았다** — CLAUDE.md가 경고한 그대로이고,
A31이 고친 죽은 정규식과 **같은 원인**이다. 편집은 편집 도구로 한다.

## 7. §5 리뷰 조리법에 추가된 것 — `--json-schema`는 조용히 지어낸다

같은 질문·같은 파일로 대조 실험을 했다.

| 리뷰 | 형식 | 턴 | 결과 |
|---|---|---|---|
| A | `--json-schema` | 2 | 정확 (파일 읽음) |
| B | `--json-schema` | **1** | **환각** — 없는 주석 인용, 숫자 `0.0227` → `0.304425` 날조 |
| C | `verdict.md` (레포 조리법) | 3 | 정확 — 실제 값 인용 |

**`--json-schema`는 도구 사용 턴 없이 스키마를 만족시킬 수 있어, 형식이 완벽하고 전부 날조된 답을
만든다.** "verdict.md에 쓰고 멈춰라"는 최소 한 번의 도구 턴을 강제하므로 이 실패 모드가 없다.
조리법의 원래 "왜"는 2026-09-12에 반증됐지만, **이 새 근거로 조리법 자체는 유지한다.**

조리법을 어겼을 때 무슨 일이 나는지도 다시 확인했다: 4개 하위질문 + argv 나열을 준 리뷰가
**300초 타임아웃 2연속**으로 죽었고, 한 주장·파일 하나로 줄이자 **정상 완료**했다.
*"한 번에 한 가지 주장만"*, *"명령 모양을 추론 대상으로 주지 말 것"* 은 장식이 아니다.
