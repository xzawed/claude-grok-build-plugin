## 이 항목들을 어떻게 재현하나

**절차의 원천은 루트 `CLAUDE.md`의 "작업 수행 방법"이다** — 여기 있는 건 그 1번 단계를 이 큐에
맞게 적은 것뿐이다. 큐는 언젠가 비지만 절차는 남아야 하므로, 방법을 이 문서로 옮겨 적지 말 것.

배포 번들을 `.mcp.json`이 하는 것과 **똑같이** stdio로 띄워 채점한다 — 세션의 MCP 프로세스는
설치 시점 버전에 고정돼 있어 그걸로 채점하면 엉뚱한 산출물을 채점하게 된다.

```bash
node .claude/tools/mcpcall.mjs list
node .claude/tools/mcpcall.mjs call grok_auth_check '{}'      # serverVersion 으로 대상 확인
GROK_BUILD_AUTH_MODE=api node .claude/tools/mcpcall.mjs call grok_auth_check '{}'
```

FAIL 4. FAIL 4건은 v0.2.19로 나갔다(`docs/releases/v0.2.19.md`).

⚠️ **이 문서는 요약이다.** 항목별 원본 페이로드와 재실행 근거는 감사 세션의 subagent 트랜스크립트에
있었고 그건 레포 밖·세션 로컬이라 사라진다. 어떤 항목을 의심하면 **다시 재는 것이 정답**이다 —

- **A68 — grok 1.0.52에서 거절된 세션은 `auth_error`가 아니라 `timeout`으로 끝나고, 브라우저 로그인 창을 남긴다.** 서버가 세션
  토큰을 거절하면 1.0.52는 `~/.grok/auth.json`을 지우고 `auth: inline auth flow`(headless:false)를 남긴 뒤 기본 브라우저로
  `auth.x.ai/oauth2/authorize`를 열고 말없이 기다린다 — 턴은 써 두고 모델 요청은 보내지 않는다(계약 §1 ③). 1.0.50은 2.6초 만에
  exit 1이었고 래퍼는 그것을 `auth_error`로 알렸다(`AUTH_ERROR_SIGNALS`). 1.0.52에서는 위임이 `timeout_ms`까지 붙잡혀 `timeout`이 되고
  (A59 안내도 붙는다) 열린 창이 남으며, `npm run probe:contract`의 worker-marker 단계도 같은 데서 멈추고 돌릴 때마다 창을 연다.
  timeout을 인증 실패로 다시 가르는 `DEVICE_AUTH_SIGNALS`는 device-flow의 표시만 본다.
  **2026-10-17, grok 1.0.62:** 이번에는 같은 단계가 STOP(`sessionAccepted`)을 냈다 — grok의 종료 코드가 0이었고
  (상한의 SIGKILL이었다면 null이다) 파이프가 닫힌 것은 125.6초였다(상한 120초). 같은 출력의 `reached`는 true(표식이 플러그인 MCP 서버에 닿았다),
  `blind`·`authRejected`는 false였다. 쿼터 0으로 본 곳에는 격리를 뚫은 자격증명이 없었다(실제 `~/.grok`에 그 세션이 없고, Windows
  자격 증명 관리자에 grok 항목이 없다). 거절된 세션이 이제 exit 0으로 끝나는지는 재지 않았다 — 그렇다면 이 STOP은 종료 코드만 보는
  판정(`worker-marker-probe.mjs`의 `exitCode === 0`)이 낸 것이다. 위임의 상태는 종료 코드가 아니라 봉투의 오류 여부와
  `stopReason`이 정한다(`delegate.ts`의 `classifySpawnResult`). 원인을 알기 전엔 그 프로브를 다시 돌리지 않는다(오너). 같은
  격리(`scripts/synthetic-auth.mjs`)로 grok을 띄우는 측정도 원인을 알 때까지 함께 보류한다 — `probe:expired`(합성 세션 — 모델
  요청이 거절되는 경로)·`probe:home`(합성 세션 — `grok models`)·`probe:unauth`(세션 없이 `-p`)는 오너가 2026-10-18 권장안으로
  정했고, 같은 하네스로 짠 계획의 A53–A55 측정(`docs/plans/2026-09-30-handoff-plan.md` — 쿼터 0 재현, 코드 전에 잴 것, A53 함정의 B1 전제 확인)과 아래 A60의
  가짜 모델 측정은 #181 검토가 같은 이유로 더했다. 이 보류를 풀 측정 — STOP의 원인을 찾는 것과 아래 최소 수정의 첫 측정 — 은 그
  예외다: 오너가 A68 착수를 승인하면 그 승인 아래 하고, `probe:contract` 자체는 원인이 밝혀진 뒤에 돌린다(#181 2차 검토가 보류가
  스스로를 풀 길을 막는다고 짚었다).
  **최소 수정:** 먼저 쿼터 0으로 창을 막는 grok 쪽 스위치를 잰다 — 숨은 불리언 `--oauth`·`--force-login`·`--no-ask-user`(이 경로에서는
  재지 않았다)와 env `CI`·`BROWSER`·`DISPLAY`. 막는 것이 없으면 stderr에서만(stdout은 아니다) `auth: inline auth flow`와
  `auth.x.ai/oauth2/authorize`를 device-flow 표시처럼 보고, 보이는 즉시 grok을 멈춰 `auth_error`로 알린다. worker-marker 단계도 같게
  묶어 창을 열지 못하게 한다. 착수는 오너 승인 후.

> **B4(`GROK_SANDBOX`가 요청하지 않은 위임을 조용히 제약하는가)는 2026-09-24에 닫혔다** — Linux에서

> **B3 — 콘솔의 0은 닫힘이 아니다. 재는 순서가 있다 (2026-09-12).** 종량제 콘솔을 보고 0이라는
> 것만으로는 아무것도 증명되지 않는다 — 집계 지연, 화면에 안 뜨는 SKU, 다른 키로의 지출이 모두
> 똑같은 조용한 0을 만든다. 그래서 **먼저 계측기를 검증한다**: `npm run probe:metered`가 의도적으로

> 그것을 찾는다. 키는 에코 끈 프롬프트로 받고 어디에도 기록하지 않는다 — 셸 변수 대입은 금지다
> (PSReadLine이 평문 이력에 남긴다, 실측). 그 프로브의 기록된 결함은 A72–A75다 — 프롬프트로 준 키도

> ⚠️ **콘솔을 브라우저 자동화로 읽으려 하지 말 것 (2026-09-13 실측).** `console.x.ai`는 Cloudflare
> 뒤에 있고, **MCP가 띄우는 브라우저**(Puppeteer/Playwright 방식 — 별도 프로필 + 자동화 플래그)는
> **하드 블록**된다("Sorry, you have been blocked", Ray ID `a3a4764f2da03290`). 첫 페이지는 열렸고
> 두 번째 이동에서 막힌 뒤에는 첫 페이지도 막혔다. **IP 차단이 아니다** — 같은 머신에서 `api.x.ai`는
> 그대로 400 인증 거부를 돌려준다. 즉 브라우저 지문 차단이고, **Playwright도 같은 벽이다**(같은 표식을
> 더 뚜렷하게 단다). ⚠️ **우회는 범위 밖이다** — 지문 위장·챌린지 해결을 시도하지 않았고, 하지 말 것.
