# v0.2.14 — 아무도 열지 않았던 곳

2026-09-03. 1차 감사가 "이 영역은 **아무도 보지 않았다**"고 남긴 목록을 같은 방식으로 다시
감사했다 — 6개 영역, 18건 발견, 항목마다 독립 2렌즈(재현 / 반증), 중요한 건 Grok 3회차.

**결과는 얇았고, 그게 정직한 결과다.** 10건이 교차검증에 들어가 **2건만 양쪽을 통과**했다.
6건은 실측 또는 문서 근거로 반증됐고, 1건은 자기 재현 명령이 `git ls-remote`의 사전식 정렬을
오독한 것이었다. 심각한 결함을 막 고친 저장소는 이런 모양이어야 한다.

## 문서가 약속한 것과 코드가 한 것이 달랐다 (실측)

`CLAUDE.md` 절대 원칙 #4는 *"credential을 로깅하거나 파일에 쓰지 않는다"*, 로깅 설계 스펙은
*"No credentials, ever."* 라고 적혀 있었다. 실제로는 **xAI 빌링 키 두 개만** 마스킹했다.

임시 히스토리 파일에 넣어 측정한 결과:

| 붙여넣은 형태 | 디스크에 기록된 것 | `grok_build_usage` 응답에 재등장? |
|---|---|---|
| `XAI_API_KEY=xai-…` | `XAI_API_KEY=<redacted>` | 아니오 |
| `Authorization: Bearer eyJ…` | **원문 그대로** | **예** |
| `AWS_SECRET_ACCESS_KEY=wJal…` | **원문 그대로** | **예** |
| `ghp_…` | **원문 그대로** | **예** |
| `password: hunter2…` | **원문 그대로** | **예** (`grok_build_status`의 최신 세션에도) |

`redactSecrets`가 이제 xAI · AWS(키/세션 토큰/AKIA) · GitHub(classic·fine-grained) ·
Slack · OpenAI/Anthropic 형태 · JWT · `Bearer` 헤더 · PEM 개인키 블록 · 그리고
`password`/`secret`/`client_secret`/`access_token`/`api_key` 류 **대입문**을 가린다.
**첫 구현은 과잉교정이었고, Grok이 그걸 잡았다.** 현실적인 프롬프트 45개를 돌려 **19개가
훼손**되는 것을 보여줬다 — `api_key: required`, `DATABASE_URL: string`,
`password: unchanged`, `Bearer authentication-middleware`, GitHub Actions의 `secrets.*`
표현식까지. 이름 옆에 8자 이상 값이 있으면 무조건 시크릿으로 본 탓이다. **이력이 일반 작업
설명을 먹어치우면 이력이 없는 것만 못하다.** 내 산문 코퍼스가 6개뿐이라 못 잡았다.

그래서 **값이 실제로 시크릿처럼 생겼을 때만** 가리도록 두 단으로 나눴다. `XAI_API_KEY`처럼
**명시된 크레덴셜 변수명**은 이름 자체가 증거이므로 값이 짧아도 가리되 타입/스펙
단어(`string`·`required`·`optional`…)는 통과시키고, `password` 같은 **일반 명사**는 값이 12자
이상이면서 영숫자가 섞여 있어야(또는 32자 이상) 가린다. `Bearer`와 `sk-`/`xai-` 접두사도 같은
값 검사를 지나므로 *"Bearer authentication-middleware"* 는 문장으로 남는다.

구분자와 따옴표도 보존한다 — `:`를 `=`로 바꾸고 따옴표를 먹던 탓에 마스킹된 JSON이 JSON이
아니게 됐었다. **Grok이 찾은 19개 전부**를 25개 산문 회귀 코퍼스로 고정했다.

**여전히 못 가리는 것도 Grok이 열거했다** — Google·Stripe·베어 커넥션 문자열·`.npmrc`·
Azure·GitLab·PGP·Basic 등. 이건 고치지 않았고, 문서가 "마스킹은 완화이지 보장이 아니다"라고
말하는 것이 그 이유다.

**동시에 문서를 사실에 맞췄다.** 원칙 #4는 이제 "서버가 **쥔** 자격증명"으로 범위를 밝히고,
프롬프트 미리보기는 이 원칙이 덮지 않으며 마스킹은 **완화이지 보장이 아님**을 명시한다.
로깅 설계 스펙에도 같은 정정을 달았다.

**그리고 사용자에게 알린다.** 이전에는 **어떤 사용자 문서도 프롬프트 미리보기 로그의 존재를
말하지 않았다** — README(EN/KO)와 `/grok:usage`가 이제 `~/.grok-build/history.jsonl`이
무엇을 담고 어디로 되돌아오며 어떻게 지우는지 말한다.

## 게이트가 지키지 못하던 것

`tool-surface` 테스트는 툴 이름이 번들 **어딘가에 문자열로 있으면** 통과했다. 그런데
`routing.ts`·`orchestrator.ts`가 `grok_build_delegate`/`plan`/`verify`를 라우팅 조언
리터럴로 품고 있어 esbuild가 같은 파일에 인라인한다. 즉 **PreToolUse hook이 게이트하는 바로
그 세 툴**이 게이트가 보호하지 못하는 세 툴이었다.

실측: 스크래치 복사본에서 `registerTool('grok_build_verify', …)` 블록을 통째로 지우고
재빌드했더니 전체 스위트가 그대로 green이었다(CI의 dist 신선도 검사까지 포함).

이제 `registerTool()` **호출 인자**를 소스와 번들 양쪽에서 **정확한 집합**으로 검사한다.
같은 삭제를 다시 하면 3건이 실패한다 — 확인했다.

## `grok_cli`

- **잘림을 선언한다.** `stdoutTail`은 말없이 마지막 4,000자만 남겼고 총 길이도 표시가 없어
  단편과 전체를 구분할 수 없었다. `grok inspect --json`은 이 머신에서 **약 81 KB**라 꼬리가
  5% 미만이고 JSON으로 파싱되지 않는데, `commands/inspect.md`는 "`stdoutTail`에서 파싱한
  config를 제시하라"고 지시하고 있었다 — 불가능한 지시였다. 결과에 `stdoutTruncated`와
  `stdoutTotalChars`가 붙고, `inspect.md`는 잘렸을 때 무엇을 하라고 말한다.
- **존재하지 않는 cwd를 거른다.** `runDelegate`는 늘 검사하던 것을 이 경로만 안 해서
  `spawn grok ENOENT`가 "설치/PATH 확인"으로 보고됐다 — 경로가 틀렸는데 설치를 의심하게 만든다.

## 그 밖

- `spawn-safety`의 `shell: true` 금지가 `delegate.ts`에만 걸려 있었다. 파일 docstring은 "grok과
  git 모두"라고 적혀 있는데 `worktree.ts`에 `shell:true`를 넣어도 green이었다 — 이제 `src/`
  전 파일을 검사한다.
- `docs/07`·`examples/orchestrator-consumer.md`의 승인 후 분기가 `step.tool`을 재사용해
  **`grok_build_plan`을 다시 호출**하고 영영 위임하지 않는다. 그 자리에 있어야 할 값은
  `afterPlanGate`의 반환값이다(플러그인 내부 구현은 이미 옳고 테스트도 있다). 두 문서 모두 정정.

## 반증된 것도 남긴다

CI 부동 액션 태그·`permissions:` 부재, non-strict 상태 검사, 히스토리 전체 읽기 비용,
`plugin-surface`의 느슨한 하한, `grok_cli`의 미기록 실행 경로 — 전부 **측정 또는 문서 근거로
반증**됐다. 특히 히스토리 읽기는 `grok_build_status` 총 대기의 **3.6%**(13.6 ms 대 auth probe
362.8 ms)로 측정됐고, "4개 릴리스가 태그 없이 나갔다"는 주장은 `git ls-remote | tail -1`이
문자열 정렬이라 `v0.2.9`가 마지막으로 보인 것이었다.
