# v0.2.54 — Windows가 이름을 바꾸는 작업 폴더는 원인을 말하며 거부한다 (§4 F, 계획 2b)

2026-11-04. Windows에서 작업 폴더 경로에 Windows가 이름을 바꾸는 성분이 있으면 — 마지막 성분 끝의 점·공백(R2), 뒤에 성분이 더 오는
성분 끝의 점 하나(R1; 계약 §8) — 같은 경로가 이 래퍼와 grok에게 다른 폴더였다. 래퍼의 존재 확인(Node의 `statSync`)은 드라이브·UNC
경로에 `\\?\`을 붙여 이름을 그대로 찾고, grok은 `--cwd`를 Windows 정규화로 연다. v0.2.35가 이 거절을 "하지 않는 것"으로 남겼고
`docs/09` §4 F가 오너 판단으로 두었다. 2026-11-04 오너가 남은 작업을 권장안대로 하라고 맡겨, 이런 경로는 존재 확인보다 먼저 거부하고
grok이 열 폴더를 말하게 했다 — 그 폴더로 바꿔 보내지는 않는다.

## 재현 (쿼터 0 — grok 1.0.70, win32, 실제 `~/.grok` 미접촉)

버릴 홈의 합성 세션, grok의 API 주소 둘을 모든 요청에 404로 답하는 루프백으로 돌렸다. 버릴 폴더에 네 배치를 만들었다 — A: `w`만,
B: `w`와 `\\?\`로 만든 `w.`, C: `\\?\`로 만든 `w.`만, M: `m\w`만. 철자마다 grok을 직접 `--cwd <철자> inspect --json`으로 띄워 grok이
쓰는 폴더(`cwd`)를 읽고, 같은 철자로 번들의 `grok_cli ["inspect","--json"]`과 `grok_build_delegate`(`timeout_ms` 15000)를 불렀다.
v0.2.53 열은 이 PC에 설치된 0.2.53 캐시의 번들(개행을 맞춘 sha256 `bcb7094c…` — 태그와 같다), v0.2.54 열은 이 릴리스의 최종 번들
(`88d74b2a…`)이다 — 하네스가 잰 번들의 해시를 결과 파일에 함께 적었다. 측정 뒤 grok·node 프로세스는 남지 않았다.

|---|---|---|---|---|
| A | `w.`·`w..`·`w `·`w. `·`w.\`·`w \` | `w` | 위임 "cwd 디렉토리가 존재하지 않거나 디렉토리가 아닙니다.", `grok_cli`도 "없음" | 새 거부 — grok이 열 폴더 `w`, "그 폴더는 있습니다" |
| B | `w.`·`w.\`·`\\?\…\w.` | `w` | 확인이 이름 그대로의 `w.`에서 통과 → 위임은 spawn, `grok_cli`는 `ok`(`inspect`의 `cwd`가 `w`) | 새 거부 — `w`, "있습니다", 이름 그대로의 폴더에서는 grok이 일하지 않는다는 안내 |
| B | `w..`·`w `·`w. `·`w \` | `w` | "…존재하지 않거나…" | 새 거부 — `w`, "있습니다" |

| C | `w..`·`w `·`w. `·`w \` | 없음(exit 1) | "…존재하지 않거나…" | 새 거부 — `w`, "없습니다" |
| M | `m.\w` | `m\w` | "…존재하지 않거나…" | 새 거부 — `m\w`, "있습니다" |
| M | `m .\w` | 없음(exit 1) | "…존재하지 않거나…" | 새 거부 — `m \w`, "없습니다" |
| A | `//?/…/w.` | `w` | "…존재하지 않거나…" | 새 거부 — `w`, "있습니다" |

| 대조 | `\\?\…\w\`·`\\?\…\.\w`·`\\?\C:/…/w`·`\\?\…\w`·`\\.\…\w.`·`//./…/w.`(A), `\\?\UNC\localhost\C$` | 그 폴더 | spawn, `grok_cli` `ok` | 같다 |
| 대조 | `w`·`w\`(C), `m..\w`, `\\?\…\w.`(A) | 없음(exit 1) | "…존재하지 않거나…" | 같다 |

B의 `w.`는 확인만 이름 그대로의 `w.`를 봤고 grok은 `w`에서 일한 경우다(래퍼가 실행 전후로 돌리는 `git -C <cwd>`도 `w`를 읽었다 — 머지 전
검토가 쟀고 다시 확인했다). C의 `w.`는 확인이 통과한 뒤 grok을 띄울 때 Windows가 `w`(없음)로 바꿔 열어 spawn이 실패했고, 메시지는
원인을 grok 설치로 돌렸다. 성분 끝에 점·공백이 있는 이름 그대로의 폴더(`w.`·`w..`·`w `·중간 `m.`)는 `\\?\` 경로로도 프로세스의
작업 폴더가 되지 못했다 — 그런 폴더만 있으면 spawn이 ENOENT로, grok이 "os error 2"로 끝났고, 이름이 바뀌지 않는 중간 `m `·`m..`은
정상이었다. `\\?\`로 친 경로는 grok도 이름 그대로 먼저 찾아서(`w`만 있으면 `\\?\…\w.`는 exit 1) 존재 확인의 "없음"이 맞는 답이고,
Node가 `\\?\`로 푸는 `//?/`는 grok이 정규화해 연다(`//?/…/w.`가 `w`에서 일했다). `\\.\` 경로는 Node가 접두사를 다시 붙이지 않아
확인과 grok이 같이 정규화했다.

## 고친 것

- `delegate.ts`의 새 `win32RenamedCwdMessage`: win32에서 `env.ts`의 `win32FolderAsEntered`(grok이 `--cwd`를 푸는 규칙 — 홈 조회와 같은
  R1·R2, 이제 내보낸다)가 돌려준 폴더가 `win32.resolve`한 경로와 다르면 거부한다. 문장은 grok이 열 폴더와 그 폴더가 있는지를 말하고,
  이름 그대로의 폴더도 있으면 그런 이름은 작업 폴더가 되지 못해 grok이 그곳에서 일하지 않는다고 말한다.
  - `\\?\`·`//?/`로 시작하는 경로는 접두사를 뗀 같은 경로(`C:\…`, `\\서버\공유\…`)로 이 규칙을 읽고, 그것도 `win32.resolve`한 것과
    비교한다(UNC 공유 루트는 어느 쪽에서든 끝 구분자를 받는다). `\\?\`로 친 경로는 이름 그대로의 폴더가 있을 때만 거부하고, 없으면 존재
    확인의 "없음"에 맡긴다. 드라이브·UNC가 아닌 `\\?\` 형태(`\\?\Volume{…}` 등)는 그대로 둔다.
  - `\\.\` 경로와 POSIX는 그대로 둔다.
- 위임·plan·검증(`runDelegate`)과 `grok_cli`가 절대 경로 확인 바로 뒤, 존재 확인보다 먼저 이것을 묻는다. 어느 쪽도 경로를 바꿔 보내지
  않는다. `grok_cli`의 폴더 확인 함수는 테스트를 위해 주입할 수 있게 했다(`GrokCliDeps.dirExists`), `runDelegate`에는 플랫폼 주입을
  더했다(`DelegateDeps.platform`).
- 문서: `docs/04`(실행 전 검증, 오류 문구), 계약 §8과 머리 표, `docs/09` §3·§4 F, 계획, `CLAUDE.md`의 `env.ts` 줄.

## 하지 않는 것

- **폴더를 대신 풀어 보내지 않는다.** 그러면 호출자가 말하지 않은 폴더에서 grok이 일하게 된다.
- **이름 그대로의 폴더(`w.` 같은)에서 grok을 돌리는 길은 없다** — 위의 측정대로 그런 폴더는 `\\?\` 경로로도 작업 폴더가 되지 못했다.
- **POSIX는 바꾸지 않았다** — 이 정규화는 Windows의 것이다.
- **다른 도구의 `cwd`.** `grok_build_worktree`의 `cwd`는 래퍼가 git만 돌리는 폴더라 이 확인을 붙이지 않았다(재지 않았다).
  `grok_build_status`·`grok_auth_check`의 `cwd`는 홈을 정하는 데만 쓰이고, 그 조회(`grokHomeFor`)는 이미 같은 규칙으로 grok과 맞는다.
  PreToolUse hook도 폴더를 확인하지 않는다.
