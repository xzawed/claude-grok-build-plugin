# v0.2.41 — MCP SDK 1.32.1: 락파일의 권고 셋, 그리고 번들 안 SDK가 바뀌며 생긴 동작 변화 셋

2026-10-09. Dependabot 경보 셋(#31–#33)과 `npm audit`이 보고한 같은 셋을 처리했다. 서버 소스는 버전 문자열(`src/version.ts`) 말고는
바뀌지 않는다. 락파일·번들·버전, 채점 도구의 두 칸, 테스트 하나, 문서가 바뀐다. 권고가 걸린 코드는 배포 번들에 들어 있지 않았지만,
MCP SDK는 번들에 들어가므로 번들이 바뀌고, 사용자에게 보이는 동작 변화가 셋 생긴다(아래 "동작 변화").

## 권고와 번들

## 락파일

npm 10.9.3의 `install`·`update`는 이 저장소에서 죽거나 `libc` 블록을 지우므로(`CLAUDE.md`) `npx npm@11 audit fix
--package-lock-only`로 바꿨다. 바뀐 패키지 항목은 위 셋뿐이고 `package.json`의 의존성 범위는 그대로다(바뀐 것은 버전 필드뿐) — SDK
범위 `^1.29.0` 안의 최신이 1.32.1이다. 세 항목의 integrity는 레지스트리(`npm view … dist.integrity`)와 같고, SDK는 내려받은
tarball의 sha512와도 같다. `libc` 블록 10개는 그대로이고, 런타임 락파일 항목 93개(이름 91개)는 경로가 같고 둘(SDK, proxy-addr)의
버전만 바뀌었다.

권고는 1.31.0에서 고쳐졌다. 1.32.x가 더한 것 중 번들에 들어오는 것은 `arguments` 없는 `tools/call`의 기본값(아래 3)과, 이 서버가 쓰지
않는 task 저장소·인자 개수 한도·`prompts/get` 기본값이다. 아래 1·2는 1.30.0부터다.

## 번들 diff

`dist/index.js`는 hunk 18개다 — SDK 모듈 안 17개(`shared/stdio`·`server/stdio`·`server/zod-compat`·`shared/protocol`·`server/index`·
`server/mcp`)와 버전 문자열 하나. `dist/hook.js`는 버전 문자열뿐이다(SDK를 담지 않는다). 번들에 든 나머지 SDK 파일 아홉은 1.29.0과
1.32.1이 바이트까지 같다.

npm에서 받은 1.29.0과 1.32.1의 해당 파일 diff와 번들 diff를 Grok에게 그대로 주고 hunk마다 분류하게 했다. 판정은
`VENDOR_AND_VERSION_ONLY`였다 — 모든 hunk가 upstream 변경(esbuild의 변환 포함)이나 버전 문자열로 설명되고, 번들에서 빠진 upstream 코드
변경도 없다.

## 동작 변화

옛 번들(v0.2.40)과 새 번들을 stdio로 직접 몰아 쟀다(2026-10-09, 쿼터 0). 홈은 버릴 폴더이고 API 키는 지웠다. 부른 것은 순수 판단인
`grok_build_route`와, 핸들러가 돌기 전에 SDK가 거절하는 인자 검증뿐이라 grok은 한 번도 뜨지 않았다.

1. **요청 한 줄은 10 MiB까지.** SDK 1.30.0부터 stdio 읽기가 10 MiB(10,485,760바이트)를 넘으면 전송을 닫는다. 따로 쓴 줄은
   줄바꿈까지 정확히 10,485,760바이트면 응답을 받고 1바이트 더 길면 받지 못하며, 그 뒤 요청에도 응답이 없다 — v0.2.40은 모두
   응답했다. 같은 읽기에 붙은 다음 메시지의 바이트도 세므로 한도보다 작은 요청도 사라질 수 있고, 처리 중이던 요청의 응답도 버려지며,
   프로세스가 끝나는지는 그 뒤에 들어오는 바이트에 달렸다. 실측 전문(두 플랫폼)은 `docs/04` "요청 한 줄은 10 MiB까지"가 원천이다.
   새 테스트 `test/stdio-limit.test.ts`가 배포 번들로 정확한 경계(한글로 채운 줄로 바이트 세기까지), 그 너머의 침묵, 크게 넘은
   줄의 exit 0을 CI의 Linux·Windows에서 지킨다 — v0.2.40 번들, 한도를 1바이트 올리거나 10,000,000으로 내린 번들, 바이트 대신
   문자를 세는 번들에서 실패한다.

2. **인자 검증 오류 문구.** 전에는 zod 이슈 배열을 JSON으로 덤프했고, 이제는 이슈마다 한 줄이다 — 경로가 있으면
   `<메시지> at <경로>`, 최상위 이슈(모르는 키 등)는 `<메시지>`만. 여전히 `isError: true`인 tool 결과이고, 앞머리
   `MCP error -32602: Input validation error: Invalid arguments for tool <이름>:`도 같다.

   ```
   전: …grok_build_route: [ { "code": "invalid_type", "expected": "string", "received": "number", "path": [ "task" ], "message": "Expected string, received number" } ]
   후: …grok_build_route: Expected string, received number at task
   ```

3. **`arguments` 없는 `tools/call`은 `{}`로 검증된다.** 전에는 "Required"로 거절됐다. 이제 필드가 모두 선택인 tool(`grok_auth_check`·
   `grok_build_usage`·`grok_build_status`·`grok_build_route`)은 돈다 — 잰 것은 `route`이고 나머지는 코드로 봤다. 필수 필드가 있는
   tool은 여전히 거절하되 필드마다 한 줄로 말한다(`grok_build_delegate`: `Required at prompt`, `Required at cwd`).

이 셋 말고는 이 서버에서 닿는 변화가 없다는 주장도 Grok에게 반증하게 했다(앱의 `index.ts`·`server.ts`와 SDK 1.32.1 원본을 그대로 줬다).
판정은 `CLAIM_HOLDS`였다 — task 저장소의 세션 구분, `maxToolInputElements`, `getLiteralValue` 정리, `prompts/get` 기본값은 이 서버가
`taskStore`·옵션·프롬프트를 쓰지 않아 닿지 않거나 결과가 같다. 그 판정은 전송이 닫혀도 프로세스가 남는다고 했다. 처음 잰
10.1 MiB에서는 끝나서 기각했지만, 다시 재 보니 끝나는지는 그 뒤에 들어오는 바이트에 달렸다(`docs/04`) — Grok의 말(닫혀도 남는다)도
첫 판의 "서버가 끝난다"도 한 조건에서만 맞았다. 한 점만 재고 판정한 것이 틀렸다.

## 채점 도구

`accept-release`의 A21 칸(모르는 키를 9개 tool이 모두 거절하는가)은 옛 문구의 `unrecognized_keys`를 찾았다. 새 문구(1.30.0부터)에는
그 말이 없어, tool이 모두 여전히 거절하는데도 9개 모두 "받아들임"으로 실패했다(14/15). 이제 두 문구를 모두 알아보고, `isError`와 키
이름까지 본다. 새 번들 15/15, 설치된 v0.2.40 캐시(옛 문구) 15/15, `grok_build_route`의 `.strict()`만 뺀 빌드는 A21이 `grok_build_route`를
이름으로 대며 실패했다. 이것을 머지 전에 찾았으므로, `CONTRIBUTING.md` "Release" 2단계에 PR 전 `accept-release --repo`를 더하고
게이트를 옮겨 적던 곳(preflight 스킬의 두 절, CONTRIBUTING의 개발 절과 "Dependabot" 절)은 그 단계를 가리키게 했다. SDK 출력에 기대는 칸이 하나 더 있었다 — A14(plan과 verify가 같은 필드를
광고하는가)는 스키마에서 `properties`가 사라지면 "plan=0 verify=0"으로 통과했으므로, 이제 필드가 하나 이상이어야 통과한다.

## 버전

`v0.2.40`은 태그와 릴리스가 이미 나갔고 이번에 번들이 바뀌므로 0.2.41로 범프했다. 캐시는 버전 키다 — 같은 번호로 다른 번들을
내보내지 않는다.
