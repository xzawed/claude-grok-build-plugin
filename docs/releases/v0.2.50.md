# v0.2.50 — grok 1.0.70이 `--cwd`를 canonicalize하므로, 홈 예측도 끝 점·공백을 항상 다듬는다 (A77)

2026-10-29. grok는 상대 `GROK_HOME`(과 드라이브 없는 루트 경로)을 자신이 **실행되는 폴더**(`--cwd`, 계약 §8) 기준으로 푼다.
그 폴더의 마지막 성분이 점·공백으로 끝나면 Windows가 그것을 다듬는다 — A36의 규칙 R2다. 1.0.44까지는 `--cwd`가 **구분자로
끝나면** 다듬지 않았는데(grok이 폴더에 들어간 뒤에야 Windows가 다듬었다), **1.0.70은 `--cwd`를 canonicalize해 구분자 유무와
무관하게 마지막 성분을 다듬는다.** 플러그인의 `grokHomeFor`(`win32FolderAsEntered`)는 1.0.44의 그 예외를 아직 쥐고 있어서,
`C:\proj\w..\` 같은 폴더 + 상대 `GROK_HOME=h`에서 **`C:\proj\w..\h`**를 예측했지만 grok 1.0.70은 **`C:\proj\w\h`**를 연다.
플러그인이 grok 대신 홈을 찾는 곳 — `grok_build_status`·`grok_auth_check`의 `ready`와 hook, 그리고 `config.toml`·세션 색인·
로그인 감시 — 이 그런 폴더에서 grok이 쓰지 않는 폴더를 가리켜 "준비됨"이라 할 수 있었다.

## 재현 (쿼터 0 — grok 1.0.70, win32, 합성 세션, 실제 `~/.grok` 미접촉)

`npm run probe:home`이 1.0.70에서 **728회 중 68회 불일치**였다(전부 `relative` 분류, 다른 분류 0). 로그 오라클로 직접
재 보니(세션 없이 `grok --cwd <폴더> models`를 돌리고 grok이 `logs/`를 만든 폴더를 읽음), grok 1.0.70은 아래를 모두 `…\w\h`로
연다 — 구분자 유무와 무관하다:

| `--cwd` 마지막 성분 | grok 1.0.70 홈 | v0.2.49 예측 | v0.2.50 예측 |
|---|---|---|---|
| `w`·`w.`·`w..`·`w `·`w. `·`w .`·`w.. .` (구분자 없음) | `…\w\h` | `…\w\h` | `…\w\h` |
| `w\`·`w.\` | `…\w\h` | `…\w\h` | `…\w\h` |
| `w..\`·`w...\`·`w \`·`w. \`·`w .\`·`w.. .\` | `…\w\h` | **철자대로 — 모양마다 다름 (`…\w..\h`·`…\w \h` 등)** | `…\w\h` |

위 맨 아랫줄이 68회의 불일치다. 1.0.41·1.0.44에서 같은 프로브는 0이었다(계약 §8) — grok의 동작이 바뀐 것이지 플러그인이
새로 틀린 게 아니다.

## 고친 것

- **`env.ts` `win32FolderAsEntered`**: `endsInSeparator` 예외를 없앴다. `win32.resolve`(구분자 제거·`.`/`..` 해소)
  **뒤에 항상** 마지막 성분의 끝 점·공백을 깎는다. R1(마지막이 아닌 성분의 홑점)과 홈 성분 처리(`win32DirAsOpened`)는 그대로다 —
  grok 1.0.70은 홈 성분의 두 점 이상·끝 공백은 그대로 두고 홑점만 버린다(측정, 계약 §8).
- 이 코드는 `grokHomeFor`로 `auth.ts`·`config-keys.ts`·`delegate.ts`·`sign-in-watch.ts`와, **hook의 `grokHomeNote`**가
  쓰므로 **두 번들(`dist/index.js`·`dist/hook.js`)이 모두 바뀐다** → 릴리스.

## 프로브도 함께 고쳤다

- `probe-home-lookup.mjs`의 `grokFound`는 grok을 `cwd: folder`(raw 철자)로 띄웠는데, 지금 Node는 일부 철자로 **chdir하지
  못한다**(리터럴 폴더가 있어도 `w .\`는 `spawn ENOENT` — 측정 2026-10-29). 그러면 grok이 아예 뜨지 않아 오라클이 거짓 "못 찾음"을
  냈다 — env.ts 수정 뒤에도 16회(모두 P 배치)가 그 때문에 남았다. grok의 홈은 `--cwd`가 정하므로(계약 §8), 프로브는 이제
  **진입 가능한 실행 폴더**에서 grok을 띄우고 시험 폴더는 `--cwd`로만 넘긴다. 1.0.41 때 이게 0이었던 건 그때 Node가 그 철자로 chdir에
  성공했기 때문이다(현재 Node에서 재현되는 하네스 한계였다). 래퍼의 위임은 `--cwd`와 `cwd` 모두에 작업 폴더를 주지만, 그런 폴더는
  이미 "폴더 없음"으로 거절한다(`docs/releases/v0.2.35.md`) — 노출은 홈을 예측만 하는 `ready`·hook 쪽이다.

## 검증

- 새 테스트(`env.test.ts`)는 고치기 전 소스에서 **빨강**이고 고친 뒤 통과한다 — 구분자로 끝나는 `w \`·`w..\`·`w...\`·`w. \`·
  `w .\`·`w.. .\` 여섯 모양이 모두 `C:\d\w\h`. 수치는 `npm test`가 원천이다.
- 다시 잰 것: `npm run probe:home` **728회·0 건너뜀·0 불일치**(grok 1.0.70) — 1.0.41·1.0.44와 같다.
- Grok 반증(정적, effort low): 경로 P1–P8을 분류해 **CLAIM_HOLDS** — `_AFTER`가 P1–P5·P7에서 grok 1.0.70과 일치하고, 달라진
  곳(P1, 구분자 경로)은 F2상 옛 코드가 틀렸던 자리이며, 이미 맞던 경로는 회귀가 없다. P6(맨 드라이브 루트)은 두 판이 같은 문자열을
  내 변화 없음.

## 하지 않는 것

- 홈 성분을 더 깎지 않는다 — grok은 `h..`·`h `·`h...`를 그대로 두고 `h.`만 `h`로 한다(R1, 측정). 플러그인도 그렇다.
- 맨 드라이브 루트(`C:\`·`C:`) 동작은 바꾸지 않았다 — 끝 점·공백이 없어 수정이 닿지 않고, 두 판이 같은 결과를 낸다.
- `~`는 여전히 풀지 않는다(A35) — grok이 풀지 않으므로.
- POSIX·드라이브 절대 홈(`C:\…`)에는 이 다듬기가 닿지 않는다(`grokHomeFor`의 분기) — 바꾸지 않았다.
- grok을 버전별로 분기하지 않는다 — 플러그인은 측정한 최신 grok(1.0.70)을 쫓는다(grok 자가 업데이트·오너 최신화 규칙·계약 §8). ≤1.0.44에서는 구분자로 끝나는 이 폴더 모양에 예측이 어긋날 수 있으나, 노출은 `ready` 예측뿐이고 위임은 그런 폴더를 "폴더 없음"으로 거절한다 — 이전 코드도 한 버전(1.0.44)의 동작을 하드코딩했다.
