### v0.2.34 — 상대 경로 `GROK_HOME`을 grok처럼 grok이 실행될 폴더 기준으로 푼다 (A35)

상세: `docs/releases/v0.2.34.md`. grok 쪽 실측: `docs/specs/grok-cli-contract.md` §8.

- **어떻게 나왔나:** v0.2.33 후속 점검에서 Grok에게 "grok 대신 홈을 찾는 세 곳"을 측정한 사실과 함께 **분류**시켰다
  (추적이 아니다). 셋 다 `DIVERGES`였다. 배포 v0.2.33 번들로 재현했다 — 세션이 `<작업 폴더>/rel-home`에 있는데
  위임은 110~129 ms에 "로그인 필요"로 거절됐고 hook도 막았다. grok은 뜨지도 않았다.
- **grok 쪽 사실 (1.0.41, win32, `grok du --json`, 쿼터 0):** 상대 `GROK_HOME`은 grok의 작업 폴더 기준이다 —
  `--cwd`가 있으면 그 폴더가 띄운 폴더를 이긴다. `~`는 풀지 않는다. `GROK_HOME`이 없으면 `USERPROFILE`이 홈을
  정하고 `HOME`은 아니다. 마지막 것은 계약 §8의 옛 문장("`HOME`/`USERPROFILE`은 못 움직인다")을 반증한다 —
  옛 명령 두 줄은 `HOME`만 바꿨다.
- **무엇:** `grokHomeFor(env, 폴더)`로 인증 사전 확인·`billingCaveat`·resume 세션 색인·hook이 grok이 실행될
  폴더를 기준으로 묻는다. status·auth check는 `cwd`를 받고, 상대 경로면 `grokHomeNote`를 붙인다. 거절·거부
  메시지도 그 메모를 붙인다.
- **첫 판이 놓친 두 경우 — 둘 다 실측으로 찾았다.**
  - `worktree: true`: grok은 새 worktree에서 뜬다(`--cwd <worktree>`). 첫 판은 작업 폴더를 확인해 통과시켰다.
    그러자 worktree가 남고 grok이 세션 없이 떠 `auth_error` + `grok login` 안내로 끝났다(3,228 ms). 이제 새
    worktree 안의 가상 폴더로 묻고, worktree를 만들기 전에 거절한다(224 ms).
  - `grok_cli` 인자의 `--cwd`: grok은 그 폴더 기준으로 푼다(`--cwd F`로 `F\rel-home` 실측). 첫 판 hook은 tool의
    `cwd`로 확인해 정상 호출을 막았다. 이제 그런 호출은 추측하지 않고 통과시킨다.
- **Grok 반증.**
  - hook: 호출 모양 5개를 분류시켰다. `CLAIM_NOT_SHOWN`, 모두 "잘못 막지 않음".
  - 서버: 조회 4개를 분류시켰다. 캡에 걸렸고, `resume` 한 번으로 답을 받았다. worktree 행이 `CAN_DIFFER`였고
    **진짜였다.** 가상 폴더가 고정 이름 `(새 worktree)`였는데 거절 메시지가 그 경로를 출력했다. 거기 합성 세션을
    심자 확인이 통과하고 worktree가 생겨 `auth_error`로 끝났다. 호출마다 새 이름으로 바꾸자 같은 상태에서 225 ms에
    거절됐다. 재분류(4종)는 `CLAIM_NOT_SHOWN`이었다.
- **Grok 프롬프트 형태별 집계 (2026-09-24, v0.2.33~v0.2.34 작업 전체 — `CLAUDE.md` §5 규칙의 근거):**
  - 코드를 **추적**하게 한 새 프롬프트(반례 만들기 포함) 5/5가 300~360초 캡에 걸렸다. 후보만 **제안**하게 한 것도
    1/1 걸렸다(후보는 스트림에서 회수).
  - 사실을 주고 **분류**하게 한 새 프롬프트는 5번이다. 첫 실행에 끝난 것 2번(A35를 찾은 G2, hook 판정), 캡에 걸린
    세션을 `resume`해 "이미 한 분석으로 지금 쓰라"고 하자 끝난 것 2번(서버 판정 — worktree 가상 폴더 결함을 찾았다 —
    과 그 재판정), 캡에 걸려 스트림에서 회수한 것 1번(v0.2.33의 읽기 함수 10상태)이다.
- **수락:** `accept-release.mjs`에 `A35` 칸을 넣었다(spawn 없음). 설치된 0.2.33은 이 칸만 실패한다(12/13).
- **머지 전 검토 (독립 검토자 셋: 코드·테스트 / 문서 / 반례) — 두 번째 커밋.** 지적은 전부 다른 방법으로 재확인했다.
  - 코드: hook이 **읽을 수 없는 페이로드**를 상대 경로에서 통과시켰다(main은 거부) → 폴더를 모를 때의 양보는 읽은
    페이로드에만. **배선 무보호** — 검토자가 스크래치 사본에서 `defaultServerDeps`의 폴더 전달과 status 필드를 빼도
    대상 유닛 스위트가 전부 녹색이었다 → 배포 번들 e2e(`relative-home-e2e.test.ts`) 추가. 같은 두 가지를 빼고 빌드하자 그
    테스트만 2개 실패했다(유닛은 녹색). 거절 메모가 "grok 미설치"·"키 없음"에도 붙었다 → `not_logged_in`에만.
  - 반례: Windows의 **드라이브 없는 루트 경로**(`\x\gh`)를 Node가 절대 경로로 봐 묻는 프로세스의 드라이브에 뒀다.
    grok은 작업 폴더의 드라이브에 둔다 — `grok du`로 재현(C: → `C:\…`, D: → `D:\…`, `--cwd <D:>` → `D:\…`).
    → `grokHomeDependsOnFolder`. 끝 공백은 grok이 버리고 플러그인은 버리지 않아 로그인 상태를 `not_logged_in`으로
    보고했다 — A35 전부터 있던 것이라 **A36으로 열었다**(배포 번들 `grok_auth_check`로 재현). [정정 2026-09-25: 공백을
    버리는 것은 `grok du`의 보고뿐이다 — 세션 조회는 버리지 않아 grok도 로그인 안 된 상태였다. v0.2.35 항목.] `--cw` 약어는 grok이
    거부해(exit 2) hook의 `--cwd` 판별로 충분하다. 닿지 않는 UNC `cwd`의 약 21초 대기와 없는 `cwd`의 "로그인 필요"
    안내는 알려진 한계로 적었다.
  - 문서: `grok_cli`에 서버 확인이 있는 것처럼 쓴 곳 4곳, `cwd`를 안 넘기던 템플릿 3곳(테스트로 고정 — 그 테스트는

    스위치", `CLAUDE.md` §5의 집계(출처와 안 맞아 규칙만 남기고 여기로 옮겼다).
- **두 번째 커밋 재검토 (코드 / 문서) — 세 번째 커밋. 수정이 또 결함을 들여왔다.** 드라이브 없는 경로를 가리려고 넣은

  장치 경로를 "폴더에 따라 달라짐"으로 봤다. 그래서 main이 거부하던 `grok_cli` 프롬프트 실행(`cwd` 없음)이 통과했고,
  메모는 절대 경로를 "상대 경로"라고 불렀다. 검토자가 세 번들로 보였고 `path.win32`로 재현했다 → 판정을 "절대가 아니거나,
  구분자 **하나**로 시작"으로 바꿨다(둘이면 UNC·장치). 새 번들에서 같은 입력이 다시 거부되고 메모가 없다.
  문서 쪽: 없는 `cwd`의 "로그인 필요"를 한계로 적었다고 했으나 적혀 있지 않았다 → 릴리스 노트·`docs/04` 두 곳에 적었다.
  `CLAUDE.md`의 결함 건수(원천은 `docs/10`)와 날짜 없는 규칙을 고쳤고, 드라이브 없는 경로를 메모·README·`docs/04`에
  반영했다(`/x`도 `grok du`로 재어 `\x`와 같음을 확인). e2e 테스트에 30초 제한을 걸었다(기본 5초가 자체 15초 경비보다 먼저 울린다).
- **세 번째 커밋 재검토 — 코드 결함 없음, 문서 4건 → 네 번째 커밋.** 검토자가 세 번들(main·두 번째·세 번째)을 입력
  21개 × 호출 모양 3개로 돌려 새 통과가 없음을 보였다. UNC 규칙을 grok으로 쟀고(공유 경로는 그대로, 서버만 쓴 형태는
  grok이 거부) 나도 다시 쟀다 → 계약 §8. "드라이브 없는 경로"라는 느슨한 표현(UNC도 드라이브 문자가 없다)과 메모를
  "상대"로만 부르던 곳을 `\grok` 예로 바로잡았다.

     (`auth.json` 삭제, `auth.json.lock`만 남음 — 계약 §7 C), hook의 거부가 hook 결함처럼 보였다. 인증 파일을

     — `CLAUDE.md`가 금지한 바로 그 메커니즘이다. 스크립트 파일로 다시 했다.
  3. B7을 적으려고 요약에서 기억한 내용을 쓰려다 멈추고, 트랜스크립트에서 원 출력을 회수해 적었다 — 요약에는

### v0.2.33 — config.toml의 모델별 키를 `billing` 옆에 알린다 (오너 목표 E)

상세: `docs/releases/v0.2.33.md`. 설계·완료 조건: `docs/specs/2026-09-24-config-model-keys-billing-caveat.md`.
grok 쪽 실측: `docs/specs/grok-cli-contract.md` §10 끝.

- **왜:** B6이 남긴 종량제 경로는 하나다. 사용자 `config.toml`의 모델별 `api_key`/`env_key`로, 세션보다 앞서고
  env 정제로는 못 막는다. 오너가 "감지·경고, 막지 않음"을 골랐다.
- **무엇:** `config-keys.ts`가 `$GROK_HOME/config.toml`을 grok과 같은 해석으로 읽는다. 구독 모드에서 status와 위임
  3종 결과에 `billingCaveat`가 붙는다. 실행은 막지 않고, `billing` 값은 그대로이며, 이력에 싣지 않는다. 키 값은
  어디에도 없다. `billing`을 보여주는 명령 템플릿 11개·에이전트·스킬 2개가 "알리되 멈추지 말라"고 지시한다
  (테스트로 고정).
- **왜 직접 읽나:** TOML 라이브러리는 세 번째 런타임 의존성으로 번들에 인라인된다. 게다가 이 레포의 npm 경로 함정을
  새로 밟는다. 필요한 문법은 작다.
- **검증 — 두 번째 독립 방법까지.**
  1. **배포 번들 + 합성 `GROK_HOME`**(가짜 세션·가짜 키, HOME·Claude 설정도 스크래치, 쿼터 0).
     - status(304ms)가 `grok-4.7 (api_key)`와 `gw (env_key → 변수명)`를 보고했다.
     - 따옴표 없는 `[model.grok-4.6]`, 그리고 구독 모드가 지우는 `XAI_API_KEY`를 가리키는 모델은 보고하지 않았다.
     - 위임은 실제로 돌았고(401 → `auth_error`) caveat를 실었다. 이력 행에는 없다. 출력 어디에도 가짜 값이 없다.
  2. **grok 자신의 해석(1.0.41)** — `inspect`의 `configWarnings`와 디버그 로그의 `model_byok`. 네 형태 모두 일치했다.
  3. **차등 비교** — 기준은 smol-toml 1.9.0(TOML 1.1).
     - 생성 문서 80,008개에서 불일치 0.
     - 하네스 자체는 판독기 사본에 결함 3개를 넣어 검증했다(누락 9,628 / throw 3,056 / 불일치 2,089를 잡았다).
     - 공식 toml-test(`ff49d10`)의 valid 문서 208개(1.0.0)·218개(1.1.0)에서 throw 0.
  4. **깨진 `config.toml`** — grok은 실행하지 않는다("Failed to load config"). 그래서 판독기가 무효 TOML을
     너그럽게 읽는 것은 과금 면에서 무해하다.
- **판독기를 고칠 때 다시 돌리는 법(차등 비교):**
  1. 스크래치 디렉터리에 `npm i smol-toml`을 설치하고, `mcp-server/`에서
     `npx esbuild src/config-keys.ts --bundle --platform=node --format=esm --outfile=<스크래치>/reader.mjs`로
     판독기를 번들한다.
  2. 시드 PRNG로 문서를 조합해 만든다. 축은 다음과 같다.
     - 쓰는 자리: 표 머리, 공백·탭 머리, 루트 dotted, `[model]` 아래 dotted·inline, 루트 inline, 하위 표 먼저
     - 키 표기: bare, basic, literal, `\u` 전부 이스케이프
     - 값: 문자열 네 종류, 빈 값, 공백, 배열
     - 앞 잡음: 따옴표 든 주석, 여러 줄 문자열 속 가짜 머리, 여러 줄 배열, `[other]`, `[[servers]]`,
       그리고 머지 전 검토 뒤에 넣은 `[[model]]`, `[[model."m".efforts]]`, `[[a]]`+`[[a.b]]`, 모델 표 뒤의 배열 표
     - CRLF, BOM
  3. `parse()` 결과의 `model.<id>.api_key|env_key`와 `modelCredentialDecls`를 비교한다. 불일치는 Python
     `tomllib`으로 동률을 가른다 — smol-toml 1.9.0은 줄 끝 역슬래시 뒤 닫는 `"""` 앞의 따옴표를 잘못 버린다
     (반례 검토가 찾았다).
  4. **결함 주입으로 하네스가 보는지부터 확인한다.**
  5. 파일 **종류**(FIFO·장치·디렉터리)는 생성기가 다루지 않는다. `test/config-keys.test.ts`에 고정돼 있고,
     POSIX 전용 테스트는 CI의 Linux 작업에서 돈다(개수는 그 파일이 원천이다 — 여기 적었다가 다음 커밋에서 낡았다).
- **Grok 반증.**
  - 주장 B("유효한 TOML에서 던지나")는 `resume` 뒤 `CLAIM_NOT_SHOWN`이었다. 추적한 8개는 테스트로 고정했다.
  - 주장 A("모델 키를 놓치나")는 300·300·360초 timeout으로 끝났다. 후보 *제안*만 시킨 실행도 timeout이었다.
  - 대신 잘린 세션의 `updates.jsonl` 스트림에서 제안 10개를 회수해 기준 파서로 판정했다. 유효한 9개는 일치했다(고정).
    나머지 1개(비ASCII bare key)는 무효 TOML이라 grok이 파일째 거부한다.
  - 그 1개가 코드 주석 "너그러움은 자격증명을 지어낼 수 없다"를 엄밀히 틀리게 만들었다. 주석을 실측 문장으로
    바꿨다. `CLAUDE.md` §5에 "반례를 만들라는 주장은 캡을 넘는다" 한 줄을 넣었다.
  - 머지 전 검토 뒤 새 읽기 함수에는 파일 상태 10가지를 **분류**시켰다(반례를 만들라고 하지 않았다). 이것도 캡에
    걸렸다. 스트림에서 회수해 보니 FIFO·장치·디렉터리·소켓은 열기 전에 거부, 자라는 파일은 원래 크기로 제한이었다.
    유일한 `CLAIM_SHOWN`은 "정규 파일을 가리키는 심볼릭 링크를 따라 읽는다"였다. 의도한 동작이라 기각했다 — grok
    문서가 dotfiles 저장소로 향하는 링크 `config.toml`을 지원 구성으로 적는다(쓰기도 링크를 따라감).
- **머지 전 검토 — 에이전트 셋(코드·테스트 / 문서 / 반례), 모두 실측으로 다시 확인한 뒤 고쳤다.**
  - **회귀(가장 무거움):** Linux에서 `config.toml`이 쓰는 쪽 없는 FIFO이거나 `/dev/zero` 링크이면, 동기 읽기가
    돌아오지 않았다. 이 읽기는 모든 spawn 전과 status에서 돌므로 **서버 전체가 응답을 멈췄다**(route까지). main은 이
    파일을 읽지 않으니 이 기능이 만든 회귀였다. 이제 정규 파일이고 1 MiB 이하일 때만 연다. 같은 스크립트로 같은
    조건을 재니: 수정 전 번들은 status 8초·route 3초 무응답, 수정 후는 status 70~72ms(`config_unreadable`)·route 2ms.
  - **오경보:** `[[model]]` 뒤의 `[model."x"]`는 TOML상 배열 원소의 하위 표인데 모델 `x`로 보고했다(검토자 둘이 따로
    찾음). grok 1.0.41은 그때 모델 재정의를 전부 무시한다(`inspect` 경고, 키 미사용 — 실측). 배열 표 접두 아래는
    모델 표로 보지 않는다.
  - **크기:** 모델 목록 상한 20개 + `modelsOmitted`, 판정 순서 Set, win32 소문자 색인, 문자열 조각 누적. 검토자
    측정으로 10만 모델 8.8초, 8 MB 문자열 0.79초였던 경로다.
  - **테스트 공백 5가지:** 결함을 주입하면 잡히는지 하나씩 확인했다. 대상은 `model` 루트 검사, 정확히 3단계,
    `api_key`→`env_key` 순서, 여러 줄 문자열 두 모양, spawn 전 계산 순서다. FIFO 테스트는 늦게 오는 쓰기
    프로세스를 붙여, 구현이 되돌아가도 멈추지 않고 1초에 실패한다(Linux 컨테이너에서 확인, CI 작업엔 시간 상한이 없다).
  - **문서 13건:** 보안 문구 "서버는 자격증명을 읽지 않는다"(README·SECURITY·`docs/02`)와, CAUTION의 "셸의 키는
    절대 자격증명이 될 수 없다"를 바로잡았다(`env_key`가 가리키는 변수는 예외). 첫 성공·프리셋 표면, 소비자 예시,
    `docs/01`·`03`·`04`, 스킬의 낡은 `grok_cli` 문장도 고쳤다. `observeBilling`의 정상 분기와 도구 설명도
    `billingCaveat`를 가리키게 했다.
  - **넓힌 차등 비교:** 새 판독기는 80,008건(시드 424242: 유효 78,991, 자격증명 있음 65,968)에서 불일치 0이다. 같은
    생성기에 옛 판독기를 넣으면 초과 보고 2,600건이다 — 이 부류를 이제 본다. 공식 코퍼스 throw 0, Grok 후보 전부 일치.
    (재현 시드: 첫 비교 12345, 결함 주입 확인 777, 넓힌 비교 424242.)
- **수정 커밋의 재검토 — 내 수정이 결함을 하나 만들었다.**
  - **결함:** 배열 표 접두 검사가 이차였다. 각 머리를 앞선 `[[…]]` 경로 전부와 비교했기 때문이다. 1 MB 유효 파일에
    배열 머리 9.6만 개를 넣으면 27초가 걸렸다. 고치려던 FIFO와 같은 부류의 멈춤이다. 이제 자격증명이 들어갈 수
    있는 머리(2부분 이하)만 보고, 그런 배열 경로만 Set에 두어 머리마다 조회는 둘 이하다.
  - **남아 있던 비용:** 키마다 표 경로 전체를 복사했다. 20만 부분 머리 뒤에 키 5.9만 개면 50초였다(수정 전부터
    있던 비용이고, 릴리스 노트의 "선형"을 거짓으로 만들었다). 자격증명 깊이(3)를 넘는 경로는 이제 만들지 않는다.
  - **최종 크기에서 잰 판별력(상한 1초):** 배열 6만 개는 이전 수정본 8,429ms, 새 판독기 37ms다. 깊은 머리 3만 ×
    키 3만은 5,152ms 대 17ms다. 3만 개에서는 1,969ms 대 19ms라 상한과 너무 가까워 크기를 키웠다.
  - **테스트 공백:** 기본 의존성이 안전한 읽기를 쓰는지 아무 테스트도 고정하지 않았다. 되돌려도 전부 녹색이었고,
    실제 FIFO는 멈췄다. 기본 경로를 거치는 끝단 테스트 둘을 넣었다.
    - 1 MiB를 넘는, 키가 든 정규 파일: 상한을 풀면 `config_model_keys`로 실패한다.
    - POSIX의 FIFO: 늦게 오는 쓰기 프로세스가 **키가 든 유효 TOML**을 넣는다. 그래서 순진한 읽기는
      `config_model_keys`로 실패하고 멈추지 않는다.
  - **사소:**
    - id·변수 이름을 200자에서 자른다(20개 × 긴 id로 2백만 자였다).
    - 도구 설명과 `docs/08`에 "확인 못 함"을 넣었다.
    - README의 "아무 변수나"를 "그 두 변수가 아닌"으로 고쳤다. 지워지는 두 변수는 보고하지 않기 때문이다.
    - 완료 조건 6번의 표면 목록(14곳)을 고쳤다.
    - FIFO 테스트의 쓰기 프로세스를 프로세스 그룹째 종료한다(`sleep`이 1초 고아로 남았다).
  - 재검토자 자신의 하네스도 네 번 틀렸다. 부분 export로 가짜 실패 21건, CRLF 때문에 돌연변이 치환 0건, 번들
    경로 주석 차이를 불일치로 오인, 존재하지 않는 잠금 상수를 썼다. 모두 결론 전에 스스로 잡았다.
- **마지막 수정 커밋의 재검토 — 코드 결함 없음.** smol-toml·tomllib 양쪽과의 표적 사례 51개, 구조 퍼즈 150만 건,
  돌연변이 6종으로 확인했다. 남은 것은 문서 드리프트 하나와 사소 셋이었고 모두 고쳤다.
  - 문서 드리프트: 이 항목이 적었던 "POSIX 전용 테스트 둘"은 다음 커밋에서 셋이 됐다. 이제 개수를 적지 않는다.
  - 이름 자르기가 UTF-16 단위라 이모지가 경계에 걸리면 반쪽이 남았다. 이제 통째로 뺀다. 경계 주변 7개 위치를
    `isWellFormed`로 확인했다.
  - JSDoc이 잘린 id를 "적힌 그대로"라고 했다.
  - 시간 테스트가 6만 개 인자를 펼쳐 V8 한계의 절반에 있었다. 이제 `join`으로 만든다.
  - 이 검토자의 하네스도 세 번 틀렸다. 하나는 `core.autocrlf`로 export한 CRLF 소스를 모르고 컨테이너에서 돌린
    것이다. 또 하나는 부분 export로 가짜 실패 24건을 낸 것이다. 마지막은 `node -e`로 돌연변이 사본을 만든 것으로,

### 후속 — v0.2.32 마지막 칸, B6 닫힘, 이 머신과 계약을 1.0.41로

- **v0.2.32 마지막 칸:** 사람의 재시작 없이 `claude -p`로 새 세션을 띄워 닫았다. 새 claude.exe의 MCP 자식이
  `…/grok/0.2.32/…`로 떴고 `grok_build_status`가 `serverVersion=0.2.32`를 돌려줬다(`docs/09` §5).
- **B6 닫힘 — env만으로 생기는 우발적 종량제 폴백은 두 키뿐이다**(계약 §10 끝). 가짜 값으로 1.0.30·1.0.41을 쟀다.
  남는 종량제 경로는 사용자 `config.toml`의 모델별 키이고, 이미 범위 밖으로 결정된 경로다. `GROK_DISABLE_API_KEY_AUTH`는
  대책이 못 된다(세션이 있으면 설정 키를 막지 않는다 — 실측). Grok 반증은 `env_key`가 가리키는 변수를 "env가
  관여하는 경로"로 짚어 `CLAIM_SHOWN`을 냈다. 참이지만 새 결함은 아니다(docs/09 교훈 ③). Grok이 다음으로 재라고 한
  `GROK_AUTH`는 쟀다 — 문서에 없는 인라인 인증 저장소이고, 스키마를 알아내지 못해 미측정으로 남겼다.
- **이 머신 grok 1.0.30 → 1.0.41, 계약 스냅샷 갱신.** 표면 diff 0, `--strict` 녹색, `drifted`·`snapshotBehindLatest`
  모두 `false`. 재측정한 절은 §6(plan 모드) — 1.0.41도 쓰기를 막는다. `write` 도구 호출이 권한 단계에서 취소된
  것을 세션 기록으로 봤다(안 쓴 게 아니라 막힌 것).
- ⚠️ **판별자를 두 번 잘못 잡았다 — 둘 다 대조군이 잡았다.** ① "출력에 401이 있나"로 자격증명 사용을 판별했더니
  `XAI_API_KEY`(문서화된 폴백)도 "안 씀"으로 나왔다. grok은 그 키를 시작할 때 `api.x.ai/v1/models`로 검증하고
  400을 **디버그 로그에만** 남긴다. ② 서버 401의 `auth_kind`로 "어느 자격증명을 썼나"를 판별하고, 설정 키는
  합성 세션이 쓰지 않는 모델(`grok-4.7`)에만 걸었다. 정답은 계약 §10이 1.0.13에서 쓴 디버그 필드
  (`auth_type`/`has_api_key`)였다. 그리고 세션이 없을 때의 `auth_type=ApiKey`는 **아무것도 없어도 찍힌다**. 대조군이
  없었다면 `GROK_AUTH`·`GROK_AGENT_SECRET`를 "API 키로 쓰인다"고 잘못 보고했을 것이다.

### B4 닫힘 — 인증된 턴에서 Linux 샌드박스는 실제로 쓰기를 막는다

`docs/10`에서 B4의 남은 절반은 "실계정이 필요하다"로 열려 있었다. 호스트 `auth.json`을 컨테이너에 복사하지 않고
**컨테이너 전용 로그인**을 했다(별도 Docker 볼륨을 `GROK_HOME`으로, 오너가 기기 코드를 승인). 토큰 갱신이 호스트
세션을 깰 위험을 피하려는 것이다. 측정 뒤에는 로그아웃하고(`auth.json` 삭제 확인) 볼륨을 지웠다.

grok 1.0.41 + bwrap(`--privileged`), 같은 4단계 과제를 두 arm으로 돌렸다. `workspace`에서는 cwd 안 쓰기만 성공했고,
`/srv`에 쓰는 것은 **grok의 파일 도구도 셸도** `Permission denied`로 막혔다(`/tmp`는 프로파일이 허용).
통제 arm(`off`)에서는 전부 성공했다. 같은 컨테이너에서 두 가지를 더 쟀다.
- **A34 끝단:** 1.0.41에서도 워커의 중첩 호출이 `blocked / inside_grok_worker`로 거절됐다.
- **모델 목록:** 인증된 `grok models`로 보면 probe의 모델 diff가 0이다 — 미인증 측정의 "두 모델 사라짐"은 착시였다.

⚠️ 응답에 "제약이 작동했다"를 싣지 않는다는 판정은 그대로다. bwrap이 **그 호스트에서** 동작했는지를 래퍼는 모른다.

### v0.2.32 — 워커가 우리 플러그인을 다시 불러와 또 다른 Grok을 띄울 수 있었다 (A34)

상세: `docs/releases/v0.2.32.md`, 실측 전문: `docs/specs/grok-cli-contract.md` §14.

**잔여 점검에서 나왔다.** v0.2.31 수락의 마지막 칸(새 세션의 프로세스 명령줄)을 재려고
`Win32_Process`를 봤더니, 떠 있는 플러그인 MCP 여섯 개 중 하나의 부모가 claude.exe가 아니라
**grok.exe**였다. grok은 설치된 Claude Code 플러그인을 자기 것으로 로드한다 — 이 플러그인까지.
그래서 위임받은 워커마다 이 서버의 사본이 떠 있었고(MCP를 구성한 세션 전부 — 기록 937개 중 932개),
워커는 그것으로 또 다른 grok을 띄울 수 있었다. 재현하니 바깥 delegate는 `filesChanged: []`를
돌려줬고, 그 사이 중첩 런이 다른 디렉터리에 파일을 썼다. **실사용에서도 세 번 시도됐다**(grok 1.0.13) —
리뷰형 프롬프트를 `grok_build_verify`로 다시 넘기려 한 것이고, 그중 한 번은 worktree 격리 런에서 본
저장소를 지목했다. 셋 다 plan 런이라 grok의 권한 게이트가 취소했을 뿐이고, `--always-approve` 런은 MCP
호출을 실행한다(9/9).

**고친 방법:** `buildGrokEnv`가 모든 grok에 `GROK_BUILD_WORKER=1`을 붙이고, 그 env를 물려받은 사본은
9개 도구를 목록에 둔 채 전부 거절한다(`reason: inside_grok_worker`, spawn·이력 없음). grok의 끄는
스위치를 쓰지 않은 이유: 찾은 것(`GROK_CLAUDE_MCPS_ENABLED` 등, 비공개)은 `~/.claude.json` 서버만 끄고
플러그인 출처 서버는 그대로 둔다(실측). 숨기지 않고 거절하는 이유: 도구가 없으면 워커가 10턴·38만
토큰을 들여 찾았다. **닫는 것은 이 플러그인을 거치는 경로뿐이다** — 셸을 쥔 워커는 `grok`을 직접 띄울
수 있고, 그건 이 플러그인의 표면이 아니다.

**전제를 probe가 감시한다.** 수정은 "grok이 env를 MCP 자식에게 물려준다"는 grok의 동작 하나에 기대고,
테스트는 전부 표식을 손으로 넣으므로 그 동작이 바뀌어도 녹색이다(반례 검토자 지적). 그래서 실제 사본과
같은 조건 — 헤드리스 세션, 플러그인 출처 서버 — 을 **합성 인증**(첫 요청 401, 쿼터 0)으로 재서
1.0.30 win32, 1.0.41 Linux(샌드박스 포함)에서 도달을 확인했고, 그 측정을 `probe:contract`의
`workerMarker`로 넣었다(`reached: false`면 `--strict` 실패). 합성 인증 생성은 `synthetic-auth.mjs`로
옮겨 `probe-expired-session.mjs`와 공유한다.

**Grok 반증:** 후보 경로 7개(표식 미도달·이름 불일치·등록 순서·배선 누락·우회 spawn·원 핸들러 호출·
다른 등록 경로)를 분류시켜 `HOLE_CLOSED`, 목록 밖 경로 "none".

**머지 전 검토 세 명(코드·테스트 / 문서 / 반례) — 구멍은 없었고, 범위와 숫자를 바로잡았다.** 반영:
거절 문구에서 변수 이름 제거(읽는 쪽이 워커 모델이다), 주장 범위를 "이 플러그인 경로"로 좁힘, 보호는
grok이 로드한 **설치본**이 0.2.32 이상이고 재시작한 세션부터라는 조건 명시, 수락 스크립트 A34 세션의
모든 홈 격리(옛 번들 v0.2.7~0.2.11은 `GROK_HOME`을 안 봐서 실제 이력에 행을 쓸 수 있었다),
`best_of_n` 가드 테스트가 **첫 줄만** 보던 것을 전부 보게 강화(A34 프로브에서 빠져도 안 걸렸다 — 변이로 확인).

**그 반영분을 다시 적대적으로 검토했더니, 새 probe에 진짜 구멍이 있었다.** 격리 env가 API 키 둘만
지웠는데, grok README가 문서화한 **`GROK_AUTH_PROVIDER_COMMAND`**(외부 토큰 발급기)는 그대로 넘어갔다.
가짜 발급기로 직접 재현하니 grok은 합성 `auth.json`이 있는데도 세션을 열 때 발급기를 불렀고, 그 토큰으로
추론을 네 번 재시도했다 — 발급기가 진짜였다면 "거부될 세션"이 실제 턴이 된다. 같은 구멍이 기존
`probe-expired-session.mjs`에도 있었다. 이제 두 프로브 모두 `isolatedGrokEnv`로 부모의 `GROK_*`·`XAI_*`를
전부 지우고(고친 뒤 발급기 호출 **0회** 실측), probe는 세션이 받아들여지면(`sessionAccepted`) 그리고 grok이
플러그인 서버를 아예 안 띄우면(`blind`) `--strict`를 실패시킨다. `--strict` 종료는 모든 경고를 찍은 뒤로
옮겼고(드리프트와 같이 오면 A34 경고가 삼켜졌다), `best_of_n` 가드는 여러 줄로 나뉜 호출도 본다(변이로 확인).
플러그인 본체가 다른 자격 변수까지 지워야 하는지는 성격이 다른 질문이라 `docs/10` **B6**으로 열어 두었다.
⚠️ **그 구멍은 Grok 반증을 통과한 뒤에 나왔다.** Grok은 probe에 대해 `CANNOT_BILL`이라 판정했는데, 내가 준
facts가 "grok이 쓰는 자격증명은 API 키 둘뿐"이라고 닫아 두었기 때문이다. 판정은 facts 안에서 옳았고 facts가
틀렸다. 찾은 쪽은 정적 판정이 아니라 **가짜 발급기로 grok을 실제로 움직여 본** 검토자였다 — `CLAUDE.md` §5에
"닫힌 facts 금지" 한 줄을 남겼다.

**grok 쪽 결함도 하나 봤다 — 우리 것이 아니다.** grok의 stdio MCP 디코더가 8 KiB를 넘는 메시지를
바이트 8192에서 잘라 읽는다. 우리 `tools/list`가 12,625바이트라 기록 937개 중 335개(36%)에서 해석 오류가
났고 292개는 그 때문에 연결에 실패했다(1.0.13 `65s`, 1.0.30 `70s` 타임아웃) — 그게 A34를 간헐적으로
가렸고, 재현이 두 번 실패한 이유다.

⚠️ **내 숫자가 세 번 그럴듯하게 틀렸다 — 문서 검토자가 기록을 다시 세서 잡았다.** "923개 중 923개"는
937개 중 932개(5개는 MCP 구성 전 종료), "약 35%·70초"는 해석 오류(36%)와 연결 실패(31%)·65/70초를 섞은
값, 그리고 실사용 3건과 plan 취소를 1.0.30에 귀속했는데 **이 머신은 09-13에야 1.0.30이 됐다** — 셋 다
1.0.13이었다. 셋 다 명백히 이상해 보이지 않았다는 점이 `CLAUDE.md` 8(b)("그럴듯하면 더 의심한다")의 실례다.

⚠️ **하네스가 아홉 번 틀렸다 — 일곱 가지, ①과 ③은 두 번씩 (진짜 결함 1건 대비).** 전부 출력이 명백히
이상해서 잡혔다.
① Write 도구에 넘긴 U+2028의 역슬래시-u 이스케이프가 **실제 U+2028 문자로 풀려** 정규식 리터럴
안에 줄 끝이 생겼다(SyntaxError) — 셸이 아니라 **작성 도구가** 한 겹을 먹은 사례다. 역슬래시-n은
그대로 남았다. **그리고 이 항목을 CHANGELOG에 쓰다가 같은 함정에 또 걸렸다** — 이스케이프를 인용한
자리가 실제 문자로 바뀌었다. 파일에 그 표기를 쓰지 말고 이름(U+2028)으로 부를 것.
② 세션 기록에서 우리 도구 이름으로 넓게 찾았더니 **1471건** — grok 자신의 내부 네임스페이스가
`grok_build`라 모든 도구 호출에 붙어 있었다. `use_tool`의 `tool_name`으로 좁히니 4건(실사용 3 + 재현 1).
③ grep에 역슬래시가 든 패턴을 셸로 넘겨 0건이 나왔다(두 번) — 파일은 멀쩡했다.
④ 분석 스크립트를 엉뚱한 폴더 경로로 불렀다(`scratchpad/a34/` vs `scratchpad/`).
⑤ 1.0.41 모델 목록이 "두 개 사라짐"으로 나왔는데 **미인증 컨테이너**에서 잰 값이라 판정하지 않았다
(합성 인증 세션은 두 버전 모두 `grok-4.6, grok-4.5`만 말했다 — 목록은 인증 상태를 따른다).
⑥ Git Bash가 `docker run -v grok-b4-home:/g … ls /g`의 `/g`를 `G:/`로 바꿨다 — `MSYS_NO_PATHCONV=1`.
⑦ "데몬이 떴나"를 `leader|daemon|serve`로 찾았더니 `mcp-server`의 `serve`가 걸렸다 — 걸린 줄은 전부 node였다.
그리고 **통제군이 결론을 지켰다:** 재현이 두 번 실패했을 때 "워커는 우리 도구를 못 쓴다"로 닫을 뻔했다.
같은 시각 다른 세션의 워커는 46ms 만에 연결돼 있었고, 그 비교가 원인(디코더)을 가리켰다.
