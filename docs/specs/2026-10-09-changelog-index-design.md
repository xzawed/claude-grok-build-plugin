# CHANGELOG를 색인으로 — 완료 조건과 설계

- 날짜: 2026-10-09 · 분류: E(오너 목표, 문서) · 릴리스 없음(번들 변경 없음)
- 오너 요청(원문): "현재 CHANGELOG.md 문서파일이 너무 비대해 있습니다. Grok과 함께 논의 하여 문서 내용을 정리할 필요가
  있어 보입니다."

## 왜

- `CHANGELOG.md`는 3,099줄·326,575바이트(커밋된 LF 기준)·항목 106개였다. 에이전트의 파일 읽기는 한 번에 2,000줄·약
  25,000토큰까지라, 어떤 세션도 통째로 읽지 못했다.
- 가장 큰 몫은 번호 붙은 하네스 일지("N회차에서 하네스·테스트·기록이 틀린 것" — v0.2.36 항목 하나에 118개)와 머지 전
  검토 회차 기록이었다(세는 방법에 따라 전체의 38~45%). v0.2.36 항목 하나가 91,734바이트로 전체의 28%였다.
- 원인은 `CLAUDE.md` 8단계와 `docs/11`의 한 문장 "하네스가 틀린 사실은 CHANGELOG에 남긴다"였다 — 상한이 없고, 메커니즘과
  회차 기록을 가르지 않았다(Grok 1차 진단).
- 항목 문장 중 같은 버전 릴리스 노트에 글자 그대로 있는 것은 약 1.6KB뿐이었다(다른 말로 같은 사실을 적은 곳은 재지
  않았다). 지우면 그 문장들을 잃으므로 줄이는 방법은 이관이다(전역 규칙: "삭제가 아니라 이관 — 지우기 전에 갈 곳을
  정한다"). git 이력은 이관처가 아니다 — 작업 트리에서 찾을 수 없고, squash 머지는 커밋 메시지를 바꾼다.

## 완료 조건 (각각 어떻게 확인했나)

1. **잃는 것 0.** 25개 파일의 본문을 이어 붙이면 옛 본문과 바이트 일치; 옛 항목 106개의 조각이 각각 정확히 한 번 나오고
   sha256 다중집합이 같다(Grok 1차가 제안한 해시 분할); 25자 이상 문장이 모두 있다(유지보수자의 분할로 2,744개, 검토자의
   여섯 가지 분할 모두에서 빠진 것 0). 망가뜨린 대조군 넷(줄 삭제·글자 변경·파일 삭제·항목 중복)이 모두 잡혔다. 검토자 하나가
   Python과 git 내부 명령으로 같은 결론을 따로 냈다.
2. **포인터가 깨지지 않는다.** 이 변경 전부터 다른 문서에 있던 CHANGELOG 언급 107줄 중 **포인터는 하나도 고치지 않았다**
   (얼린 릴리스 노트 포함). 고친 9줄은 CHANGELOG의 역할이나 기록 규칙을 말하는 줄이다(`CLAUDE.md` 두 줄, `docs/11`·`docs/09`
   한 줄씩, CONTRIBUTING, README 둘, 테스트 둘). 버전·날짜 포인터는 색인에서 날짜 파일을 찾아 그 제목에 닿고, 번호
   인용("CHANGELOG 57"·"19번"·"하네스·기록 13·14" 같은)은 옮긴 뒤에도 같은 항목의 같은 글이다 — 검토자가 원문과 하나씩
   대조했다. 번호가 **어느 목록**인지는 기계가 아니라 읽어서 확인했다(Grok 2차와 검토자, 아래).
3. **`CHANGELOG.md`는 한 번에 읽힌다** — 204줄, 약 11.6KB. 이력 파일 중 `2026-09-25.md`(700줄, 읽기 도구 기준 약 4.9만
   토큰 — v0.2.36 항목 하나가 9만 바이트다)만 나눠 읽는다; 다음으로 큰 `2026-09-24.md`(약 35KB)는 검토자가 한 번에 읽었다.
   항목별로 나눠도 v0.2.36 하나는 한 번에 안 읽힌다.
4. **다시 비대해지지 않는다** — 규칙을 고치고(`CLAUDE.md` 8단계, `docs/11` 8번 (b), `docs/09` 5b의 기록 안내),
   `mcp-server/test/changelog-shape.test.ts`가 모양을 지킨다. 검토 두 회차가 찾은 우회로를 변이 43개로 넣었고 모두 그
   테스트에서 실패했다; 다음 릴리스 항목·CRLF 저장·NFD 한글 같은 정당한 수정 12가지는 통과했다.

## 설계

- `docs/history/<작업일>.md` 25개 — 옛 `## <날짜>` 절(같은 날짜의 `(2)`·`(3)` 절은 같은 파일에 원래 순서대로)을 글자
  그대로 옮기고 머리 한 줄만 더했다. 옮긴 뒤로 고치지 않는다 — 파일마다 해시를, 폴더 안의 항목 전부(OS가 만드는 파일만
  빼고)를 테스트가 고정한다.
- `CHANGELOG.md` — 머리말(무엇을 어디에 쓰나, 옮긴 항목으로 가는 안내 — 해시 고정) + 새 항목(2026-10-09 이후의 실제
  작업일 아래 글머리표, 300자 이하, 최신이 위, 다른 Markdown 블록을 열지 않는 평문) + "옮긴 항목 색인"(날짜와 제목만, 이력
  파일에서 기계로 도출 — 테스트가 같음을 확인). 옮긴 제목은 요약이 아니라 닻이라 고치지 않는다. 파일 전체는 4만
  바이트·2,000줄 안에 머물고, BOM·제어 문자·방향 전환 문자를 받지 않는다.
- 포인터는 고치지 않는다 — "`CHANGELOG.md` v0.2.35"는 색인이 날짜 파일로 잇는다(한 번 건너기). 이력 파일의 위치를 아는
  곳은 색인 하나뿐이다.
- 새 이력은 글머리표 한 줄과 원천이다(릴리스 노트, `docs/09` §5, `docs/10`, `docs/specs/`·`docs/plans/`). 원천이 따로 없는
  작업(결함 0건인 감사 같은)은 그 한 줄이 기록이다. 하네스가 틀린 사실도 메커니즘 한 줄로 — 다시 밟을 함정이면
  `CLAUDE.md`에 규칙 한 줄과 근거 포인터, 아니면 그 작업의 원천에(원천이 없으면 그 작업의 CHANGELOG 한 줄 안에).
- 하루치 상한은 두지 않았다 — 바쁜 날의 정당한 항목 수를 정할 근거가 없고, 전체 4만 바이트가 비대를 막는다. 넘으면 오래된
  항목을 다시 옮겨야 하는데, 새 항목은 글머리표라 이번처럼 제목으로 색인을 도출할 수 없다 — 방법은 그때 오너와 정하고
  테스트의 고정값을 함께 고친다.

## Grok과의 논의 (3회, `STATIC ANALYSIS ONLY`, 빈 폴더에 원문 그대로)

**1차 — 독립 제안**(유지보수자의 초안을 보여주지 않았다). 채택: 진단(일지 ≈70KB, 회차 기록 ≈55KB, 원인 문장), git 이력은
이관처가 아님, 해시 분할 증명, 얼린 노트는 고치지 않음, 일지를 `docs/09` §5에 붓지 않음, 2,000줄 상한, "파일 하나에 링크
하나" 검사. 기각:
- 얼린 노트가 직접 가리키는 여섯 항목(v0.2.36·v0.2.37·v0.2.33·v0.2.31·v0.2.16·PR #53 — 942줄·129,764바이트)을 제자리에
  두기 — 가장 큰 일지가 색인 안에 남는다. 한 번 건너기로 포인터가 산다는 것을 2차에 반증하게 했다.
- 항목마다 파일 하나(≈100개) — 날짜 포인터가 날짜 파일에 1:1로 맞고, 항목별로 나눠도 v0.2.36 하나는 한 번에 안 읽힌다.
- 옛 항목마다 새 요약 1~3줄 — 과거에 대한 새 주장 수백 줄을 다시 검증해야 한다. 제목이 이미 있다.
- 새 항목 40줄·1,500바이트 상한 — 1년이면 다시 비대해진다.
- 오너의 전역 규칙 파일 고치기 — 레포 밖, 오너의 개인 파일이다. 그 규칙은 이미 "별도 이력 문서"를 허용한다.

**2차 — 종합안 반증.** 판정 `SYNTHESIS_BREAKS_POINTERS` — 구조가 아니라 **안내 문장**이 틀렸다: 초안은 번호만 댄 포인터를
모두 "v0.2.36 항목 안의 번호"로 설명했는데, `docs/releases/v0.2.37.md`의 "CHANGELOG 19번"·"하네스·기록 13·14"는 v0.2.37
항목의 번호다(v0.2.36의 19번은 다른 단락 — 원문으로 다시 확인했다). 안내 문장을 "번호는 그 문서가 다루는 릴리스 항목 안의
번호"로 고쳤다. 같은 판정이 CI 구멍 둘을 짚었다 — 제목만 맞으면 옮긴 본문을 고쳐도 통과, 머리말에 상한이 없음 — 그래서
파일별 해시를 고정했다(머리말은 3차 뒤 해시로 고정). 2차의 사실 하나는 틀렸다(v0.2.31 항목의 작업일을 2026-09-24로
적었다 — 2026-09-23이다); 색인을 기계로 도출하므로 결과에는 영향이 없다.

**3차 — 구현 반증**(머지 전 검토 1회차와 함께). 판정 `FINAL_HAS_DEFECTS` — 번호 포인터는 모두 한 번 건너 닿는다고
확인했고, 테스트의 구멍을 짚었다: 짧은 글머리표를 쌓거나 머리말에 긴 줄 하나를 넣으면 다시 비대해지고, 안내 문장은
포함 여부만 봐서 앞에 모순된 문장을 끼워도 통과했다. 3차의 사실 하나는 틀렸다(옛 파일을 3,100줄이라 했다 — 줄바꿈 3,099개,
마지막 줄이 3,099번째다).

## 머지 전 검토

- **1회차**(검토자 셋 + Grok 3차): 읽기 한도는 줄만이 아니라 토큰이기도 하다, 이력 폴더 검사가 `.md`만 봤다, 날짜 순서·
  중복·빈 절을 안 봤다, 함정의 자리가 전역 규칙("항상 로드되는 곳에 한 줄")과 어긋났다, 크기 수치가 CRLF 체크아웃
  기준이었다 → 바이트 상한, 머리말 해시 고정, 날짜 검사, 규칙 문장.
- **2회차**(새 검토자 둘): 한 칸 들여쓴 줄은 글머리표를 벗어나 GitHub에서 가짜 색인 제목을 보이거나 `<!--`로 진짜 색인을
  숨길 수 있었다(GitHub 렌더러로 확인); NUL·방향 전환 문자, 점으로 시작하는 파일·폴더, 터무니없는 날짜, 들여쓴 색인 제목이
  통과했다; BOM·NFD 한글은 이유를 알 수 없게 실패했다; 이 문서가 "포인터 107줄 중 어느 것도"라고 과하게 말했고, 기록 자리
  규칙이 문서마다 달랐다(`docs/09` 5b 포함) → 평문만 받는 파서, 제어 문자 검사, 폴더 전체 대조, 날짜 범위, BOM·NFC 처리,
  이 문서와 규칙 문장.

- 일지에서 아직 규칙이 되지 않은 메커니즘을 골라 `CLAUDE.md`·`docs/11`로 옮기는 일 — 오너 목표 밖이다.
- `docs/09` 등 다른 큰 문서(검토자 측정으로 `docs/09`는 약 4.1만 토큰, 크기 가드가 없다) — 오너 목표 밖이다.
