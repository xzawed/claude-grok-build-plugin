# v0.2.34 — 상대 경로 `GROK_HOME`을 grok처럼, grok이 실행될 폴더 기준으로 푼다 (A35)

2026-09-24. `GROK_HOME`을 상대 경로로 두면 grok은 그것을 **자기 작업 폴더** 기준으로 푼다. 이 플러그인은
그동안 **묻는 프로세스**(MCP 서버·hook)의 폴더 기준으로 풀었다. 그래서 둘이 서로 다른 홈을 봤다.
세션이 `<작업 폴더>/rel-home`에 있는데도 위임은 "로그인 필요"로 거절됐다(서버와 hook 둘 다). 거꾸로
`billingCaveat`와 resume 세션 색인도 grok이 읽지 않는 파일을 읽었다. 오너가 "grok과 같게 풀기"를 골랐다.

| 잰 것 (grok 1.0.41, win32, `grok du --json`, 쿼터 0) | 답 |
|---|---|
| 상대 `GROK_HOME`은 무엇 기준인가 | **grok의 작업 폴더** — `--cwd`가 있으면 그 폴더(띄운 폴더보다 이긴다), 없으면 띄운 폴더 |
| `~`를 푸나 | **아니다** — `~/.x`는 `<폴더>\~\.x`다 |
| `GROK_HOME`이 없으면 무엇이 홈을 정하나 | win32에서 **`USERPROFILE`**. `HOME`은 아니다(둘 다 바꾸면 `USERPROFILE`이 이긴다) |
| `grok login`도 그런가 | `login --help`만으로 `<띄운 폴더>\rel-home`이 생겼다 — 실제 로그인은 재지 않았다 |

---

## 무엇이 바뀌나

grok 대신 홈을 찾는 곳은 이제 모두 **grok이 실행될 폴더**를 기준으로 묻는다(`env.ts` `grokHomeFor`).
절대 경로 `GROK_HOME`과 미설정은 전과 똑같다 — 폴더와 무관하기 때문이다.

- **위임 3종(delegate·plan·verify)** — 인증 사전 확인과 `billingCaveat`가 작업 폴더(`cwd`) 기준이다.
  resume 세션 색인은 grok이 실제로 뜨는 폴더 기준이다.
- **`worktree: true`** — grok은 `~/.grok-build/worktrees` 아래 **새 폴더**에서 뜬다. 상대 `GROK_HOME`은 그 안(새
  checkout)을 가리키므로 세션이 있을 수 없다. 그래서 worktree를 만들기 **전에** 거절한다. 전에는 작업 폴더를
  확인해 통과시키고, worktree를 만들고, grok을 띄운 뒤 `auth_error`와 `grok login` 안내로 끝났다. 그 안내로는
  고칠 수 없었다 — 다음 worktree도 새 폴더다. 확인은 호출마다 새 이름의 가상 폴더로 한다. 아무것도 미리 있을
  수 없게 하려는 것이다(아래 "머지 전 검토").
- **hook** — 호출의 `cwd`로 찾는다. grok의 폴더를 알 수 없는 호출은 **추측하지 않고 통과시킨다**. `cwd` 없는
  `grok_cli`, 인자에 `--cwd`가 있는 `grok_cli`, `worktree: true` 위임이 그렇다. 판단은 서버와 grok이 한다. 이
  hook의 원칙은 "정상 호출을 절대 막지 않는다"이다.
- **`grok_build_status`·`grok_auth_check`** — `cwd`를 받으면 그 폴더 기준으로 답한다(`grok_auth_check`는 새
  입력). 상대 경로면 **`grokHomeNote`** 가 붙어 어느 폴더의 홈 기준인지 말한다. 명령 템플릿·에이전트·스킬이
  작업의 `cwd`를 넘기도록 바뀌었고, `/grok:status`는 그 메모를 보여준다.
- **거절 메시지** — 상대 경로에서 로그인 확인이 실패하면 메시지 뒤에 같은 메모가 붙는다(서버·hook 둘 다).
  `grok login`만 안내하면 로그인은 사용자 터미널의 폴더에 떨어진다.

## 전후 실측 (배포 번들, 합성 세션·가짜 키, 쿼터 0)

세션은 작업 폴더 Y의 `rel-home`에만 있고, MCP 서버와 hook은 다른 폴더 X에서 뜬다. `GROK_HOME=rel-home`.

| 경우 | v0.2.33 | v0.2.34 |
|---|---|---|
| hook — 위임 `cwd: Y` | **거부** "구독 로그인이 필요합니다" | 통과 |
| status `cwd: Y` | `ready: false`, caveat 없음 | `ready: true`, `billingCaveat`(Y 아래 설정), `grokHomeNote` |
| 위임 `cwd: Y` | 110 ms에 거절, grok 안 뜸 | grok이 Y에서 뜸(합성 세션이라 401 → `auth_error`) |
| 위임 `cwd: Y`, `worktree: true` | 거절(우연히 맞음 — X를 봤다) | 225 ms에 거절, worktree 0개, 메시지가 새 worktree 안의 홈을 말함 |
| hook — `grok_cli --cwd Y -p x`, tool `cwd: Z` | 거부 | 통과 |
| hook — `grok_cli -p x`, tool `cwd: Z`(세션 없음) | 거부(어느 홈인지 말 없음) | 거부 + `Z\rel-home`을 말함 |

작업 중간 판(worktree를 몰랐던 첫 수정)은 worktree 위임을 통과시켰다. 그러자 worktree 1개가 남고 grok이 세션 없이
떠 `auth_error`로 끝났다. 그래서 worktree를 따로 다뤘다.

## 하지 않는 것

- **`~`를 풀지 않는다.** grok이 풀지 않기 때문이다. 풀면 사용자의 의도와는 맞고 grok과는 어긋난다 — 그게 이
  결함이었다.
- **상대 경로를 막지 않는다.** 폴더마다 다른 홈을 일부러 쓰는 사용자는 그대로 동작한다. 그 사용자는 작업 폴더에서
  `grok login`을 하면 된다.
- **POSIX는 재지 않았다.** 위 표는 win32 실측이다. `GROK_HOME`이 없을 때 POSIX에서 무엇이 홈을 정하는지는
  미측정이다.

## 머지 전 검토

- **Grok 반증 (hook).** "정상 호출을 hook이 막는 호출 모양이 있다"는 주장을 호출 모양 5개 × `GROK_HOME` 종류로
  **분류**시켰다. 결과는 `CLAIM_NOT_SHOWN`, 5개 모두 "잘못 막지 않음"이다.
- **Grok 반증 (서버) — 진짜 결함 하나.** 같은 방식으로 조회 4개를 분류시켰더니 worktree 행이 `CAN_DIFFER`였다.
  첫 판의 가상 폴더는 고정 이름 `(새 worktree)`였다. 그 폴더가 세션과 함께 존재하면 확인은 통과한다. 그런데 grok은
  다른 새 폴더에서 뜬다. 게다가 **거절 메시지가 바로 그 경로를 출력했다** — 사용자가 거기서 로그인하라고 초대하는
  셈이었다. 실측으로 확인했다: 그 폴더에 합성 세션을 심자 worktree 1개가 생기고 grok이 떠 `auth_error`로 끝났다.
  가상 폴더를 호출마다 새 이름으로 바꾸자 같은 상태에서 225 ms에 거절되고 아무것도 생기지 않았다.

## 새로 연 것 — B7

모델 자체 키(`config.toml`)가 거부될 때, 래퍼는 `grok login`을 안내하는데 grok 자신은 *"no need to run /login"*
이라고 말했다. 합성 세션으로는 거부된 것이 키인지 세션인지 가를 수 없다. 실세션(컨테이너 전용 로그인)이 필요하다
— `docs/10` B7.
