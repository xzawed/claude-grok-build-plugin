# v0.2.33 — 구독으로 도는 줄 알았던 위임이 다른 키로 청구될 수 있을 때, 그 사실을 `billing` 옆에 적는다

2026-09-24. 구독 모드는 env의 종량제 키 둘을 지운다. 그런데 사용자가 grok의 `config.toml`에 직접 적은
**모델별 키**는 env 정제로 막을 수 없고, 구독 세션보다 먼저 쓰인다. 그동안 응답의 `billing`은 여전히
`"subscription"`을 말했다. `billing`은 설정된 모드에서 파생된 태그라 그 파일을 보지 못하기 때문이다.
이 릴리스는 그 틈을 **알린다**. 막지는 않는다 — 오너의 결정이다.

| 잰 것 | 답 |
|---|---|
| 모델별 키가 세션보다 앞서나 | **앞선다** — 1.0.13, 1.0.30, 1.0.41(디버그 로그 `auth_type=ApiKey`, `model_byok="byok"`) |
| env 정제로 막히나 | **아니다** — 파일에 적힌 키다. `GROK_DISABLE_API_KEY_AUTH`도 세션이 있으면 막지 않는다 |
| 플러그인이 grok과 같은 모델을 짚나 | **같다** — 네 형태 모두 grok 1.0.41 자신의 해석과 일치 |
| 경고가 실행을 바꾸나 | **아니다** — 실행 여부, `status`, `isError`, 이력 행이 전과 같다 |
| 키 값이 새어 나가나 | **아니다** — 모델 id와 변수 **이름**만 싣는다. 가짜 값으로 잰 출력 어디에도 값이 없다 |

---

## 무엇이 보이나

구독 모드에서 `$GROK_HOME/config.toml`(기본 `~/.grok/config.toml`)에 아래 둘 중 하나가 있으면
`/grok:status`와 위임 결과(`grok_build_delegate`·`plan`·`verify`)에 `billingCaveat`가 붙는다.

- 모델 표에 비어 있지 않은 `api_key`
- 모델 표의 `env_key`가 가리키는 변수가 **grok이 받을 env**에서 비어 있지 않음

```json
"billingCaveat": {
  "reason": "config_model_keys",
  "configPath": "C:\\Users\\me\\.grok\\config.toml",
  "models": [
    { "model": "grok-4.7", "via": "api_key" },
    { "model": "gw", "via": "env_key", "envVar": "GATEWAY_API_KEY" }
  ],
  "message": "grok 설정(…)에 자체 자격증명을 가진 모델이 있습니다: … 실행은 막지 않습니다 — …"
}
```

- 파일을 읽거나 해석하지 못하면 `reason: "config_unreadable"`이다. 뜻은 "키 없음"이 아니라 "확인 못 함"이다.
- 파일이 없으면 아무것도 붙지 않는다. api 모드에서도 붙지 않는다(`billing`이 이미 `metered_api`다).
- 명령 템플릿(`/grok:status`·`/grok:delegate`·`/grok:plan`·`/grok:verify`·`/grok:review`)과 `grok-worker` 에이전트,
  `grok-routing` 스킬은 이 메시지를 사용자에게 전하라고 지시한다. 그리고 **그것 때문에 멈추지 말라**고 적는다.

## grok과 같은 해석이어야 경고가 맞다

- **따옴표 없는 `[model.grok-4.6]`은 보고하지 않는다.** TOML에서 그것은 `model."grok-4"."6"`이다. grok은
  `unknown-field` 경고를 내고 무시한다(`grok inspect` 실측). 이 플러그인도 같게 읽는다.
- **`env_key = "XAI_API_KEY"`는 보고하지 않는다.** 구독 모드가 그 변수를 grok에 넘기기 전에 지우기 때문이다.
  grok의 판정도 `model_byok="not_byok"`였다.
- **`env_key` 배열은 처음으로 설정된 변수를 짚는다.** grok은 첫 변수가 비어 있을 때 둘째 변수의 값을 읽었다.
  이 플러그인도 그 변수 이름을 보고한다.

TOML은 새 의존성 없이 직접 읽는다. 라이브러리는 번들에 인라인되는 세 번째 런타임 의존성이 되기 때문이다. 대신
독립 파서(smol-toml, TOML 1.1)와 차등 비교했다. 생성 문서 80,008개에서 불일치가 0이었다. 공식 적합성
코퍼스(toml-test)의 유효 문서(1.0.0 목록 208개, 1.1.0 목록 218개 — 두 목록은 겹친다)에서도 한 번도 실패하지
않았다. 이 하네스가 결함을 볼 수 있는지는 판독기
사본에 결함 3개를 넣어 먼저 확인했다.

## 하지 않는 것

- **그 모델이 실제로 돌았는지는 판정하지 않는다.** 카탈로그 id(`grok-4.7`)와 실행 id(`grok-4.7-build`)가
  다르고, 기본 모델은 grok이 스스로 옮긴다. 그래서 문구는 설정에 대한 사실만 말한다: "그 모델로 도는 위임은
  … 청구될 수 있다".
- **보지 않는 자격증명 경로가 있다.** 모델의 `auth_provider`, `extra_headers`·`env_http_headers`에 담은 키,
  `[model_providers.*]`, `managed_config.toml`·`requirements.toml`은 보지 않는다. 앞의 것들은 실측하지 않았고,
  뒤의 둘은 조직 배포 계층이다. `GROK_CONFIG*` 오버레이는 grok이 모델별 키를 버리므로(실측) 볼 필요가 없다.
- **`grok_cli`·`grok_auth_check`·훅에는 붙이지 않는다.** 오너 범위는 status와 위임 응답이다.

## 한 가지 덧붙임 — grok의 디버그 로그

재측정하다 알게 됐다. grok의 `--debug-file` 로그에는 **실제로 쓰인 모델의 키 값이 평문으로** 남는다(1.0.41).
이 플러그인은 그 플래그를 쓰지 않는다. 계약을 다시 잴 사람은 가짜 키로만 재고, 로그는 스크래치에 둘 것
(계약 §10).

## 재현과 수락

- grok 쪽 실측 전문: `docs/specs/grok-cli-contract.md` §10 끝("플러그인의 감지"). 측정 방법과 차등 비교를 다시
  돌리는 절차: `CHANGELOG.md` 이 버전 항목.
- 쿼터 0 확인: 배포 번들을 합성 `GROK_HOME`(가짜 세션·가짜 키)으로 띄운다. `grok_build_status`가 caveat를
  보고한다. 위임은 막히지 않고 401로 끝나며 caveat를 싣는다.
- 수락: `accept-release.mjs`에 `caveat` 칸이 생겼다. 임시 홈의 가짜 모델 키를 status가 보고하는지, 값은 싣지
  않는지를 본다(spawn 없음). 기능이 없는 0.2.32 설치본은 이 칸만 실패한다(11/12).
