# v0.2.39 — `/grok:plan`이 사용자 허용 규칙대로 쓰기·커밋·push를 하던 결함 (A50)

2026-10-04. 2026-09-30 grok 1.0.44 계약 재측정이 연 결함 중 피해가 가장 큰 항목이다. 오너가 "다음 후속 작업을 Grok과 함께"로
착수를 맡겼고, 최소 수정의 대가(아래)를 받아들일지는 따로 물어 같은 날 받아들였다.

| | 사용자에게 보이던 것 | 이제 |
|---|---|---|
| plan의 실행 | `--permission-mode plan`은 승인되지 않은 호출만 취소했다. 사용자의 허용 규칙(grok 설정, 기억된 승인, Claude Code의 `~/.claude/settings.json`)이 승인한 쓰기·커밋·push·`gh`·MCP 호출은 plan에서도 돌았다. push·`gh`·MCP는 결과에 흔적이 없었다 — `completed`·`planWroteFiles: false`·`committed: false` | plan은 `--permission-mode plan` 바로 뒤에 `--deny Bash --deny Edit --deny Write --deny MCPTool(*)`를 넘긴다. grok은 그런 호출을 허용 규칙이 승인해도 거부한다(셸 "deny rule on bash", 쓰기와 하위 에이전트 "deny rule on edit", MCP "deny rule on mcp"). 파일 읽기는 된다 |
| 대가 | — | plan은 `git status` 같은 읽기 셸도 못 쓴다. 둘을 다 하는 옵션은 찾지 못했다 |
| 약속하던 문구 | `/grok:plan` 설명 "Read-only … (no edits)", "it only skips edits", plan 차단을 grok 버전에 돌리는 문장, worktree가 plan의 "real containment"라는 문장 | 실제 동작대로 고쳤다. plan 뒤 사람 승인을 받는 흐름 여섯 곳(route·delegate 명령, 라우팅 스킬, 워커, `docs/07`, 예제)은 plan 결과의 `planWroteFiles`·`committed`가 `true`면 이미 바뀐 것이니 그것부터 알린다 |

`planWroteFiles`와 `committed`는 그대로 둔다 — 규칙을 지키는 것은 grok이고, 그 두 신호는 이번 실행의 사실이다.

## 실측 (쿼터 0)

배포 번들을 `.claude/tools/mcpcall.mjs`로 띄웠다. 버릴 홈에 합성 세션을 두고, 모델은 도구 호출을 강제하는 가짜 모델이다. 사용자식 허용
규칙은 버릴 홈의 `~/.claude/settings.json`에 넣었다. 가짜 `gh`를 PATH 앞에 두고, 원격은 로컬 bare 저장소, MCP는 기록만 하는 가짜 서버다.

| 시나리오(허용 규칙) | v0.2.38 번들 (1.0.44·1.0.46) | 고친 번들 (1.0.13·1.0.30·1.0.44·1.0.46) |
|---|---|---|
| push·`gh api`·MCP (`Bash(git push:*)`·`Bash(gh api:*)`·`mcp__stubsrv`) | 원격에 push, `gh` 1회, MCP 1회 — 결과는 `completed`·`planWroteFiles: false`·`committed: false` | 셋 다 거부, 효과 0 |
| 쓰기 (`Write`) | 파일 생김, `planWroteFiles: true` | 거부, 파일 없음 |
| 커밋 (`Bash(git commit:*)`) | HEAD 이동, `committed: true` | 거부, HEAD 그대로 |
| 읽기 (규칙 없음) | 파일 읽기와 `git status` 둘 다 됨 | 파일 읽기는 됨, `git status`는 거부 |
| 하위 에이전트 (`*`) | 하위 에이전트가 파일을 씀 | `spawn_subagent` 거부 |

1.0.13·1.0.30은 스크래치 폴더에 받은 공식 바이너리로 쟀다. 두 버전의 `--help`에도 `--deny <RULE>`이 있다 — 이 래퍼가 지원하는
가장 오랜 버전(1.0.13)에서도 이 플래그 때문에 plan이 exit 2로 깨지지 않는다. 1.0.46은 스크래치에서 `probe:contract`로 재
1.0.44 스냅샷과 플래그·서브커맨드·중첩 서브커맨드가 같음을 확인했다.

## Grok과 함께

- **반증(STATIC ANALYSIS ONLY, effort low, 코드 그대로).** 1차는 `CANNOT_TELL`이었다. plan의 모든 분기(새 실행, resume,
  continue, sandbox, worktree, `--prompt-file`)가 규칙을 싣고 호출자 입력으로 규칙을 뒤집을 수 없다는 것은 성립했다. 다만
  `grok_cli`의 spawn이 패킷 밖이었다. `grok-cli.ts`를 넣은 2차는 `ALL_CLAIMS_HOLD`였다.
- **범위.** `grok_cli`는 `--no-auto-update`만 덧붙이는 원시 통로라, 거기서 `--permission-mode plan`을 직접 넘긴 실행에는 이 규칙이
  붙지 않는다. 그 사실을 계약 §6과 `docs/04` §2b에 적었다.

## 테스트

`delegate.test.ts`에 열 개를 더했다. plan의 여섯 분기는 `--permission-mode plan` 바로 뒤의 8토큰을 **리터럴**과 비교한다(상수를
import하면 같은 오타가 양쪽에 들어가도 녹색이다). delegate·verify·resume·continue는 `--deny`가 없고 `--always-approve`가 있다.
다섯 변이는 모두 실패로 잡혔다 — `bash`, `Bsh`, 규칙 하나 빼기, `--disallowed-tools`, plan이 아닌 실행에도 싣기.

## 하지 않은 것

- 이 규칙 밖의 도구(`web_fetch`, 이미지 생성, `send_feedback`, 실행 뒤에도 남는 예약 작업)는 재지 않았다.
- `grok_cli`는 원시 통로 그대로다.
