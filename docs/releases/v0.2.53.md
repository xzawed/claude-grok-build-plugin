# v0.2.53 — plan이 grok의 예약·백그라운드 도구를 빼고 시작한다 (A60)

2026-11-04. `grok_build_plan`(`/grok:plan`)은 v0.2.39부터 `--permission-mode plan` 뒤에 거부 규칙 넷(셸·편집·쓰기·MCP)을 넘긴다(A50).
grok 1.0.44·1.0.46·1.0.70은 이 규칙으로 예약·백그라운드 도구(`scheduler_create`·`workflow`)도 거부하지만("deny rule on edit"),
1.0.13·1.0.30에서는 규칙에 걸리지 않았다 — plan이 반복 예약 작업을 만들고 백그라운드 workflow를 시작해도 결과는 `completed`·
`planWroteFiles: false`로 아무것도 말하지 않았고, 2026-10-04·05에는 그 세션을 이은 승인 실행이 예약 작업을 돌려 파일을 썼다(계약 §6).
`docs/10` A60으로 열려 오너 판단을 기다렸고, 2026-11-04에 오너가 남은 작업을 권장안대로 하라고 맡겨 권장안(플래그를 더한다)대로 고쳤다.
이제 모든 plan이 거부 규칙 바로 뒤에 `--disallowed-tools scheduler_create,scheduler_delete,scheduler_list,workflow`를 넘기고, grok은 네
도구를 모델에 내놓지 않는다.

## 재현 (쿼터 0 — win32, 실제 `~/.grok` 미접촉)

가짜 chat-completions 모델(grok 설정의 `[model.mock]`, `api_backend = "chat_completions"`)이 시나리오마다 도구 호출 하나를 강제하고, grok의
다른 요청은 같은 루프백이 404로 받는다. 버릴 홈(`HOME`·`USERPROFILE`·`GROK_HOME`·`APPDATA`·`LOCALAPPDATA`·`CLAUDE_CONFIG_DIR`)에 합성
세션과 가짜 키, 버릴 git 저장소를 뒀다. 옛 grok은 x.ai의 배포 경로에서 버릴 폴더로 받은 `grok-1.0.13-windows-x86_64.exe`·
`grok-1.0.30-windows-x86_64.exe`(버전 줄 `grok 1.0.13 (5e9a58528b76)`·`grok 1.0.30 (04b7ffed98c6)`)이고, 그 폴더를 `GROK_BIN_DIR`로 줬다 —
번들이 띄운 grok의 버전은 같은 서버의 `grok_cli ["--version"]`으로 확인했다. 1.0.70은 설치본(`f50904eaee6c`)이다. 번들을 stdio로 띄워
`grok_build_plan`(`timeout_ms: 90000`)을 불렀다. v0.2.52 열은 이 PC에 설치된 0.2.52 캐시의 번들(개행을 맞춘 sha256 `9163443d…` — 태그와
같다), v0.2.53 열은 이 릴리스의 번들(`bcb7094c…`)이다 — 하네스가 잰 번들의 해시를 결과 파일에 함께 적었다. 측정 뒤 grok·node 프로세스는
남지 않았다(`Win32_Process`).

| grok | 가짜 모델이 부른 도구 | v0.2.52 | v0.2.53 |
|---|---|---|---|
| 1.0.13 | `scheduler_create`(`interval: "1m"`·`prompt`·`durable: true`) | 도구 25개에 넷 다 제시 → "*Scheduled task created (ID: …, every 1 minute).*" → `completed`·`planWroteFiles: false` | 도구 21개, 넷 다 없음 → 호출 없이 `completed` |
| 1.0.13 | `workflow`(인라인 스크립트) | "*Workflow 'a60probe' started in the background. …*" → `completed`·`planWroteFiles: false` | 같다(도구 21개, 호출 없음) |
| 1.0.30 | `scheduler_create` | 도구 26개에 넷 다 제시 → "*Scheduled task created (ID: …, every 1 minute).*" → `completed` | 도구 22개, 호출 없이 `completed` |
| 1.0.30 | `workflow` | "*Workflow 'a60probe' started in the background. …*" → `completed` | 같다(도구 22개, 호출 없음) |
| 1.0.70 | `scheduler_create`·`workflow` | 도구 26개에 제시, 둘 다 "*Tool `…` was not executed: Denied by permission policy: deny rule on edit*" → `completed` | 도구 22개, 호출 없이 `completed` |

이번 실행에서는 plan 세션 폴더에 `resources_state.json`(2026-10-04·05의 측정이 예약 작업을 찾은 파일)이 없었다. 예약 작업은 1.0.13에서는
그 세션의 `chat_history.jsonl`·`updates.jsonl`에만, 1.0.30에서는 그 둘과 `resume_status.json`(`loops` — id, `interval_secs: 60`, 프롬프트)에
남았다. 승인 실행으로 잇는 경로는 다시 재지 않았다 — 계약 §6의 2026-10-04·05 측정이 원천이다.

## 고친 것

- `delegate.ts`의 새 상수 `PLAN_DISALLOWED_TOOLS_ARGS`(`--disallowed-tools` 하나와 네 이름을 쉼표로 이은 값 하나)를 모든 plan spawn이
  `PLAN_DENY_ARGS` 바로 뒤에 넘긴다 — 새 plan, resume·continue한 plan, 샌드박스·worktree plan, `--prompt-file`로 가는 긴 프롬프트의 plan
  모두. plan이 아닌 위임·검증·resume·continue에는 붙지 않는다.
- 넷은 묶음째다. 1.0.44 시절 빌드에서 일부만 넣은 변이는 세션 시작이 "*Requirements unsatisfied*"(`GrokBuild:scheduler_delete`)로
  실패했고, 1.0.30도 넷 중 하나의 철자가 틀리면 세션 시작이 "*unsatisfied requirements*"(`GrokBuild:scheduler_create`)로 exit 1이었다.
  이 묶음은 1.0.13·1.0.30·1.0.44·1.0.46·1.0.70에서 plan을 시작했다(계약 §6). grok은 없는 이름을 거부하지 않는다 — 1.0.13은 말이 없고,
  1.0.70은 stderr에 "*--disallowed-tools "…" names no tool, so it removes nothing*"을 쓰지만 성공한 plan의 결과에는 stderr가 실리지
  않는다. 그래서 철자는 `delegate.test.ts`가 리터럴로 비교한다.
- 안내: `grok_build_plan`의 도구 설명과 `commands/plan.md`가 네 도구를 뺀다고 말하고, `grok_cli`의 도구 설명은 그 통로로 넘긴
  `--permission-mode plan`에는 거부 규칙도 도구 제거도 붙지 않는다고 말한다. `docs/04`·`SECURITY.md`·계약 §6·`docs/11`·`CLAUDE.md`의
  plan 항목을 맞췄고 `docs/10` A60을 닫았다.

## 하지 않는 것

- **이 수정 전에 만든 세션의 예약 작업.** 세션에 이미 남은 반복 작업은 지우지 못한다. 1.0.30에서 옛 번들(v0.2.52)의 plan이 남긴
  세션을 이 릴리스의 plan으로 이으면(resume) grok이 그 작업을 복원했다 — 모델 요청에 "*These loops are still scheduled despite the
  restart: …*"가 들어갔고 `resume_status.json`은 사라졌다. plan에서는 `scheduler_list`·`scheduler_delete`도 빠지므로 그 작업을 보거나
  지울 수 없다. 그 작업이 언제 발화하는지는 가리지 못했다 — 머지 전 검토가 80초 턴으로 재 보니 그 plan에서도, 같은 방식으로 만든 세션을
  이은 승인 실행 대조군에서도 발화하지 않았다(2026-10-04·05에는 승인 실행이 발화시켜 파일을 썼다 — 계약 §6). 1.0.13(그 파일이 없다)과 1.0.70(옛 plan이
  거부됐다)에서는 복원 문구가 없었다. 2026-10-12 검토가 남긴 단서(그 resume에 `--no-subagents`)는 재지 않았다
  (`docs/plans/2026-10-12-grok-enhancement-backlog.md`).
- **grok이 도구 이름을 바꾸거나 묶음을 나누는 경우.** 이름이 바뀌면 그 도구는 남고(1.0.70의 stderr 경고는 성공한 plan의 결과에 실리지
  않는다), 묶음이 나뉘면 plan이 시작되지 않을 수 있다.
  1.0.70에서는 거부 규칙이 이미 두 도구를 막으므로 지금은 이중 방어다. `probe:contract`는 모델에 제시되는 도구 목록을 보지 않는다.
- **`grok_cli`로 넘긴 `--permission-mode plan`.** 원시 통로라 거부 규칙도 도구 제거도 붙지 않는다(전과 같다 — 도구 설명이 말한다).
- **계획의 2b(끝에 점·공백이 붙은 Windows 작업 폴더).** "작으면 함께"였지만 모든 도구가 쓰는 작업 폴더 확인을 바꾸고 win32에서 따로 재야
  해서 따로 낸다(`docs/plans/2026-11-04-residual-plan.md`).

## 검증

- 새 테스트(`delegate.test.ts`의 A50 묶음 안 A60 열 칸)는 고치기 전 소스에서 plan 여섯 모양이 실패했고 plan이 아닌 넷은 통과했다. 고친
  뒤 모두 통과한다. 변이 열하나 — 이름 하나 빼기(둘), 철자 틀리기, `--disallowed-tools=…` 한 인자, `--disallowedTools`로 쓰기(grok에서는
  `--deny`의 별칭이라 아무 도구에도 맞지 않는 거부 규칙이 된다 — 가장 위험한 변이다), argv에 넣지 않기, 거부 규칙 앞에 넣기, 두 번 넣기,
  plan이 아닌 실행에도 넣기, plan이 아닌 실행에 `--disallowedTools` 넣기, plan에 `--disallowedTools`를 하나 더 넣기 — 가 모두 테스트를
  깨뜨린다(뒤의 둘은 1회차 검토 뒤 보강한 테스트가 잡는다). 수치는 `npm test`가 원천이다.
- 다시 잰 것: 위 표의 v0.2.53 열 — 같은 하네스, 같은 두 호출, 세 버전. 이어 하는 plan도 쟀다 — 같은 서버에서 plan 한 번 뒤 그 세션을
  `resume`(id)으로, 또는 `continue`로 잇는 plan을 치면 세 버전 모두 두 번째 plan이 같은 세션에서 `completed`였고 어느 모델 요청에도 네
  도구가 제시되지 않았다. grok은 세 버전 모두 `--disallowed-tools`를 `--resume`·`--continue`와 함께 받았다.
- `accept-release --repo` 16/16(`serverVersion=0.2.53`).
- SonarCloud는 주석을 되돌리기 전의 분석마다 새 코드의 중복 줄 4.0%(기준 3%)로 게이트를 막았다 — `server.ts`의 도구 등록 블록(원래부터
  중복으로 잡힌 곳) 안에서 고친 세 줄 때문이었다(SonarCloud API의 파일별 새 중복 줄 3과 그 블록의 줄 범위로 가렸다). 그중 `delegate.ts`와 같은 말을 되풀이하던 주석 두 줄을 되돌렸고, 그 주석은 번들에 남는 자리라
  번들이 바뀌어 위의 측정을 모두 최종 번들로 다시 쳤다(결과는 같다).
- 머지 전 검토(독립 리뷰어 한 명 — 오너가 정했다). 지적은 원자료로 다시 확인한 뒤에만 고쳤다.
  - 1회차 BLOCKER 0·MAJOR 1·MINOR 2·NIT 6. MAJOR는 1.0.30의 예약 작업이 `resume_status.json`에도 남았는데 "두 파일에만"이라고 쓴
    것과, 그 작업이 이 릴리스의 plan으로 이은 세션에 복원된다는 것이었다 — 같은 하네스에 시나리오를 더해 다시 재서 확인하고 위 재현 절,
    "하지 않는 것", 계약 §6, `docs/04`, `SECURITY.md`, 코드 주석을 고쳤다. MINOR 둘: 1.0.70은 없는 이름을 stderr로 경고하고 1.0.30은 한 이름이
    틀린 묶음에서 시작을 거부한다(다시 재서 확인하고 "이름을 검증하지 않는다"는 문장들을 고쳤다), `SECURITY.md`의 단정과 빠진 잔여 위험.
    NIT 다섯은 고쳤다 — 낡은 포인터(테스트 주석), `grok_cli` 쪽 문구 둘(`commands/cli.md`, `docs/04`)에 "도구 제거도", `/grok:plan`의
    머리말, `docs/04`의 거부 버전 목록에 1.0.70, plan이 아닌 실행의 테스트가 `--disallowed`로 시작하는 어떤 인자도 도구 목록 자체도 잡게.
    `server.ts`의 주석 한 줄(`PLAN_DENY_ARGS`만 이름 댄다)은 그대로 뒀다 — 위의 중복 기준 때문에 되돌린 바로 그 줄이고, 같은 사실은
    `delegate.ts`에 있다(리뷰어도 2회차에서 동의했다).
  - 2회차(1회차 수정만 좁게) BLOCKER 0·MAJOR 0·MINOR 1·NIT 2. MINOR는 1회차 수정이 `--disallowedTools`를 이 플래그의 별칭이라고 쓴
    것이었다 — grok에서는 `--deny`의 별칭이다(세 바이너리의 도움말 문자열 "*Permission deny rule (compat alias: --disallowedTools)*"와
    1.0.70의 `--help`로 다시 확인했다; 계약 §1도 그렇게 적는다). 테스트 주석·이 노트·커밋 메시지를 고쳤다(단언은 그대로 맞다). NIT: 커밋
    메시지가 "노트가 회차마다 적는다"고 한 것(그 말을 빼고 처분은 노트에 있다고만 했다), 검토가 더 잰 것의 버전·대조군의 세션·하네스
    표현(정확히 했다). 리뷰어가 덧붙인 것 — SonarCloud가 막은 것은 첫 분석만이 아니라 되돌리기 전의 분석마다였다 — 도 고쳤다.
- Grok 반증(5단계)은 하지 않았다 — 2026-11-04 Grok Build 사용량 소진(402)으로 오너가 Grok 검토를 사용량이 돌아올 때까지 보류했다.
  돌아오면 이 릴리스의 코드를 그대로 주고 반증시키며, 실측으로 확인한 지적만 `docs/10`에 새 번호로 연다.
