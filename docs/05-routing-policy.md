# 05. 라우팅 정책 — 언제 Grok Build에 위임하는가

이 문서는 구현 스펙이 아니라 **판단 기준**이다. MCP 서버는 이 판단을 강제하지 않는다
(Claude가 세션 내에서 이 기준을 참고해 delegate tool 호출 여부를 스스로 결정).
멀티에이전트 오케스트레이터의 QA Agent 위험도 라우팅(LOW/MEDIUM/HIGH)과 같은 결을
맞춘다.

## Grok Build로 위임하기 적합한 경우

| 조건 | 이유 |
|---|---|
| 대량 반복 작업 (동일 패턴을 N개 파일에 적용) | 8개 subagent 병렬 처리로 시간 단축 |
| 탐색적/실험적 구현 (여러 방식 중 하나를 고르는 프로토타입) | Grok Build의 병렬 race 방식이 "같은 문제의 여러 답"을 빠르게 만들어냄 |
| 컨텍스트가 작은 독립 작업 (단일 파일/모듈 범위) | 256K 컨텍스트 윈도우로 충분 |
| 리스크가 낮은 작업 (테스트 코드, 문서, 보일러플레이트) | 실패해도 되돌리기 쉬움 |

## Claude가 직접 처리해야 하는 경우 (위임 금지)

| 조건 | 이유 |
|---|---|
| 모노레포 전체 맥락이 필요한 작업 | Claude Code 1M 컨텍스트 vs Grok Build 256K — 컨텍스트 부족 위험 |
| 아키텍처 결정, 설계 판단이 포함된 작업 | SWE-bench 기준 Claude가 더 신뢰도 높음 (벤치마크 격차 존재) |
| 의료/금융 등 규제 도메인 코드 | 규제 도메인 특성상 최종 판단은 항상 Claude/사람이 담당 |
| 보안 관련 변경 (인증, 권한, 암호화) | 낮은 실패 허용도 |
| 최종 코드 리뷰 및 품질 게이트 | "AI executes, human owns quality gates" 원칙 — Grok Build의 결과물도 예외 아님, Claude가 최종 검수 |

## 위임 시에도 지켜야 할 것

- Grok Build가 만든 변경사항은 **Claude가 diff를 검토한 뒤** 커밋 여부를 판단한다.
  MCP 서버가 자동으로 커밋하지 않는다 (Phase 1~3 범위에서는 커밋 자동화 자체를
  넣지 않음).
- 위임 이력은 hook을 통해 로컬 로그에 남긴다 — 나중에 "이 변경이 Claude가 만든 건지
  Grok Build가 만든 건지" 추적 가능해야 한다 (과거 시크릿 하드코딩 사고에서 얻은
  "AI 실행, 사람이 품질 게이트 소유" 원칙과 일관성 유지).

## 비용 관점 참고

이 프로젝트는 서버 레벨 `GROK_BUILD_AUTH_MODE`로 **구독(기본)**과 **API(opt-in,
종량제)** 두 모드를 지원한다(`docs/02-auth-strategy.md`). 비용 고려는 모드에 따라
달라진다:

- **구독 모드(기본, `billing: "subscription"`):** API 종량제가 아니라 정액이므로
  "위임 횟수를 아낄 이유"는 크지 않다. 다만 구독 플랜별 사용량 제한(공개된 고정
  쿼터 없음, tier별 가변)이 있을 수 있으므로, 과도한 자동 위임(예: 매 파일
  저장마다 트리거)은 지양하고 명시적 트리거(슬래시 커맨드 또는 Claude의 판단적
  호출) 중심으로 설계한다.
- **API 모드(`GROK_BUILD_AUTH_MODE=api`, `billing: "metered_api"`):** 호출마다
  종량제로 과금되므로 비용 고려가 그대로 부활한다 — 이 표의 위임 기준(대량
  반복/탐색적/저리스크 작업)을 더 엄격히 적용하고, 불필요한 재시도·과도한
  `--best-of-n` 병렬 실행을 피한다. 모든 delegate 응답에 `mode`/`billing`이
  포함되므로 Claude는 매 호출이 어느 쪽으로 과금됐는지 즉시 알 수 있다.
