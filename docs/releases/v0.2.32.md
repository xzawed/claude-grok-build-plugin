# v0.2.32 — 워커 안에서 이 플러그인이 다시 떠서, 또 다른 Grok을 띄울 수 있었다

2026-09-24. grok CLI는 설치된 Claude Code 플러그인을 **자기 것으로** 로드한다. 그 목록에 이 플러그인도
있다. 그래서 이 플러그인이 위임하는 **모든 워커 안에 이 MCP 서버의 사본이 떠 있었고**, 워커는 그 사본으로
또 다른 grok을 띄울 수 있었다. 이 릴리스는 그 사본이 아무것도 하지 않게 만든다.

| 잰 것 | 답 |
|---|---|
| 워커가 이 플러그인을 로드하나 | **한다** — MCP를 구성한 세션 전부(기록 937개 중 932개, 1.0.13·1.0.30), 1.0.41(Linux) 재현 |
| 워커가 그 도구를 실제로 부르나 | **부른다** — 실사용 3회(1.0.13), 전부 리뷰를 `grok_build_verify`로 다시 넘기려 함 |
| 막는 것이 있었나 | **plan 런뿐** — plan은 MCP 호출을 취소했고, `--always-approve`는 실행한다(9/9) |
| 사용자에게 보인 것 | 바깥 delegate `filesChanged: []` — 그 사이 중첩 런이 **다른 디렉터리**에 파일을 씀 |
| grok의 끄는 스위치로 막히나 | **아니다** — 찾은 스위치는 `~/.claude.json` 서버만 끄고 플러그인 출처는 그대로 둔다 |

## A34 — 검토 범위 밖의 두 번째 Grok

사용자가 보는 것은 하나다. `grok_build_delegate`가 **바뀐 파일 없음**을 돌려준다. 그런데 워커가 이
플러그인의 도구로 띄운 두 번째 grok은 `--always-approve`로 돌고, 워커가 **다른 디렉터리**를 고르면 그
편집은 바깥 결과의 `filesChanged`에 나타나지 않는다. Claude의 diff 검토 게이트는 그것을 보지 못한다.
쿼터도 두 번 나간다.

이론이 아니다. 실사용 기록에서 세 번 나왔다(09-06·07·12, grok 1.0.13). 세 번 모두 "REVIEW ONLY…"
리뷰를 받은 워커가 그 리뷰를 `grok_build_verify`로 다시 넘기려 했다. 그중 한 번은 **worktree로 격리된
런에서 본 저장소를 지목했다.** 셋 다 plan 런이어서 grok이 호출을 취소했을 뿐이다.

**고친 방법.** 이 플러그인이 띄우는 모든 grok에 `GROK_BUILD_WORKER=1`을 붙인다. grok은 자기 env를 MCP
서버에 물려준다 — 실제 사본과 같은 조건(헤드리스 세션, 플러그인 출처 서버)에서 1.0.30(win32)과
1.0.41(Linux, 샌드박스 포함)으로 쟀다. 그래서 워커 안의 사본은 그 표식을 보고 9개 도구를 **목록에 둔 채
전부 거절**한다(`{"status":"blocked","reason":"inside_grok_worker"}`). grok을 띄우지 않고 이력 행도
남기지 않는다.

- **숨기지 않고 거절하는 이유:** 도구가 없으면 워커는 그것을 찾느라 10턴·약 38만 토큰을 썼다(실측, 두 번).
  이유를 말하는 거절은 호출 한 번으로 끝난다.
- **일부가 아니라 전부인 이유:** worktree `apply`·`remove`도 호출자의 트리에 작용한다. 게다가 호출자는
  아직 그 워커의 결과를 기다리는 중이다. 워커에게 필요한 도구는 여기 없다.
- **거절 문구가 변수 이름을 말하지 않는 이유:** 읽는 쪽은 워커 모델이다. 스위치의 이름은 우회 방법으로
  읽힌다(검토 지적). 사람은 `docs/04`와 README 문제 해결 표에서 찾는다.

## 이 변경이 닫는 것과 닫지 않는 것

- **닫는다:** 워커가 **이 플러그인의 도구를 통해** 또 다른 Grok을 띄우는 경로 — 실사용에서 실제로 쓰인
  경로다.
- **닫지 않는다:** `--always-approve` 워커는 셸을 쥐고 있어 `grok`을 직접 실행할 수 있다. 그건 이
  플러그인의 표면이 아니고, 이 변경은 경계가 아니다.
- **작동 조건:** 사본은 grok이 로드한 **설치본**이다. 표식을 붙이는 서버와 거절하는 설치본이 둘 다
  0.2.32 이상이어야 하므로, 플러그인을 갱신한 뒤 **재시작한 Claude Code 세션부터** 보호된다.
- **전제의 감시:** 표식 상속은 grok의 동작이라 업데이트로 바뀔 수 있고, 그래도 유닛 테스트는 녹색이다
  (전부 표식을 손으로 넣는다). 그래서 `npm run probe:contract`에 `workerMarker` 검사를 넣었다. 합성
  인증으로 헤드리스 세션을 하나 열어(첫 요청이 401 — 쿼터 0) 표식이 플러그인 MCP에 닿는지 재고,
  닿지 않으면 `--strict`가 실패한다. 이 probe는 부모 env의 `GROK_*`·`XAI_*`를 **전부** 지우고 돈다 —
  재검토가 찾은 구멍이다: grok은 문서화된 토큰 발급기(`GROK_AUTH_PROVIDER_COMMAND`)로 거부될 세션을 다시
  인증한다(가짜 발급기로 재현, 고친 뒤 호출 0회). 세션이 받아들여지거나 grok이 플러그인 서버를 아예 안
  띄우면 그것도 `--strict` 실패다.

Grok에게 후보 경로 7개(표식 미도달, 이름 불일치, 등록 순서, 배선 누락, 우회 spawn, 원 핸들러 호출, 다른
등록 경로)를 분류시켰고 `HOLE_CLOSED`였다. 머지 전 검토 에이전트 세 명(코드·테스트 / 문서 / 반례)은
구멍을 찾지 못했다. 대신 위의 범위와 조건, 그리고 아래 숫자들을 바로잡았다.

## grok 쪽 결함 하나 — 이 플러그인의 것이 아니다

grok의 stdio MCP 디코더는 8 KiB를 넘는 메시지를 **바이트 8192에서 잘라** 읽는다. 이 서버의 `tools/list`
응답은 한 줄 12,625바이트다. 기록 937개 중 해석 오류가 난 세션이 335개(36%), 그 때문에 연결에 실패한
세션이 292개다(타임아웃 문구는 1.0.13 `65s`, 1.0.30 `70s`). **이 결함이 A34를 간헐적으로 가렸다** —
재현이 두 번 실패한 이유다. 우리 출력은 정상이라 기록만 남기고 손대지 않았다(계약 §14).

## 재현과 수락

- 전문: `docs/specs/grok-cli-contract.md` **§14**. 로드 경로, env 상속, 스위치의 범위, 권한 게이트(버전별),
  디코더 오프셋, 세션 기록을 grep할 때의 함정(grok 자신의 네임스페이스가 `grok_build`다)이 있다.
- 쿼터 0 수락: `accept-release.mjs`에 **A34** 검사가 추가됐다. 표식을 단 세션에 재현에서 워커가 보낸 중첩
  호출(+`best_of_n`)을 보낸다. 모든 홈(`GROK_HOME`·`HOME`·`USERPROFILE`)을 임시 폴더로 돌리므로, 어느
  버전의 번들을 채점하든 인증 확인에서 멈추고 아무것도 쓰지 않는다.
