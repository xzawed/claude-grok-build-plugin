## A27 — `total`이 자기 breakdown과 어긋나 성공률을 낮게 보고할 수 있었다

`summarizeHistory`는 파싱된 행을 전부 `total`에 넣는데, `accumulate`는 `mode`/`billing`/`status`가
**아는 값일 때만** 버킷을 올렸다. 그래서 JSON 객체로 파싱되지만 값이 미지인 행은 `total`에만
들어가고 어느 버킷에도 안 들어갔다.

문제는 헤드라인 둘이 **모두 `total`로 나눈다**는 것이다
(`successRatePct = byStatus.completed / total`, `subscriptionBillingPct = byBilling.subscription / total`).
즉 그런 행 하나가 **성공률을 조용히 낮춘다** — `completed > 0`일 때.

**실측 (`.claude/tools/mcpcall.mjs` → `dist/index.js`, 정상 행 1개 + 적대적 행 1개):**

| 적대적 행 | 수정 전 total / sum(byStatus) | 수정 후 |
|---|---|---|
| `{"mode":"nonsense","status":"nonsense"}` | 2 / **1** | 2 / 2 |
| `{"status":null}` | 2 / **1** | 2 / 2 |
| `{"ts":…,"cwd":"/b"}` (mode·status 없음) | 2 / **1** | 2 / 2 |
| `{}` | 2 / **1** | 2 / 2 |
| `[1,2,3]` · `null` · `"hello"` · `42` · `NOT JSON {{{` | 1 / 1 (건너뜀) | 1 / 1 (유지) |

10개 사례 중 **4건 INCONSISTENT → 0건.** 비객체·비JSON 행은 전과 같이 `readHistory`가
건너뛰므로 `total`에 들어가지 않는다.

**현재 위험은 없었다 — 잠재였다.** 오너의 실제 326행 파일은 total = byMode = byStatus =
byBilling = 326으로 정합했고 파일 직접 재계산도 일치했다. 도달 경로는 **버전 스큐**다:
`history.jsonl`은 append-only이고 **설치본보다 오래 산다.** 오늘 writer는 모든 내부 status를
4개 버킷으로 정규화하지만(`CLI_STATUS_TO_DELEGATE` + `?? 'grok_error'`), 다른 status를 아는
빌드가 쓴 행이 같은 파일에 남는다.

**수정:** 미지 값을 **버리지 말고 `unknown`으로 센다.** 원래 의도("malformed 행에 throw하지
않는다")를 유지하면서 빠진 반쪽을 채운 것이다 — 이제 세 breakdown이 **항상 `total`과 같고**,
외부 행은 헤드라인을 움직이는 대신 **눈에 보인다**. `byMode`·`byBilling`·`byStatus`에 `unknown`
키가 추가된다 (가산적 변경).

**기각한 대안:** 미지 행을 `total`에서도 빼는 것. 그러면 파일에 327행이 있는데 326으로 보이는
**조용한 데이터 손실**이 되고, 이 레포가 A17에서 이미 배운 것("0이라는 답은 두 가지 사실을
구별해야 한다")과 정면으로 어긋난다.

## A26 — 감사 하네스가 서버 사망을 4분간 "정지"로 바꿨다

`.claude/tools/mcpcall.mjs`에 `child.on('exit')`·`on('error')`가 **없었다.** pending 콜백은
`resolve`만 하고 `reject`하지 않으므로, 자식이 답하기 전에 죽으면 240초 타이머 말고는 그
promise를 깨울 것이 없었다.

**실측:** 잘못된 `GROK_BUILD_AUTH_MODE`로 서버는 **100ms 안에** stderr 한 줄 + exit 1로 끝난다.
그런데 이 하네스를 거치면 **240초 정지**였고, 진단은 그동안 `stderr` 변수에 담긴 채 출력되지
않았다. 그리고 그보다 짧은 호출자 타임아웃(실측: 120초 캡)에서는 **진단을 아예 잃는다** —
감사자에게는 이유 없는 행으로만 보인다.

| | 수정 전 | 수정 후 |
|---|---|---|
| 잘못된 모드 | 240초 정지 (120초 캡에서는 진단 소실) | **449ms** · exit 1 · 서버 진단 한 줄 그대로 출력 |
| 정상 호출 · `list` | 정상 | 정상 (무변경) |

**이건 배포물이 아니다.** 그러나 `CLAUDE.md` "작업 수행 방법" **1단계가 이 하네스를 지정**한다 —
감사 도구가 실패를 정지로 바꾸면 다음 감사가 조용히 틀린다. 같은 레포 `accept-release.mjs`의
`runServerWithBadMode`는 이미 자식 close를 올바로 처리하고 있었으므로, 이 수정은 설계 변경이
아니라 **누락을 메운 것**이다.

## 결함이 아닌 것 (감사가 확인하고 넘어간 것)

- **절대 원칙 1은 차등 실측으로 성립한다.** 카나리아 키를 서버 env에 심고 `GROK_BUILD_AUTH_MODE`만
  바꾸니 자식이 `You are logged in with grok.com.` ↔ `You are using XAI_API_KEY.`로 갈렸고,
  카나리아 **값**은 tool 출력·이력 어디에도 없었다. 326행 전체에 raw `xai-` 형태 0건.
- **A24가 일반화돼 있다 (새 측정).** `grok --help` 실측 결과 프롬프트를 싣는 플래그는 4개다 —
  `-p` · `--single` · `--prompt-file` · `--prompt-json`. 8가지 형태(분리·붙임)를 전부 쳤더니
  로그아웃 상태에서 **전부 deny**, 읽기 전용은 **전부 allow**. 이전에 측정된 적 없는 사실이다.
- **입력 검증·표면:** 배포 번들 프로브 15/15 계약대로(가드 전부 spawn 이전 sub-second),
  입력 학대 6/6 거부, hook 22-case 매트릭스에서 의미 있는 20건 정확.
- **문서:** 유지보수 문서 66개 스윕 → 죽은 포인터 **0건**. 후보 10건은 전부 오탐이었고, 그중
  `02-authentication.md`·`18-sandbox.md`는 grok 설치본 user-guide를 가리키는 **외부 인용**으로
  `~/.grok/docs/user-guide/`에 실재함을 확인했다.
- **릴리스 무결성:** `accept-release` 10/10 ×2(레포·캐시), 캐시 번들 = 커밋 blob = 워킹트리
  **내용 동일**(차이는 CRLF뿐, 정확히 줄당 1바이트).

## 절차 규칙이 하나 늘었다

`CLAUDE.md` "작업 수행 방법"에 **8단계(수행 후 검증·과정 감사)**를 넣었다. 근거는 이 감사
자체다 — 실제 결함 2건을 찾는 동안 **내 측정 하네스가 6번 틀렸다**(heredoc 역슬래시 접힘으로

명백히 이상해서 잡았지, 그럴듯했다면 그대로 보고됐을 것이다.
