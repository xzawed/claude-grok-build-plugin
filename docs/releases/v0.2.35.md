# v0.2.35 — Windows에서 grok이 **여는** 이름으로 세션을 찾는다 (A36)

2026-09-25. A36은 "`GROK_HOME`에 끝 공백이 붙으면 로그인해 있어도 '로그인 필요'로 거절한다"였다. 그 근거는
`grok du --json`이 공백을 버린 홈을 보고한다는 것이었다. **재 보니 그 전제가 틀렸다.** grok이 세션을 찾는 곳은
`du`가 보고하는 곳이 아니었다. 끝 공백이면 **grok도 로그인하지 않은 상태**다 — 플러그인의 "로그인 필요"가 맞았고,
틀린 것은 "`grok login`하라"는 안내뿐이었다. 대신 재는 동안 **진짜 불일치**가 나왔다. 점 하나로 끝나는 경로 성분,
그리고 점·공백으로 끝나는 작업 폴더다. 불일치는 양쪽으로 났다. 대부분은 grok이 로그인해 있는데 플러그인이
"로그인 필요"로 거절한 것이다. 이름이 점으로 끝나는 폴더가 실제로 있으면 반대도 났다 — grok은 로그인하지 않았는데
플러그인이 "준비됨"이라 했다.

| 잰 것 (grok 1.0.41, win32, 합성 세션, 쿼터 0) | 답 |
|---|---|
| `GROK_HOME` 끝 공백 (cmd의 `set GROK_HOME=C:\x && …`) | **grok도 세션을 못 찾는다**("Not signed in"). `grok du`만 다듬은 홈을 보고한다 |
| 점 하나로 끝나는 성분 (`C:\x.`, `C:\a.\h`) | grok은 점을 뺀 폴더에서 찾는다 — 플러그인은 못 찾았다 |
| 상대 `GROK_HOME` + 점·공백으로 끝나는 작업 폴더 | grok은 다듬은 폴더(`inspect`가 보고) 기준으로 푼다 — 플러그인은 원래 이름 아래를 봤다 |
| 홈 성분 끝의 점 둘 이상(`h..`), `\\?\` 경로 | 아무도 바꾸지 않는다 — 전과 같다 |

오라클은 셋이었다. `grok du`는 홈을 다듬어 보고한다. 합성 세션을 둔 `grok models`와 위임 모양의 헤드리스 실행은
세션을 실제로 여는 쪽을 보고하고, 함께 잰 칸에서 서로 전부 일치했다. 전문: 계약 §8.

---

## 무엇이 바뀌나

Node의 fs는 드라이브·UNC 경로를 `\\?\` 형태로 바꿔 Windows 경로 정규화를 건너뛴다. grok(Rust)은 보통의 Win32
경로로 열어 정규화를 거친다. 그래서 정규화가 이름을 바꾸는 곳마다 둘이 다른 파일을 봤다. 이 릴리스는 Windows에서
grok 대신 찾는 모든 곳 — 인증 사전 확인·`billingCaveat`·resume 세션 색인·hook — 이 **grok이 여는 이름**으로
찾게 한다(`env.ts` `grokHome`·`grokHomeFor`). 규칙은 잰 것 둘뿐이다.

- **R1** — 뒤에 성분이 더 오는 성분은 끝의 점이 **정확히 하나**일 때 그 점을 잃는다(`h.` → `h`, `h .` → `h `;
  `h..`·`h...`는 그대로 — 이름이 `h.`·`h..`인 실제 폴더로 확인했다). 홈의 모든 성분이 여기 해당한다 —
  `auth.json` 앞에 오기 때문이다.
- **R2** — grok의 작업 폴더는 마지막 성분 끝의 공백·점을 잃는다(`w..`도 `w`가 된다). 경로가 구분자로 끝나면
  아니다(`w \`이면 grok은 그 폴더에 들어가지도 못한다). `.`·`..`가 먼저 풀린다(`w\x\..`는 `w`).
- 이 규칙들이 바꾸지 않는 값은 **전과 똑같은 문자열**로 돌아온다. `\\?\`는 건드리지 않는다. POSIX도 기본 홈도 바뀌지 않는다.

**끝 공백은 고치지 않고 말한다.** grok이 공백까지 경로로 쓰므로, 지우고 찾으면 거짓 "준비됨"이 된다. 대신
`grokHomeNote`가 원인을 말한다 — status·auth check의 필드로, 그리고 거절·hook deny 메시지 뒤에 붙는다. hook은 홈이
폴더와 무관하면 폴더를 모르는 호출에서도 붙인다(폴더에 따라 달라지는 값은 폴더를 모를 때 hook이 확인하지 않는다 — A35).
`/grok:status`의 `nextSteps`도 그 메모를 먼저 가리킨다. 예:

> GROK_HOME('C:\x ')의 끝에 스페이스 1자가 붙어 있습니다. grok은 이 값을 그 문자까지 그대로 경로로 쓰므로 'C:\x'의
> 세션은 쓰이지 않습니다 — 의도한 문자가 아니라면 GROK_HOME을 'C:\x'로 고친 뒤 Claude Code를 재시작하세요(`grok
> login`보다 먼저). (cmd의 `set GROK_HOME=C:\x && …`는 `&&` 앞의 공백까지 값에 넣습니다.)

앞에 붙은 공백이나 탭·줄바꿈이면 그 종류와 위치를 말한다(끝의 탭·줄바꿈, 드라이브 경로 앞의 공백이면 grok의 `du`·`models`가
exit 1, os error 123). cmd 설명은 끝 공백에만 붙인다. 값이 **공백뿐**이면(cmd에서 변수를 지우려던
`set GROK_HOME= && …`가 공백을 넣는다 — 실측) 기본 홈을 쓰려던 것이라 보고 **변수를 지우고 재시작하라고** 말한다.
빈 값은 grok에게도 미설정이지만, 공백뿐인 값은 아니다(grok도 "not authenticated").

## 전후 실측

배포 번들(`mcpcall.mjs`, `accept-release.mjs`)과 grok을 같은 입력으로. 세션은 합성(쿼터 0).

| 경우 | grok | v0.2.34 | v0.2.35 |
|---|---|---|---|
| `GROK_HOME=<dir> ` (끝 공백) | Not signed in | `not_logged_in` (원인 설명 없음) | `not_logged_in` + 공백을 말하는 `grokHomeNote` |
| `GROK_HOME=<dir>.` | logged in | `not_logged_in` | `ok: true` |
| 상대 `GROK_HOME`, status `cwd: <task>.` | logged in | `ready: false` | `ready: true` |
| 같은 상대 홈, hook — `grok_cli -p`, `cwd: <task>.` | — | **deny** "로그인 필요" | allow |

- **차등 비교 — 손으로 고른 81가지 표기**(점·공백으로 끝나는 실제 폴더, Grok이 제안한 8가지 포함):
  v0.2.34 불일치 24(거짓 거절 23, 거짓 "준비됨" 1) → v0.2.35 **0**.
- **차등 비교 — 생성한 357가지 표기 × 세션 위치 2곳**(수정이 예측한 곳 / 원래 철자 그대로의 곳, 714회):
  v0.2.34 불일치 456(두 방향 228씩) → v0.2.35 **0**. 표기: 드라이브 경로 128(`<D>\a<끝1>\h<끝2>`, 끝 구분자 유무)·
  슬래시 64·상대 경로 128(`h<끝>` × 작업 폴더 `w<끝>`, 끝 구분자 유무)·UNC `\\localhost\C$` 8·드라이브 없는 루트 8·
  중간 성분 16·통째로 점·공백인 성분 5. 끝은 없음·`.`·`..`·`...`·공백·`. `·` .`·`.. .` 여덟 가지.
- **재측정 도구로 남겼다: `npm run probe:home`**(win32, 쿼터 0). 위 생성 표기에 실제 폴더 7가지를 더해 grok에게 묻고,
  불일치가 있으면 exit 1이다. 이 릴리스의 소스로 728회, 불일치 0.
- `accept-release`에 `A36` 칸을 넣었다(spawn 없음). 설치된 0.2.34는 이 칸만 실패한다(13/14).

## 하지 않는 것

- **공백·점으로 끝나는 작업 폴더로 위임하면 여전히 "cwd 디렉토리가 존재하지 않거나…"로 거절된다.** grok은 그
  폴더를 다듬어 들어가지만, 위임의 폴더 확인은 Node가 그 이름 그대로 찾는다. 이 릴리스는 **인증 확인**을 grok에
  맞췄다 — 그래서 그런 폴더의 거절 이유가 "로그인 필요"(틀림)에서 "폴더 없음"으로 바뀌었다.
- **`GROK_HOME`의 공백을 대신 지우지 않는다.** grok이 지우지 않으므로 지우면 거짓 "준비됨"이 된다.
- **`grok login`이 공백 붙은 경로에서 무엇을 하는지는 재지 않았다** — 실제 OAuth가 필요하다. 그래서 안내는
  "변수를 먼저 고치라"까지만 말한다.
- **POSIX는 바꾸지 않았고 재지 않았다.** 이 정규화는 Windows의 것이다.
- **UNC의 서버·공유 이름과 기본 홈(`USERPROFILE`)의 끝 점은 다루지 않는다** — 재지 않았다.
- **`\??\`로 시작하는 `GROK_HOME`은 여전히 "로그인 필요"다**(반례 검토가 찾음, v0.2.34부터 같음). grok은 이 NT 내부
  접두사를 받아들이지만 Node의 fs는 그런 경로를 아예 조회하지 못한다. 사람이 설정 폴더로 쓰는 표기가 아니고, 틀리는
  쪽이 안전한 쪽(거짓 거절 + 안내)이라 코드를 더하지 않았다.

## 머지 전 검토

독립 검토자 셋(코드·테스트 / 문서 / 반례)과 Grok의 메시지 판정이 첫 커밋을 봤다. 지적은 다른 방법으로 다시 확인한 뒤
두 번째 커밋에서 고쳤다.

- **코드:** 막을 결함은 없었다. 검토자는 GetFullPathNameW를 두 번째 오라클로 생성 입력 약 13만 가지를 돌려 회귀 0을
  봤다. 확인된 빈틈 넷: hook이 폴더 없이도 메모를 붙이는 새 동작에 테스트가 없었다(되돌려도 전부 녹색) → 테스트 추가.
  세션이 실제로 이름 끝에 공백이 있는 폴더에 있으면 확인은 통과하는데 메모가 "고치라"고 해 동작하는 사용자를 옮기게
  했다 → 두 경우 모두 참인 문장으로. `\\?\` 작업 폴더를 그대로 두는 분기와 메모의 앞/끝 표현에 테스트가 없었다 → 추가.
  새 테스트는 각각 되돌린 코드에서 실패하는 것을 봤다.
- **반례:** 260자 넘는 경로, 장치 이름(CON·NUL…), `\\?\`·`//?/`·`\\.\`, 유니코드 공백, 8.3 짧은 이름, `subst` 드라이브
  루트, `..`로 올라가기 등에서 grok과 전부 일치. 불일치는 위의 `\??\` 하나.
- **문서:** 약 20곳 — 커밋되지 않은 하네스를 가리키던 계약 문장(→ `probe:home`을 커밋), "불일치는 한 방향"이라는 요약
  (실제로는 양방향), "`grok login` 대신"과 "먼저"가 섞인 안내, 폴더 없는 hook 메모의 적용 범위, 재지 않은 `inspect`,
  `nextSteps`가 메모와 반대로 로그인만 안내하던 것 등.

## Grok과 함께 한 것

- **오라클로서의 grok이 전제를 뒤집었다.** `du`·`models`·헤드리스 실행을 같은 입력에 나란히 대자 `du`만 달랐다.
- **Grok의 제안 8가지**가 전부 v0.2.34의 진짜 불일치였고, 차등 비교 표에 들어갔다.
- **Grok의 메시지 판정** — 측정한 사실 6행을 주고 새 안내문이 정확하고 따를 만한지 분류시켰다. 진짜 지적이 넷이었다:
  재시작하라는 말이 없다(두 행에서 — 값은 Claude Code가 시작할 때 읽힌다), 탭을 "공백 문자"로만 불렀다, 앞 공백에 cmd `&&`
  설명을 붙였다, 앞 공백·탭에서 grok은 세션을 놓치는 게 아니라 실패한다. 전부 고쳤다. 나머지 1건(A35 메모의 `~` 문장)은
  준 사실 밖이라 기각했다 — 그 문장은 계약 §8에 측정돼 있다.
- **끝나지 않은 것.** 기본 effort의 35행 분류와 후보 제안은 `resume`까지 캡(300·240초)에 걸렸다. 행 수를 줄이고
  `effort: low`로 주자 제안(8행)과 메시지 판정(6행)은 3턴에 끝났다 — 둘을 함께 바꿨으니 어느 쪽 덕인지는 가르지
  않았다. 수정본 반례 찾기는 `effort: low`로도 캡에 걸렸고 답은 "끝낸 후보가 없다"였다. **통과로 세지 않았다** —
  반례는 grok 자신을 독립 구현으로 둔 차등 비교로 찾았다.
